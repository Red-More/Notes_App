# 第二部分：包管理与构建

> 本部分对应第 6–10 章。
> 这一层解决的核心问题：**同一份 Rust 源码，为什么在桌面构建时完全不碰 NDK，而在 Android 构建时却要拉进一个 212 MB 的 C++ 静态库？**
> 答案不在代码里，而在 `Cargo.toml` 的 feature 开关、`Cargo.lock` 的精确版本、`[[example]]` 的编译门槛，以及目标三元组的选择上。

在开始之前，先把本部分会反复出现的四个术语定下来。它们很容易混，混了就会看不懂构建日志。

| 术语 | 定义 | 生活化类比 |
|---|---|---|
| **包（package）** | Cargo 管理的最小发布单位，有名字、版本、作者、许可证，由 `Cargo.toml` 描述 | 一个快递箱：外面贴着面单（名字、版本），里面装着若干件货物 |
| **crate** | 一次编译产出的单元，分库 crate（`lib`）和二进制 crate（`bin`）两种 | 箱子里的一个独立包裹；一个箱子可以装多个包裹 |
| **依赖（dependency）** | 当前包需要使用的外部包 | 你做菜要用别人的调料，调料不在你厨房里，得先买回来 |
| **目标三元组（target triple）** | 描述“给哪种 CPU + 哪种操作系统 + 哪种运行环境”编译的字符串，如 `aarch64-linux-android` | 快递的收件地址：写错一个字段，包裹就送错城市 |

**一个常见误解先说清楚**：一个 package 里可以有多个 crate。本项目 `src-tauri/Cargo.toml` 里 `[package] name = "app"` 是包名，`[lib] name = "app_lib"` 是库 crate 名，`[[example]] name = "mnn_smoke"` 是 example crate 名。三个名字都不一样，这是合法的，也是 Tauri 项目的常见做法。[仓库已核实]

## 第 6 章 crate、Cargo.toml 与 Cargo.lock

### 6.1 本章要解决什么问题

你打开 `src-tauri/` 目录，看到两个文件：`Cargo.toml` 和 `Cargo.lock`。它们看起来都是“配置”，为什么需要两份？删掉一份会怎样？为什么 `Cargo.lock` 里会有 533 个 `[[package]]` 条目，而我只写了二十来行依赖？[仓库已核实：`src-tauri/Cargo.lock` 共 533 个 package 条目]

本章要让你能回答：

- `Cargo.toml` 的每个字段在构建流程的哪一步被读取；
- `Cargo.lock` 到底锁住了什么，为什么它必须提交进 Git；
- `crate-type = ["staticlib", "cdylib", "rlib"]` 这三种产物分别给谁用。

### 6.2 概念：从直觉到机制

#### 6.2.1 直觉：manifest 是“需求清单”，lock 是“实际采购单”

把构建一个 Rust 项目想成开一家餐厅：

- `Cargo.toml` 是**菜单需求**：“我需要面粉（`serde` 1.0）、需要黄油（`tauri` 2.12.3）”。它写的是**范围**，`"1.0"` 意思是“1.0 及以上、2.0 以下”。
- `Cargo.lock` 是**采购单存根**：“这次实际买到的是面粉 1.0.228、黄油 2.12.3”。它写的是**精确版本 + 校验和**。

需求清单可以长期不变，但市场（crates.io）上的版本会变。如果只有需求清单，今天构建和明天构建可能装进不同版本的依赖，别人的机器和你的机器也会不同。`Cargo.lock` 的作用就是把“这一次实际装了什么”钉死。

#### 6.2.2 机制：Cargo 的解析流程

```
        Cargo.toml（你写的范围）
                │
                ▼
     ┌──────────────────────┐
     │ 依赖解析（resolver） │  ← 读所有依赖的 Cargo.toml，做版本求解
     └──────────────────────┘
                │
                ├── 没有 Cargo.lock ──→ 求解一次，把结果写入新 lock
                │
                └── 已有 Cargo.lock ──→ 尽量沿用已锁定版本，只在必要时升级
                │
                ▼
     ┌──────────────────────┐
     │ 下载 + 校验 checksum │  ← 用 lock 里的 checksum 校验 tarball
     └──────────────────────┘
                │
                ▼
     ┌──────────────────────┐
     │ 编译（按 feature 裁剪）│
     └──────────────────────┘
```

关键点：**版本求解只做一次，结果写进 lock；后续构建不再重新求解**（除非你改 `Cargo.toml` 或显式 `cargo update`）。这就是“可复现构建”的基础。

#### 6.2.3 细节：逐个字段读本项目的 `Cargo.toml`

下面是 `src-tauri/Cargo.toml` 的 `[package]` 段，逐行解释。[仓库已核实]

```toml
[package]
name = "app"
version = "0.1.0"
description = "A Tauri App"
authors = ["you"]
license = ""
repository = ""
edition = "2021"
rust-version = "1.88"
```

| 字段 | 含义 | 在本项目里的实际影响 |
|---|---|---|
| `name` | 包名 | 生成二进制默认叫 `app`；但 `[lib]` 又把它改成了 `app_lib` |
| `version` | 包版本 | 只影响发布与依赖引用，不影响产物文件名 |
| `description` / `authors` / `license` / `repository` | 元数据 | `license = ""` 是**空值**，对内部项目无害；若要发布到 crates.io，必须填 SPDX 标识符 |
| `edition` | 语言版本 | `2021` 决定你可用哪些语法（如 `let else`），与编译器版本不是一回事 |
| `rust-version` | 最低编译器版本（MSRV） | `1.88` 是硬约束：低于 1.88 的 rustc 会在解析阶段直接报错，而不是编译到一半才失败 |

注意 `rust-version = "1.88"` 上面那行注释：[仓库已核实]

```toml
# Android Keystore 依赖（android-native-keyring-store 1.0）要求 rustc ≥ 1.88。
rust-version = "1.88"
```

这条注释解释了因果：**不是项目自己想用新语法，而是某个 Android 专属依赖抬高了门槛**。这正是“依赖会反向约束工具链”的典型例子。当你在 CI 上遇到 `rustc 1.85.0 is not supported by the following package` 这类错误时，第一反应应该是查 `rust-version` 的来历，而不是无脑升级。

#### 6.2.4 细节：`[lib]` 与 `crate-type`

```toml
[lib]
name = "app_lib"
crate-type = ["staticlib", "cdylib", "rlib"]
```

`crate-type` 是一个列表，表示**同一次编译要产出几种形态的库**。三种形态的用途必须分清，否则后面链接章节会全程困惑：

| crate-type | 产物（Linux/Android 目标） | 谁在消费它 | 类比 |
|---|---|---|---|
| `staticlib` | `libapp_lib.a` | Android 的 Gradle/NDK 打包流程、C 链接器 | 一整箱预装好的零件，直接焊进最终产品 |
| `cdylib` | `libapp_lib.so` | 需要动态加载的平台（如某些桌面场景、移动端 JNI 入口） | 一个可插拔模块，运行时才插上 |
| `rlib` | `libapp_lib.rlib` | 其他 Rust crate（包括本包的 `examples/`、`tests/`） | Rust 自己的“中间件包裹”，只有 rustc 认识 |

为什么要三种都产出？因为 Tauri 在 Android 上需要通过 `staticlib` 把 Rust 主逻辑交给原生侧链接；而 example 与单元测试又需要 `rlib` 才能 `use app_lib::...`。[通用原理 + 项目配置]

顺带说明一个易踩的点：`staticlib` 产物会**把 Rust 标准库一起静态打包进去**，所以体积明显大于 `rlib`；这也是后面“212 MB 静态库 vs 5 MB 可执行文件”话题的伏笔。

#### 6.2.5 细节：`Cargo.lock` 的结构

打开 `src-tauri/Cargo.lock`，头部是：[仓库已核实]

```toml
# This file is automatically @generated by Cargo.
# It is not intended for manual editing.
version = 4
```

逐项解释：

- 第一行是警告：**手改无效**，下次 `cargo build` 可能重写。
- `version = 4` 是 lock 文件格式版本，不是项目版本。格式 4 对应较新的 Cargo（含更紧凑的依赖表示）。版本号变大时，老 Cargo 会拒绝读取并提示升级——这是“工具链版本不一致”的常见故障源。
- 每个 `[[package]]` 条目通常包含 `name`、`version`、`source`、`checksum`、`dependencies`。

本项目里 MNN 的两个 crate 条目是这样的：[仓库已核实]

```toml
[[package]]
name = "mnn-rs"
version = "0.1.7"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "93b2fbaec153bcaa97ea963273fa8a1b25c733b9fdd492b67e6f055d807fc156"
dependencies = [
 "mnn-rs-sys",
 "thiserror 1.0.69",
]

[[package]]
name = "mnn-rs-sys"
version = "0.1.7"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "4b315ac53ccb2f12d84ec40e95c626549036e78356d2fdd8aef974b09a736a87"
dependencies = [
 "cc",
 "pkg-config",
]
```

三个信息值得记住：

1. `checksum` 是**内容哈希**。即使有人篡改了 registry 上的同名同版本包，Cargo 也会因为哈希不匹配而拒绝使用。这是供应链安全的第一道闸。
2. `mnn-rs-sys` 依赖 `cc`（C/C++ 编译驱动）和 `pkg-config`（查找系统库）。这两个依赖的存在，直接说明**这个 crate 会在构建期调用本机 C/C++ 工具链**——这正是第 13 章 `build.rs` 要展开的内容。
3. `source` 字段出现 `registry+...`，说明它来自 crates.io 镜像，而不是本地路径依赖。若你改成 `path = "../mnn-rs"`，这一行会变成没有 `source` 的本地条目。

#### 6.2.6 细节：为什么 20 行依赖会变成 533 个包

这是“传递依赖（transitive dependency）”的必然结果：

```
你直接依赖：tauri, serde, reqwest, rusqlite, mnn-rs ...   （约 20 个）
        │
        ├── tauri 依赖 wry、tao、http、tokio ...
        │        └── wry 依赖 webkit2gtk / ... 
        ├── reqwest 依赖 hyper、h2、rustls、ring ...
        └── mnn-rs 依赖 mnn-rs-sys → cc + pkg-config
                        │
                        ▼
              合计 533 个 package（去重后）
```

**类比**：你装修只买了 20 样主材，但每个主材都带着自己的配件清单，最后仓库里堆了 533 种物料。Cargo 的 lock 文件就是那张完整的仓库盘点表。

### 6.3 本项目真实案例

#### 6.3.1 一次真实的依赖树查询

```powershell
# 在 src-tauri 目录下执行；--tree 让输出呈树状，-e normal 只看普通依赖
cargo tree --target aarch64-linux-android -e normal -i mnn-rs
```

逐个参数解释：

| 参数 | 作用 | 不写会怎样 |
|---|---|---|
| `--target aarch64-linux-android` | 只解析**该目标**的依赖图 | 默认用宿主目标（`x86_64-pc-windows-msvc`），会漏掉 `[target.'cfg(target_os = "android")'.dependencies]` 里的 Android 专属依赖 |
| `-e normal` | 只显示普通依赖，排除 build-dependencies 与 dev-dependencies | 输出里会混入 `tauri-build`、测试框架，树更难读 |
| `-i mnn-rs` | 反向查询：谁依赖 `mnn-rs` | 正序树会从 `app` 开始展开几百行，看不到重点 |

预期你会看到 `app → mnn-rs → mnn-rs-sys`，并且能确认 `mnn-rs` 是否真的被启用。**如果树里完全没有 `mnn-rs`，说明 feature 没开**（第 7 章会解释原因）。

#### 6.3.2 `Cargo.lock` 的位置说明了什么

本项目 `Cargo.lock` 在 `src-tauri/` 下，而不是仓库根目录。[仓库已核实]

这传递了两个事实：

1. **Rust 侧的工作目录就是 `src-tauri/`**，Cargo 以它为一个独立的包根。
2. 仓库根目录的 `pnpm-lock.yaml` 管的是 JavaScript 依赖，和 Rust 依赖**互不相干**。两套锁文件、两套版本体系，这是 Tauri 项目的常态。

### 6.4 常见坑与判别方法

| 错误信息（原文或典型形态） | 原因 | 处理 |
|---|---|---|
| `error: failed to select a version for the requirement 'serde = "^1.0"'` | `Cargo.toml` 里的版本范围与已锁定版本冲突，或镜像索引不完整 | 先 `cargo update -p serde --precise 1.0.228`；仍失败则检查镜像是否同步 |
| `the lock file version 4 requires -Znext-lockfile-bump` / 提示 lock 版本不支持 | 你的 Cargo 太旧，读不了 `version = 4` | 升级 rustup 工具链；不要试图手改 lock 降级 |
| `error: package 'app' cannot be built because it requires rustc 1.88 or newer` | MSRV 不满足 | `rustup update stable`，或 `rustup override set 1.88` |
| `checksum for 'xxx' changed between lock files` | lock 被外部改动，或镜像返回了不同内容 | 删除该条目重新 `cargo update`；若反复出现，怀疑镜像缓存污染 |
| `no matching package named 'mnn-rs' found` | 没开 feature，或拼写/镜像问题 | 用 `cargo tree -i mnn-rs --features local-mnn` 确认 |

**判别思路**：先分清错误发生在“解析阶段”还是“编译阶段”。解析阶段的报错通常带 `failed to select a version`、`lock file` 字样，此时**根本还没开始编译 C++**，不要浪费时间查 NDK。

### 6.5 小结

1. `Cargo.toml` 写的是版本**范围**和构建**意图**；`Cargo.lock` 记的是精确版本与内容哈希，两者职责不重叠。
2. `Cargo.lock` 必须提交（应用项目），因为它保证你、队友、CI 装到同一批依赖。
3. `crate-type` 决定产物形态：`staticlib` 给原生链接器，`cdylib` 给动态加载，`rlib` 给 Rust 内部复用。
4. `rust-version` 是被依赖“顶”上去的，不是随手写的；它是排查 CI 环境问题的第一条线索。
5. 533 个 package 是传递依赖正常膨胀的结果，不是依赖污染。

### 6.6 练习题

**第 1 题**：把 `src-tauri/Cargo.toml` 里 `[lib] crate-type` 改成只有 `["rlib"]`，然后跑 `cargo build --target aarch64-linux-android`。预测会发生什么，为什么？

> 参考答案要点：Android 打包链需要 `libapp_lib.so`（`cdylib`）或静态库形态；只留 `rlib` 时，Gradle/jniLibs 阶段找不到 `.so`，即使 Rust 编译成功，APK 也会缺库。`rlib` 只是给 rustc 用的中间产物，不是可部署产物。

**第 2 题**：`Cargo.lock` 里的 `checksum` 校验发生在什么阶段？如果把某个包的 `checksum` 手改成 `"0"`，运行 `cargo build` 会得到什么？

> 参考答案要点：校验发生在下载/解包阶段，早于编译。手改后 Cargo 会报校验和不匹配并拒绝使用该包；`cargo build` 不会“带病编译”。这也说明 lock 文件是安全边界的一部分。

**第 3 题**：用 `cargo tree` 找出本项目里 `cc` 这个 crate 是被谁引入的，并解释它为什么只在 Android/原生构建时可以缺席于桌面运行。

> 参考答案要点：`cc` 由 `mnn-rs-sys` 的构建依赖引入，只在**构建期**运行，用于驱动 C/C++ 编译器；它不会出现在最终二进制里。桌面默认构建不开 `local-mnn`，因此整条 `mnn-rs-sys` 链都不参与，`cc` 也不会被编译。

## 第 7 章 feature、optional 依赖与 `dep:`

### 7.1 本章要解决什么问题

上一章留下的悬念：为什么默认 `cargo build` 不需要 NDK，而一旦打开某个开关就必须有 NDK？为什么 `mnn-rs` 明明写在 `[dependencies]` 里，`cargo tree` 却看不到它？

答案在 Cargo 的 **feature** 机制。它是本项目“一套代码，两条构建路径”的总开关。

### 7.2 概念：从直觉到机制

#### 7.2.1 直觉：feature 是“出厂配置单”，不是“运行时开关”

买车时你会选装天窗、选装四驱。**选装发生在出厂前**，出厂后车上有没有天窗是固定的。Cargo 的 feature 就是这样：

- 它在**编译前**决定哪些代码参与编译、哪些依赖被拉进来；
- 一旦编译完成，产物里要么有这段能力，要么完全没有；
- 它不是 `if (config.enableMnn)` 那种运行时判断，**不会**留下“功能关闭但仍占体积”的分支。

**类比**：feature 像装修时决定“这面墙要不要开窗”。开窗是施工阶段的事，住进去以后不能靠按按钮把窗变出来。

#### 7.2.2 机制：feature 如何影响依赖图

```
                 [features]
        local-mnn = ["dep:mnn-rs"]
                        │
                        │ 只有这个 feature 被启用时
                        ▼
              mnn-rs（optional = true）
                        │
                        ▼
              mnn-rs-sys
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
   build.rs 需要 C++ 工具链     链接阶段需要 libmnn.a
          │                           │
          ▼                           ▼
      NDK / clang                 -lmnn 搜索路径
```

这条链是单向的：**feature → 依赖 → 工具链 → 产物**。你看到的每一个“为什么必须装 NDK”的抱怨，源头都在最左边那一格。

#### 7.2.3 细节：本项目的两行关键配置

```toml
[features]
local-mnn = ["dep:mnn-rs"]
```

```toml
mnn-rs = { version = "0.1.7", optional = true, default-features = false, features = ["cpu", "static", "llm"] }
```

[仓库已核实：`src-tauri/Cargo.toml` 第 16–19 行、第 58–59 行]

逐项拆解：

| 写法 | 含义 | 类比 |
|---|---|---|
| `optional = true` | 这个依赖默认**不参与**构建；只有被 feature 激活时才加入依赖图 | 仓库里备着但不上流水线的零件 |
| `local-mnn = ["dep:mnn-rs"]` | 定义一个名为 `local-mnn` 的 feature，启用它等价于启用 `mnn-rs` 这个可选依赖 | 按下“启用 MNN 产线”的总闸 |
| `dep:mnn-rs` | 冒号前缀表示“**直接启用这个依赖**，不要顺带创建一个同名隐式 feature” | 直接点名零件，而不是新建一个同名标签 |
| `default-features = false` | 关闭 `mnn-rs` 自己的默认 feature 集合 | 不买“标配套餐”，只勾选需要的项目 |
| `features = ["cpu", "static", "llm"]` | 只开启 CPU 后端、静态链接、LLM 接口三项 | 只买这三个配件 |

**`dep:` 的意义需要单独说清楚。** 在旧写法里，`local-mnn = ["mnn-rs"]` 会出现一个问题：Cargo 会为每个 optional 依赖自动生成一个**同名隐式 feature**，于是“依赖名”和“feature 名”混在一起，用户执行 `--features mnn-rs` 也能打开它，语义混乱。`dep:` 语法（Rust 1.60 起稳定）明确区分两者：**要开依赖就写 `dep:名字`，要开 feature 就写 `名字`**。

#### 7.2.4 细节：`mnn-rs` 的 feature 表

`mnn-rs 0.1.7` 自己的默认 feature 是 `["cpu", "static", "use-prebuilt"]`。[仓库已核实：crate 源码 `Cargo.toml`]

| feature | 作用 | 本项目是否开启 | 说明 |
|---|---|---|---|
| `cpu` | 启用 CPU 后端绑定 | 是 | 手机端没有 NVIDIA GPU，CPU 是唯一稳妥选择 |
| `static` | 以静态库方式链接 MNN | 是 | 产物自带引擎，不依赖运行时的 `.so` |
| `llm` | 暴露 `MNN::Transformer::Llm` 的绑定 | 是 | 没有它就没有 `Llm` 类型，只能跑普通模型 |
| `use-prebuilt` | 构建时下载官方预编译库 | **否**（被 `default-features = false` 关掉） | 关键：我们要用自己交叉编译的 `libMNN.a` |
| `build-from-source` | 让 `mnn-rs-sys` 自己调 CMake 编译 MNN | 否 | 我们选择**手工**编译 + `MNN_LIB_DIR` 指向产物，控制力更强 |
| `system-mnn` | 用 `pkg-config` 找系统已安装的 MNN | 否 | Android 上没有系统级 MNN |
| `dynamic` | 以动态库方式链接 | 否 | 与 `static` 互斥方向 |
| `android` | Android 平台相关适配 | 未在项目显式开启（由目标平台与 sys 构建脚本处理） | 以实际构建日志为准 |
| `fp16` / `int8` | 启用半精度/整型加速相关后端 | 否 | 与量化格式不是同一件事，见第 21 章 |

> 表中 `android` 一行特别标注：项目没有写这个 feature，但 `mnn-rs-sys` 的构建脚本会依据 `CARGO_CFG_TARGET_OS == "android"` 走 Android 分支。**feature 与“目标平台判断”是两套机制**，不要混为一谈。

**为什么必须关掉 `use-prebuilt`？** 因为预编译库是官方按它自己的工具链和 ABI 参数构建的。你的项目可能需要 `android-24`、需要特定 STL 设置、需要打 CMake 补丁。用预编译库等于放弃了这些控制点，也无法解释“为什么我的符号在库里找不到”。关掉它，`mnn-rs-sys` 就只剩两条路：`MNN_LIB_DIR` 指向你给的库，或自己 `build-from-source`。

### 7.3 本项目真实案例

#### 7.3.1 开启与不开启的对比

```powershell
# 桌面开发循环：不启用 local-mnn
cargo build

# 启用 MNN：需要 MNN_LIB_DIR / MNN_INCLUDE_DIR 已指向 staging 目录
$env:MNN_LIB_DIR = "D:\mnn-stage\lib"
$env:MNN_INCLUDE_DIR = "D:\mnn-stage\include"
cargo build --features local-mnn --example mnn_smoke
```

参数解释：

| 片段 | 作用 |
|---|---|
| `--features local-mnn` | 打开项目的 feature，从而激活 `dep:mnn-rs` |
| `--example mnn_smoke` | 只构建这个 example，而不是整个库和主二进制 |
| `$env:MNN_LIB_DIR` | PowerShell 设置环境变量，供 `mnn-rs-sys` 的 `build.rs` 读取 |

**顺序很重要**：环境变量必须在**同一个 PowerShell 会话里、且在 `cargo` 之前**设置。用一个新开的窗口执行 `cargo`，变量就丢了。

#### 7.3.2 feature 在代码里怎么落地

`src/agent/local_mnn/mod.rs` 顶部有这样的条件编译：[仓库已核实]

```rust
#[cfg(feature = "local-mnn")]
pub mod worker;
```

以及同一文件里成对出现的两套 `load` / `generate` / `unload` 实现：打开 feature 时走真实 worker，关闭时返回“不可用”。[仓库已核实：`mod.rs` 中的双实现分支，约第 173–176 行]

这意味着：

- **桌面默认构建**：`worker` 模块根本不参与编译，`mnn-rs` 也不在依赖图里，代码里对 `Llm` 的所有引用都被 `#[cfg]` 抹掉。
- **Android/实验构建**：`worker` 参与编译，`Llm` 类型存在，链接器需要 `libmnn.a`。

**一个必须记住的推论**：如果你在不开 feature 的情况下写了引用 `worker::...` 的代码，编译器会报“找不到模块”，而**不是**“找不到符号”。这两种错误分别属于编译期和链接期，排查方向完全不同。

#### 7.3.3 feature 是“加法”，不能做减法

Cargo 的 feature 是**可加的（additive）**：依赖图里只要有任何一个包打开了某个 feature，这个 feature 对所有使用者都生效。它**没有**“关闭某个依赖的某个 feature”的语法（`default-features = false` 只能关默认集合，不能关别人显式打开的）。

实际后果：

- 如果某个底层 crate 的 `std` feature 被别的依赖打开了，你无法在自己的包里把它关掉；
- 所以 feature 的命名应当表达“**增加能力**”（`llm`、`fp16`），而不是“移除能力”（`no-std` 这种命名要特别小心）。

这条规则解释了一个常见困惑：**为什么我明明没开某个 feature，`cargo tree -f` 里却是 enabled？** 因为别人替你开了。

### 7.4 常见坑与判别方法

| 错误 / 现象 | 原因 | 处理 |
|---|---|---|
| `error: failed to run custom build command for 'mnn-rs-sys'`，日志里出现 `MNN_LIB_DIR` 未设置 | 关了 `use-prebuilt`，又没提供库路径 | 设置 `MNN_LIB_DIR` 与 `MNN_INCLUDE_DIR`，或改用 `build-from-source` |
| `unresolved import 'mnn_rs'` / `no external crate 'mnn_rs'` | 没开 feature，可选依赖未进入依赖图 | 加 `--features local-mnn`；检查拼写是 `mnn_rs`（下划线）还是 `mnn-rs`（连字符） |
| `cargo build` 突然开始编译 MNN，耗时暴涨 | 某个上层 feature 被默认打开，或 `default-features` 忘了关 | 看 `cargo tree -e features`，确认 `mnn-rs` 是 `feature "local-mnn"` 引入的，而非默认 |
| `--features` 写了但完全不生效 | 用了 `--features local-mnn` 却构建另一个 package（在 workspace 下常见） | 在正确的包目录执行，或用 `--package` 指定 |
| 同一 crate 出现两份不同 feature 组合 | 依赖图里同一 crate 的两个版本共存 | 用 `cargo tree -d` 找重复版本，统一版本 |

**判别口诀**：`可选依赖没出现` → 查 feature；`出现了但编译失败` → 查 `build.rs` 与环境变量；`编译过了但链接失败` → 查第 23–25 章的符号与搜索路径。

### 7.5 小结

1. feature 是**编译期**开关，决定代码与依赖是否参与构建，不是运行时配置。
2. `optional = true` + `dep:名字` 是“按需拉入重型依赖”的标准写法，`dep:` 避免了隐式同名 feature 的歧义。
3. `default-features = false` 关掉的是**默认集合**，本项目借此摆脱官方预编译库，改用自建 `libMNN.a`。
4. `cpu`/`static`/`llm` 三个 feature 分别对应后端、链接方式、API 面，缺一个都会在后续阶段以不同错误暴露。
5. feature 是可加的，无法“减法关闭”；排查异常开启时用 `cargo tree -e features`。

### 7.6 练习题

**第 1 题**：把 `local-mnn = ["dep:mnn-rs"]` 改成 `local-mnn = ["mnn-rs"]`，仓库能否编译？行为有何差别？

> 参考答案要点：仍能编译，但会额外生成一个隐式 feature `mnn-rs`，使用户可以直接 `--features mnn-rs` 打开依赖，语义边界变模糊。现代写法优先 `dep:`。

**第 2 题**：为什么 `default-features = false` 在本项目里是**必需**，而不是“优化项”？

> 参考答案要点：默认含 `use-prebuilt`，会让 `build.rs` 去下载官方预编译库，覆盖/绕过我们手工交叉编译的 `libMNN.a`；同时预编译库的 ABI、API level、STL 设置无法对齐本项目要求。

**第 3 题**：不开 `local-mnn` 时，`src/agent/local_mnn/mod.rs` 里引用 `mnn_rs::...` 的代码会怎样？请描述编译器的具体行为，并说明它与“链接期找不到符号”的区别。

> 参考答案要点：这些代码被 `#[cfg(feature = "local-mnn")]` 排除，根本不进入编译单元；若你误把 `use mnn_rs::...` 写在未加 `#[cfg]` 的位置，会得到 `E0432 unresolved import`（编译期）。链接期错误则是编译已成功、只是找不到 `MNN::...` 符号，对应 `undefined reference`（第 25 章）。

## 第 8 章 `[[example]]` 与 `required-features`

### 8.1 本章要解决什么问题

`src-tauri/examples/mnn_smoke.rs` 是一个可以独立运行的程序：给它模型目录、提示词、token 数、线程数，它就在终端里打印推理结果。但它**不在** `src/bin/` 下，也不是主程序的一部分。为什么不放在 `src/bin/`？为什么平时 `cargo build` 不会编译它？

本章回答“example 是什么、什么时候编译、如何只构建它”。

### 8.2 概念：从直觉到机制

#### 8.2.1 直觉：example 是“随书附赠的演示程序”

**定义**：example 是 Cargo 约定的一种额外二进制目标，源码放在 `examples/` 目录，用 `cargo run --example <名字>` 运行。它和 `src/bin/` 的区别在于**定位**：

- `src/bin/` 里的程序是“产品的一部分”，通常随包一起安装；
- `examples/` 里的程序是“说明书配图”，用于演示 API 用法，默认不随发布分发。

**类比**：`src/bin/` 是店里卖的成品家具；`examples/` 是展厅里的样品，能坐能看，但不进销售清单。

#### 8.2.2 机制：example 的编译时机

```
cargo build                  → 编译 lib + 主 bin；example 默认【不】编译
cargo build --examples       → 编译所有 example
cargo build --example foo    → 只编译 foo 这一个
cargo test                   → 会编译 example（确保它们没坏）
cargo run --example foo      → 编译并运行 foo
```

> 注意最后一行与 `cargo test`：不同 Cargo 版本对 example 在测试时的处理细节有差异，但“`cargo test` 会构建 example 作为编译检查”是长期行为。[通用原理]

#### 8.2.3 细节：`[[example]]` 段在做什么

```toml
[[example]]
name = "mnn_smoke"
path = "examples/mnn_smoke.rs"
required-features = ["local-mnn"]
```

[仓库已核实]

| 键 | 作用 | 省略会怎样 |
|---|---|---|
| `name` | 目标名，决定 `--example mnn_smoke` 的写法与产物名 | 默认取文件名 `mnn_smoke`，此处是显式声明 |
| `path` | 源文件路径 | 默认 `examples/mnn_smoke.rs`，显式写更清楚 |
| `required-features` | **只有这些 feature 全部启用时，该目标才参与构建** | 省略则任何构建配置下都会尝试编译它，从而在无 NDK 的环境里直接失败 |

`required-features` 是本章的核心。它的语义是“**前置条件**”，不是“提示”：

- 条件不满足时，Cargo **跳过**这个目标，**不报错**；
- 条件满足时才编译；若此时编译/链接失败，才是真错误。

这解释了日常体验：桌面 `cargo build` 一切正常，`mnn_smoke` 仿佛不存在；一旦 `--features local-mnn`，它才“出现”，并立刻要求 `libMNN.a`。

#### 8.2.4 细节：为什么用 example 而不是 `src/bin/`

| 方案 | 优点 | 缺点 | 本项目为何不选/选 |
|---|---|---|---|
| 放 `src/bin/mnn_smoke.rs` | `cargo run --bin` 直达 | 会成为包的正式二进制目标，Android 打包时可能被误纳入；且无法用 `required-features` 精细隔离（`[[bin]]` 也支持，但语义上它是产品） | 不选 |
| 放 `examples/mnn_smoke.rs` | 语义清晰：演示/验证工具；天然与 `required-features` 配合 | 需要多打几个参数 | **选它** |
| 单独建一个 crate | 隔离最彻底 | 增加目录与依赖管理成本；本项目只需一个验证程序 | 不选 |

**关键判断**：`mnn_smoke` 的职责是“验证 Rust → MNN → 真机这条链路”，它不是产品功能。把它放 examples 既表达了职责，又避免污染发布产物。

#### 8.2.5 细节：example 如何复用库代码

`examples/` 下的 crate 会自动把**同包的 lib target** 作为依赖。本项目 `[lib] name = "app_lib"`，所以 example 里可以写：

```rust
use app_lib::...;   // 前提是 lib 里 pub 了对应模块
```

但对 `mnn_smoke` 而言，它主要直接使用 `mnn_rs`，并没有大量复用 `app_lib` 的内部模块。这是有意的：**验证程序应尽量少依赖被测系统之外的代码**，否则“到底是引擎坏了还是我的业务封装坏了”会混在一起。

### 8.3 本项目真实案例

#### 8.3.1 `mnn_smoke` 的参数与输出

```powershell
cargo run --release --features local-mnn --example mnn_smoke -- `
  "D:\models\Qwen3-0.6B-MNN" "你好，请用一句话介绍你自己" 64 4
```

参数解释：

| 片段 | 作用 |
|---|---|
| `--release` | 用优化构建；debug 构建的推理速度会差一个量级，测速必须在 release 下做 |
| `--features local-mnn` | 满足 `required-features` |
| `--example mnn_smoke` | 选中目标 |
| `--`（单独两个短横） | **分隔符**：它左边的参数给 cargo，右边的参数给 mnn_smoke 自己 |
| `"D:\models\..."` | 模型 bundle 目录（含 `config.json`） |
| `"你好..."` | prompt |
| `64` | 最大生成 token 数 |
| `4` | 线程数 |

忘记 `--` 是高频错误：cargo 会把 `D:\models\...` 当成自己的未知参数，直接报 `error: unexpected argument`。

`mnn_smoke` 会打印两类信息：[仓库已核实：`examples/mnn_smoke.rs`]

- 流式文本本身（边生成边打印）；
- 一行汇总：`summary load_ms=... chunks=... first_chunk_ms=... total_ms=...`；
- 以及 `performance()` 的细项：`prompt_tokens / output_tokens / prefill_ms / decode_ms / sample_ms / load_us / decode_tok_s`。

这些字段的**口径**很重要，第 18 章会逐个解释。这里只需记住：**`load_ms` 与 `prefill_ms` 是两件事**，前者是加载模型，后者是处理 prompt。

#### 8.3.2 交叉编译时的 example 路径

给 Android 编译时，`cargo build --target aarch64-linux-android` 的 example 产物在：

```
src-tauri/target/aarch64-linux-android/release/examples/mnn_smoke
```

注意：**没有 `.exe` 后缀**，因为目标不是 Windows。这个无后缀文件就是后面要 `adb push` 的那个 ARM64 可执行文件。[通用原理]

### 8.4 常见坑与判别方法

| 错误 / 现象 | 原因 | 处理 |
|---|---|---|
| `error: unexpected argument 'D:\models\...' found` | 忘了 `--` 分隔符 | 在 example 名后加 `--` |
| `error: target 'mnn_smoke' requires the features: local-mnn`（不同 Cargo 版本措辞略有差异） | 没满足 `required-features`，但你**显式**点名了该目标 | 加 `--features local-mnn` |
| `cargo build` 静默不产出 example | 默认不编译 example，且 `required-features` 未满足 | 用 `--example` 明确点名 |
| `error[E0463]: can't find crate for 'std'` | 没装目标平台的标准库 | `rustup target add aarch64-linux-android`（第 10 章） |
| example 能编译但链接报 `undefined reference to MNN::...` | 库路径/符号问题，不是 example 语法问题 | 转第 24–25 章 |

### 8.5 小结

1. example 是“演示/验证”目标，默认不参与 `cargo build`，也不随包分发。
2. `required-features` 是硬门槛：不满足就跳过，满足才编译；它让重型依赖只在需要时进入构建。
3. `--` 是 cargo 与程序参数的分界线，交叉编译与本地运行都需要它。
4. example 产物文件名不带平台后缀，这与 Windows 目标的 `.exe` 习惯不同。
5. 测性能必须 `--release`，debug 下的数字没有比较意义。

### 8.6 练习题

**第 1 题**：如果把 `required-features` 删掉，在没装 NDK 的 Windows 机器上执行 `cargo build` 会发生什么？为什么？

> 参考答案要点：Cargo 会尝试编译 `mnn_smoke`，进而编译 `mnn-rs-sys` 的构建脚本；由于缺少 NDK/C++ 工具链或 `MNN_LIB_DIR`，构建在 `build.rs` 阶段失败，导致整个 `cargo build` 失败。`required-features` 的价值正是“不该编译的时候绝不碰它”。

**第 2 题**：为什么 `mnn_smoke` 输出里要同时给 `load_ms` 和 `prefill_ms`？只报一个总时间会掩盖什么？

> 参考答案要点：加载是读权重+建后端，prefill 是计算 prompt；两者优化手段完全不同（减少量化/减少线程 vs 调整批处理/KV 布局）。合并成一个数字，无法判断瓶颈在 I/O 还是计算。

**第 3 题**：在 Android 目标上构建 example，产物在哪个目录？为什么不能用 `Get-ChildItem target -Recurse -Filter *.exe` 找它？

> 参考答案要点：在 `target/aarch64-linux-android/<profile>/examples/`；Linux/Android 的可执行文件没有 `.exe` 扩展名，用 `.exe` 过滤会一无所获。应改用 `mnn_smoke` 精确名或 `Get-ChildItem -Filter mnn_smoke`。

## 第 9 章 workspace 与锁文件边界

### 9.1 本章要解决什么问题

你在网上看到大量 Cargo 配置写着 `[workspace] members = [...]`、`workspace = true`。打开本项目却发现 `src-tauri/Cargo.toml` 里**没有** `[workspace]`。那它到底是不是 workspace？根目录的 `pnpm-workspace.yaml` 又是什么？

本章要让你能分清三类“workspace”：

1. **Cargo workspace**：Rust 的包集合；
2. **pnpm workspace**：JavaScript 的包集合；
3. **Tauri 的“项目”**：前端 + `src-tauri` 的组合，只是目录约定，不是构建系统概念。

### 9.2 概念：从直觉到机制

#### 9.2.1 直觉：workspace 是“共享一个仓库的多个摊位”

**定义**：Cargo workspace 是多个 package 的集合，它们共享一个 `Cargo.lock`、一个 `target/` 目录，并可以共享依赖版本声明。

**类比**：一个商场里有很多摊位（package），但整个商场只有一个总仓库（`target/`）和一本总账（`Cargo.lock`）。摊位之间可以互相供货，也可以统一采购。

#### 9.2.2 机制：workspace 的三个可观察特征

| 特征 | 独立包（本项目） | workspace |
|---|---|---|
| `Cargo.lock` 位置 | 包目录下（`src-tauri/Cargo.lock`） | workspace 根目录下，所有成员共享 |
| `target/` 位置 | 包目录下（`src-tauri/target/`） | workspace 根目录下 |
| 依赖版本 | 各自声明 | 可用 `[workspace.dependencies]` 集中声明，成员用 `workspace = true` 引用 |

本项目全部落在左列。[仓库已核实：`src-tauri/Cargo.lock` 存在，仓库根无 `Cargo.toml`]

#### 9.2.3 细节：workspace 的典型写法（对照用，本项目未使用）

```toml
# 假设的 workspace 根 Cargo.toml（本项目没有这个文件）
[workspace]
members = ["src-tauri", "crates/mnn-bridge"]
resolver = "2"

[workspace.dependencies]
serde = { version = "1.0", features = ["derive"] }
```

成员包则写：

```toml
[dependencies]
serde = { workspace = true }
```

**`workspace = true` 的含义**：不要把版本写在这里，去根 `[workspace.dependencies]` 查。好处是“一处改版本，全仓生效”；代价是“看单个包的 `Cargo.toml` 不知道实际版本”。

**`resolver` 是什么**：依赖解析策略。`resolver = "2"` 主要改变 feature 合并规则（例如 build-dependencies 与普通依赖的 feature 不再互相污染）以及目标平台条件的处理。edition 2021 的包默认 `resolver = "2"`，workspace 根则需要显式声明。[通用原理]

#### 9.2.4 细节：`pnpm-workspace.yaml` 不是 Rust 的 workspace

本项目根目录有 `pnpm-workspace.yaml`，内容只有构建脚本许可配置：[仓库已核实]

```yaml
allowBuilds:
  '@google/genai': false
  protobufjs: false
```

它属于 **pnpm**（JavaScript 包管理器），语义是“允许/禁止哪些依赖在安装时执行构建脚本”。它与 Cargo 完全无关，也不会影响 `cargo build`。

**为什么容易混**：两者都叫 workspace，都在仓库根，都管依赖。但一个管 `node_modules`，一个管 `target/`。

#### 9.2.5 细节：为什么本项目“不该”用 Cargo workspace

| 考量 | 说明 |
|---|---|
| 只有一个 Rust 包 | workspace 的核心价值是“多包共享”，单包没有收益 |
| Tauri 约定 | `src-tauri` 作为独立包根，是 Tauri CLI 的默认假设；改成 workspace 需要调整路径与 CLI 行为 |
| 前端/Rust 分离 | 前端由 pnpm 管，Rust 由 Cargo 管，强行合并成 workspace 不会让两者更一致 |

**反过来说**：如果你要新增一个 `crates/mnn-bridge` 来封装 FFI，workspace 就值得引入了——因为那时你有了两个 Rust 包，需要共享锁文件与构建产物目录。

### 9.3 本项目真实案例

#### 9.3.1 确认“不是 workspace”的三条命令

```powershell
# 1) 仓库根是否有 Cargo.toml？没有则不是 workspace 根
Test-Path .\Cargo.toml

# 2) 当前包的 workspace 归属；独立包通常显示包自身路径
cargo metadata --no-deps --format-version 1 |
  ConvertFrom-Json |
  Select-Object -ExpandProperty workspace_root

# 3) 锁文件位置是否与包目录一致
Get-ChildItem .\src-tauri\Cargo.lock
```

参数解释：

| 片段 | 作用 |
|---|---|
| `--no-deps` | 只解析当前包，不展开全部依赖；输出小、快，适合确认归属 |
| `--format-version 1` | 指定 JSON 结构版本，便于 `ConvertFrom-Json` 稳定解析 |
| `ConvertFrom-Json` | PowerShell 把 JSON 转成对象 |
| `Select-Object -ExpandProperty workspace_root` | 直接取出字段值，而不是打印对象 |

预期：`workspace_root` 指向 `src-tauri` 自身目录（或与包目录一致），说明它就是独立包根。

#### 9.3.2 锁文件边界的实际影响

因为不是 workspace：

- 你在 `src-tauri/` 执行 `cargo`，读写的是 `src-tauri/Cargo.lock`；
- 根目录的 `pnpm-lock.yaml` 变化**不会**触发 Rust 重编译；
- 在根目录执行 `cargo build` 会失败（没有 `Cargo.toml`），必须 `cd src-tauri` 或用 `--manifest-path`。

最后一条最容易踩：

```powershell
# 从仓库根执行，显式指定 manifest
cargo build --manifest-path .\src-tauri\Cargo.toml --features local-mnn
```

`--manifest-path` 让 Cargo 在任意工作目录下找到包根，避免 `cd` 来回切换。

### 9.4 常见坑与判别方法

| 错误 / 现象 | 原因 | 处理 |
|---|---|---|
| `error: could not find 'Cargo.toml' in ... or any parent directory` | 在仓库根执行 cargo | `cd src-tauri` 或用 `--manifest-path` |
| `error: multiple workspace roots found` | 子目录里有人加了 `[workspace]`，与上层冲突 | 删掉多余的 workspace 声明，或加 `[workspace]` 到根统一 |
| `cargo build` 产物出现在意料之外的 `target/` | 当前包属于某个 workspace，产物在 workspace 根 | `cargo metadata` 查 `target_directory` |
| 改了根 `pnpm-workspace.yaml` 后 Rust 重新全量编译 | 误解为 Rust 配置 | 理论上不会发生；若发生，检查是否误改了 `Cargo.toml` 或触碰了 `build.rs` 监听的文件 |
| `workspace.dependencies` 里的版本“看不见” | 成员用 `workspace = true` | `cargo tree` 才是实际版本的真实来源 |

### 9.5 小结

1. Cargo workspace 是“多包共享一个锁文件和 target 目录”的机制；本项目是单包，因此没有 workspace。
2. `pnpm-workspace.yaml` 属于 JavaScript 生态，和 Cargo 无关。
3. 锁文件的位置直接告诉你构建边界：在 `src-tauri/` 就是独立包。
4. 单包项目不必为了“看起来规范”引入 workspace；等到真的出现第二个 Rust 包再引入。
5. 用 `cargo metadata` 的 `workspace_root` / `target_directory` 两个字段，可以一锤定音判断归属。

### 9.6 练习题

**第 1 题**：如果在仓库根新建一个 `Cargo.toml` 并写入 `[workspace] members = ["src-tauri"]`，会发生哪些可观察变化？至少列出三处。

> 参考答案要点：`Cargo.lock` 会被移动到或生成于根目录；`target/` 变为根目录下共享；`src-tauri/Cargo.lock` 会失效/被忽略；`cargo build` 可在根目录执行；Tauri CLI 的部分路径假设可能受影响。

**第 2 题**：为什么 `resolver = "2"` 对“同时有 build-dependencies 和普通依赖”的项目尤其重要？

## 第 10 章 目标三元组与交叉编译

### 10.1 本章要解决什么问题

你在一台 Windows x86_64 机器上，要产出能在 ARM64 手机上运行的文件。CPU 指令集不同、操作系统不同、系统库不同、可执行文件格式不同。**这不是“换个编译选项”，而是换一整套工具链。**

本章要让你能：

- 读懂 `aarch64-linux-android` 每一段的含义；
- 说清 `rustup target add` 到底装了什么；
- 知道链接器、C 编译器、CMake 工具链文件这三者分别由谁提供；
- 看懂本项目 Android 构建实际依赖的那几个环境变量的必要性。

### 10.2 概念：从直觉到机制

#### 10.2.1 直觉：给谁做饭，就要用谁的厨房

**定义**：目标三元组（target triple）是一个字符串，描述“产物的运行环境”。它至少包含三件事：CPU 架构、操作系统、运行时/ABI 环境。

**类比**：你要给一位住在“上海、用 220V 电压、说中文”的客户寄一台电器。地址、电压、语言三项写错任何一项，东西到了也用不了。三元组就是这三项的组合写法。

#### 10.2.2 机制：`aarch64-linux-android` 拆开看

| 段 | 值 | 含义 | 写错会怎样 |
|---|---|---|---|
| 架构 | `aarch64` | 64 位 ARM，即 ARMv8-A 的 AArch64 执行状态 | 写成 `armv7` 会产出 32 位库，装到 64 位手机上直接 ABI 不匹配 |
| 平台/内核 | `linux` | 使用 Linux 内核（Android 内核基于 Linux） | 写成 `none` 会进入裸机/嵌入式配置，没有 libc |
| 运行环境 | `android` | Android 的 libc（bionic）、动态链接器、以及 NDK 提供的 ABI 约定 | 写成 `gnu` 会链接 glibc，Android 上找不到对应符号 |

**注意**：API level（如 `android-24`）**不在三元组里**。它由 NDK/CMake 的 `ANDROID_PLATFORM` 与 clang 的 `--target=aarch64-linux-android24` 参数表达。这是一个高频混淆点：三元组说“这是 Android”，API level 说“最低支持哪个 Android 版本”。

#### 10.2.3 细节：`rustup target add` 装了什么

```powershell
rustup target add aarch64-linux-android
```

它下载的是**该目标的预编译标准库**（`std`、`core`、`alloc` 等的 `.rlib`），放到：

```
%USERPROFILE%\.rustup\toolchains\stable-x86_64-pc-windows-msvc\lib\rustlib\aarch64-linux-android\lib\
```

**它不装链接器，也不装 C 编译器。** 这是最关键的一句：`rustup target add` 只解决“Rust 标准库从哪来”，不解决“谁来把 `.o` 变成可执行文件”。

为什么需要目标平台的标准库？因为 `std` 里包含平台相关的实现：文件系统调用、线程创建、动态库加载。这些代码必须为目标平台编译。你无法用 Windows 的 `std` 去链接 Android 程序。

#### 10.2.4 细节：三类工具的职责划分

```
┌──────────────────────────────────────────────────────────────┐
│ rustc（宿主 x86_64）                                         │
│  ├── 读 Rust 源码 → 生成 LLVM IR → 生成 aarch64 目标文件      │
│  └── 调用【链接器】把目标文件 + Rust 标准库 + 原生库 合成产物  │
├──────────────────────────────────────────────────────────────┤
│ 链接器：NDK 的 aarch64-linux-android<API>-clang               │
│  └── 内部驱动 lld，处理 ELF、动态库依赖、符号解析              │
├──────────────────────────────────────────────────────────────┤
│ C/C++ 编译器：同一套 NDK clang                               │
│  └── 编译 MNN 的 .cpp（mnn-rs-sys 的 build.rs 或手工 CMake）  │
├──────────────────────────────────────────────────────────────┤
│ CMake + Ninja：生成并执行构建规则                              │
│  └── 需要 android.toolchain.cmake 才知道“为 Android 编译”      │
└──────────────────────────────────────────────────────────────┘
```

四层里，**rustup 只提供第一层里的 Rust 标准库**；其余全部来自 NDK 与手工安装的 CMake/Ninja。

#### 10.2.5 细节：告诉 Cargo 用哪个链接器

Cargo 不会自动知道 NDK 在哪。两种等价写法：

**写法 A：环境变量**

```powershell
$env:CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER = "$NdkRoot\toolchains\llvm\prebuilt\windows-x86_64\bin\aarch64-linux-android24-clang.cmd"
```

变量名规则：`CARGO_TARGET_<三元组大写并把 - 换成 _>_LINKER`。逐段解释：

| 片段 | 含义 |
|---|---|
| `CARGO_TARGET_` | 固定前缀 |
| `AARCH64_LINUX_ANDROID` | 目标三元组大写，连字符换成下划线 |
| `_LINKER` | 固定后缀，值必须是可执行文件绝对路径 |
| `...-clang.cmd` | Windows 上的批处理包装；Linux/macOS 上通常是无后缀的 `...-clang` |

**写法 B：`.cargo/config.toml`**

```toml
[target.aarch64-linux-android]
linker = "C:/Android/Sdk/ndk/28.2.13676358/toolchains/llvm/prebuilt/windows-x86_64/bin/aarch64-linux-android24-clang.cmd"
```

**取舍**：环境变量适合脚本临时切换 NDK 版本；`config.toml` 适合团队固化配置，但要注意**里面是绝对路径**，换机器就失效。本项目选择脚本注入环境变量（见下节），理由是 NDK 路径因机器而异，不该写进仓库。

#### 10.2.6 细节：为什么还要设置 `CC_aarch64_linux_android`

`cc` crate（`mnn-rs-sys` 的构建依赖）在编译 C/C++ 时，需要知道用哪个编译器。它的约定变量名是：

```
CC_<target>      例如 CC_aarch64_linux_android
CXX_<target>     例如 CXX_aarch64_linux_android
```

`cc` 会优先读这些变量；没有时才回退到宿主默认编译器（那会编出 x86_64 目标文件，链接时立刻失败）。**注意适用范围**：这只对使用 `cc` crate 的依赖成立；本项目 llama.cpp 与 MNN 都通过 CMake 构建，所以第 32 章 E 组实验不设 `CC`/`CXX`/`AR`/linker 也能成功 `[已验证]`。

**判别技巧**：如果链接阶段报 `file format not recognized` 或 `incompatible target`，八成是 C/C++ 部分被宿主编译器编了。此时查 `CC_aarch64_linux_android` 是否生效。

### 10.3 本项目真实案例

#### 10.3.1 本项目真实依赖的构建变量

Android 构建不再使用包装脚本：`pnpm android:build` / `pnpm android:build:local` 直接执行 `tauri android build --target aarch64 --features local-llm`。[仓库已核实]

| 变量 | 值/来源 | 作用 |
|---|---|---|
| `ANDROID_NDK` | `src-tauri/.cargo/config.toml`，本机指向 `ndk/28.2.13676358` | NDK 探测链的第一位；`llama-cpp-sys-2` 优先读它（第 32 章 A 组 `[已验证]`）。它不读 `NDK_HOME`，所以只设 `NDK_HOME` 会退回到“扫描 SDK 取版本号最大者” |
| `CMAKE_GENERATOR_aarch64_linux_android` | `Ninja`（同一份 `src-tauri/.cargo/config.toml`） | 让 CMake 用 Ninja 而不是 Visual Studio 生成器；按目标限定，桌面构建不受影响 |
| `CC_aarch64_linux_android` / `CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER` | 不需要 | 第 32 章 E 组显示，llama.cpp 与 MNN 都走 CMake，不设这些变量也能成功 `[已验证]` |

**NDK 完整性由配置固定**：旧包装脚本的 `pickNdk()` 会过滤掉不含 `build/cmake/android.toolchain.cmake` 的目录；脚本删除后，这项保护改为“由 `src-tauri/.cargo/config.toml` 把 `ANDROID_NDK` 固定到完整 NDK”。SDK 里可能残留旧版或不完整目录，盲选 `ndk/<版本号>` 会拿到不可用的一套。

#### 10.3.2 手工交叉编译 MNN 时的参数对应关系

MNN 的 CMake 构建需要三个与“目标”有关的参数（第 30 章展开）：

| 参数 | 值 | 对应三元组的哪一段 |
|---|---|---|
| `-DANDROID_ABI=arm64-v8a` | `arm64-v8a` | 对应 `aarch64`，但这是 **NDK 的 ABI 目录名**，不是三元组名 |
| `-DANDROID_PLATFORM=android-24` | `android-24` | API level，不在三元组中 |
| `-DCMAKE_TOOLCHAIN_FILE=.../android.toolchain.cmake` | NDK 提供 | 告诉 CMake “这是 Android 目标” |

**必须记住的映射**：

```
Rust 三元组          aarch64-linux-android
NDK ABI 名           arm64-v8a
APK 内目录名         lib/arm64-v8a/
```

三者指同一件事，但**写法完全不同**。把 `arm64-v8a` 填进 `--target` 会报“未知目标”；把 `aarch64-linux-android` 填进 `ANDROID_ABI` 会报“不支持的 ABI”。[通用原理]

#### 10.3.3 产物目录的层级

```powershell
# 交叉编译 example 后
Get-ChildItem .\src-tauri\target\aarch64-linux-android\release\examples\mnn_smoke
```

路径拆解：

| 段 | 含义 |
|---|---|
| `target/` | Cargo 产物根 |
| `aarch64-linux-android/` | **目标**专用子目录，与宿主产物隔离 |
| `release/` | profile（`debug` 则对应另一目录） |
| `examples/` | 目标种类 |
| `mnn_smoke` | 文件名，无扩展名 |

如果没写 `--target`，产物会在 `target/release/` 下，是**宿主**架构，推到手机上无法执行。这是“推上去报 `Exec format error`”的最常见原因。

### 10.4 常见坑与判别方法

| 错误信息 | 原因 | 处理 |
|---|---|---|
| `error[E0463]: can't find crate for 'std'` + `the 'aarch64-linux-android' target may not be installed` | 没装目标标准库 | `rustup target add aarch64-linux-android` |
| `error: linker 'aarch64-linux-android24-clang' not found` | 链接器不在 PATH，或变量没设 | 设 `CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER` 为绝对路径 |
| `error: linking with ... failed: ... file format not recognized` | 混入了宿主架构的目标文件 | 检查 `CC_aarch64_linux_android` 与 CMake 的 `ANDROID_ABI` |
| `Exec format error`（在手机上执行时） | 产物是 x86_64 宿主架构 | 确认构建时带了 `--target aarch64-linux-android`；用 `readelf -h` 查 `Machine` |
| `error: unknown target triple 'arm64-v8a'` | 把 NDK ABI 名当三元组 | 用 `aarch64-linux-android` |
| `note: run with 'rustc --explain E0463'` 但装了 target 仍失败 | 工具链不是 `stable`，或用了 `+nightly` 覆盖 | `rustup target add --toolchain <具体工具链> aarch64-linux-android` |
| CMake 报 `Could not find toolchain file` | NDK 目录不完整，或缺 `android.toolchain.cmake` | 逐个检查 `ndk/*`，让 `ANDROID_NDK` 指向含 toolchain 文件的那一个 |

### 10.5 小结

1. 目标三元组决定“为谁的 CPU、系统、运行环境”编译；`aarch64-linux-android` 三段分别对应 ARM64、Linux 内核、Android 运行时。
2. API level 不在三元组里，它由 NDK 参数表达；`arm64-v8a` 是 NDK 的 ABI 名，三者不能混填。
3. `rustup target add` 只装目标标准库，不装链接器；链接器与 C/C++ 编译器都来自 NDK。
4. `CARGO_TARGET_<TRIPLE>_LINKER` 与 `CC_<triple>` 是两个不同消费者（rustc 与 cc crate），缺一不可。
5. 所有交叉编译产物都在 `target/<triple>/` 下；找不到产物时先确认有没有 `--target`。

### 10.6 练习题

**第 1 题**：为什么 `rustup target add` 不能替代 NDK？

> 参考答案要点：它只提供目标平台的 Rust 标准库（`.rlib`），不含链接器、C/C++ 编译器、bionic 系统库、`libc++_shared`。Rust 代码编译需要链接器才能变成 ELF 可执行文件，C++ 部分更需要完整 NDK 工具链。

**第 2 题**：一个同事把 `ANDROID_ABI` 写成 `aarch64-linux-android`，CMake 报错。请指出错在哪一层，并给出正确值。

> 参考答案要点：`ANDROID_ABI` 属于 NDK 的 ABI 命名体系，合法值是 `arm64-v8a` 等；`aarch64-linux-android` 是 Rust/LLVM 三元组，两者属于不同命名空间。正确值 `arm64-v8a`。

**第 3 题**：你在手机上执行产物得到 `Exec format error`。请给出至少三条判别命令，并说明每条看什么。

> 参考答案要点：`adb shell file /data/local/tmp/mnn/mnn_smoke` 看架构；`readelf -h`（WSL/NDK 工具链）看 `Machine: AArch64` 与 `Type: DYN`；`Get-ChildItem target\aarch64-linux-android` 确认产物确实在目标目录；再检查构建命令是否漏了 `--target`。
