# 第六部分：构建工具链

> **本部分要解决什么**
>
> 第五部分解释了“库是什么”。这一部分解释“库是怎么被造出来的”。你会在 Windows 上，用 CMake 指挥 NDK 里的 clang，把一份 C++ 源码编成 ARM64 静态库；中间还会遇到一个 CMake 的规则报错、一个 CMake 4.x 的政策报错，以及一个被反复误判的 Windows 构建报错（第 32 章用一组 A–G 对照实验把它拆开）。
>
> 这三个报错都不是“环境坏了”，而是几套规则在互相碰撞：
>
> - CMake 的 target 类型规则（OBJECT library 不能挂 `POST_BUILD`）；
> - CMake 的版本政策规则（4.x 不再兼容过旧的 `cmake_minimum_required`）；
> - Windows 上的环境变量链、符号链接与“命令执行环境”的差异（不是简单的“权限不足”）。
>
> 本部分的目标是让你看到报错时，能判断“这是哪套规则在起作用”，而不是盲目重装工具链。

## 第 28 章 CMake 语法要点：target、OBJECT library 与 install

### 28.1 本章要解决什么问题

MNN 的构建入口是一个 `CMakeLists.txt` 树。你不需要读懂全部，但必须能：

- 找到“哪个 target 产出 `libMNN.a`”；
- 看懂 `-D<VAR>=<VALUE>` 这类参数最终影响了什么；
- 看懂 `install` 规则把哪些文件放到了哪里（这决定了 staging 目录长什么样）；
- 独立判断“`Target "llm" is an OBJECT library that may not have PRE_BUILD, PRE_LINK, or POST_BUILD commands.`”这条报错的原因与修法。

### 28.2 概念

#### 28.2.1 CMake 是“生成器”，不是编译器

**定义**：CMake 读取 `CMakeLists.txt`，生成另一套构建系统需要的文件（Ninja 的 `build.ninja`、Make 的 `Makefile`、Visual Studio 的 `.sln`），然后由那套系统去调编译器。

**类比**：CMake 是装修设计师，出的是施工图；Ninja 是施工队，按图干活。设计师不砌墙。

**三个阶段**：

```
① configure（配置）：读 CMakeLists，检查编译器/依赖，把结果写进 CMakeCache.txt
        ↓
② generate（生成）：产出 build.ninja（或 Makefile / .sln）
        ↓
③ build（构建）：Ninja 按依赖图编译、归档、链接
        ↓
④ install（安装）：把“声明要安装的产物”复制到 CMAKE_INSTALL_PREFIX
```

`cmake -S <src> -B <build>` 做 ①②；`cmake --build <build>` 做 ③；`cmake --install <build>` 做 ④。

#### 28.2.2 target 是 CMake 的中心

**定义**：target（目标）是构建产物的抽象单位：一个可执行文件、一个静态库、一个动态库，或者一组“只编译不打包”的目标文件。

常见类型：

| 类型 | 写法 | 产物 | 用途 |
|---|---|---|---|
| 可执行 | `add_executable(name ...)` | `name`（或 `.exe`） | 工具、demo |
| 静态库 | `add_library(name STATIC ...)` | `libname.a` | 本项目的 MNN |
| 动态库 | `add_library(name SHARED ...)` | `libname.so` | 另一种部署方案 |
| 模块库 | `add_library(name MODULE ...)` | `libname.so`（不自动链接） | 插件 |
| **对象库** | `add_library(name OBJECT ...)` | **无产物**，只有 `.o` | 多个 target 共享源文件 |
| 接口库 | `add_library(name INTERFACE)` | 无产物 | 只传播头文件/编译选项 |

**OBJECT library 是什么**：它只负责“把源码编成 `.o`”，不归档、不链接。别的 target 通过 `$<TARGET_OBJECTS:name>` 把它的 `.o` 拿过去用。

**类比**：普通库是“装好盒的零件箱”，OBJECT library 是“散放在流水线旁的半成品”，谁需要谁拿。

**这就解释了那个报错**：`POST_BUILD` 是“链接完成后执行一条命令”的钩子。OBJECT library 没有链接步骤，所以 CMake 拒绝给它挂 `POST_BUILD`。这不是 MNN 写错了语法，而是“给没有发动机的车装排气管”。

#### 28.2.3 `target_link_libraries` 的可见性

```cmake
target_link_libraries(mnn_smoke PRIVATE mnn)
target_link_libraries(mnn PUBLIC mnn_core)
```

- `PRIVATE`：只影响本 target，使用者不需要知道；
- `PUBLIC`：本 target 与使用者都需要；
- `INTERFACE`：本 target 不用，但使用者需要（典型是纯头文件库）。

**类比**：`PRIVATE` 是“我自己的工具，不外借”；`PUBLIC` 是“我用的工具你也得有”；`INTERFACE` 是“我不用，但你要用”。

#### 28.2.4 `install` 决定 staging 长什么样

```cmake
install(TARGETS mnn ARCHIVE DESTINATION lib)
install(FILES include/MNN/Interpreter.hpp DESTINATION include/MNN)
```

- `TARGETS`：安装构建产物；`ARCHIVE` 指静态库，`LIBRARY` 指动态库，`RUNTIME` 指可执行文件；
- `DESTINATION`：相对于 `CMAKE_INSTALL_PREFIX` 的目标目录；
- `install(FILES ...)`：安装显式列出的文件；`install(DIRECTORY ...)`：安装整个目录。

**这解释了“为什么 staging 要手工拼 include”**：如果 MNN 的 install 规则漏掉了 `transformers/llm/engine/include/llm`，`cmake --install` 之后 include 目录里就没有 `llm/llm.hpp`，只能手工补。

### 28.3 本项目实例

#### 28.3.1 那条真实的构建命令

`mnn-rs-sys` 在 Android 目标上会拼出大致这样一条命令（`[依赖源码已核实]`，见 `build.rs` 第 964–1194 行；下面是等价还原，不是逐字日志）：

```powershell
cmake -G Ninja `
  -S <mnn-src> -B <build-dir> `
  -DCMAKE_TOOLCHAIN_FILE=<ndk>\build\cmake\android.toolchain.cmake `
  -DANDROID_ABI=arm64-v8a `
  -DANDROID_PLATFORM=android-24 `
  -DANDROID_STL=c++_static `
  -DCMAKE_SYSTEM_NAME=Android `
  -DCMAKE_BUILD_TYPE=Release `
  -DCMAKE_INSTALL_PREFIX=<stage> `
  -DMNN_BUILD_SHARED_LIBS=OFF `
  -DMNN_SEP_BUILD=OFF `
  -DMNN_BUILD_LLM=ON `
  -DMNN_LLM_BUILD_DEMO=OFF `
  -DLLM_SUPPORT_HTTP_RESOURCE=OFF `
  -DMNN_KLEIDIAI=OFF
```

逐个参数解释：

| 参数 | 作用 | 不写会怎样 |
|---|---|---|
| `-G Ninja` | 选生成器 | 默认可能是 Make，Android 交叉编译下经常直接失败 |
| `-S <mnn-src>` | 源码目录 | 找不到 `CMakeLists.txt` |
| `-B <build-dir>` | 构建目录（可不存在） | 会写进源码目录，污染仓库 |
| `-DCMAKE_TOOLCHAIN_FILE=...` | 告诉 CMake 用 NDK 的交叉编译工具链 | 会用宿主机的 gcc/clang，产出 x86_64 库，后面链接全错 |
| `-DANDROID_ABI=arm64-v8a` | 目标 ABI | 默认可能编多个 ABI 或 32 位 |
| `-DANDROID_PLATFORM=android-24` | 最低 API | 版本过低可能缺符号，过高则老设备跑不了 |
| `-DANDROID_STL=c++_static` | C++ 运行时形态 | 默认值可能与最终链接方式冲突（第 26 章） |
| `-DCMAKE_BUILD_TYPE=Release` | 优化级别 | 默认空构建类型，性能数据没有意义 |
| `-DCMAKE_INSTALL_PREFIX` | install 落点 | 装到 `/usr/local`（Windows 上会失败或无意义） |
| `-DMNN_BUILD_SHARED_LIBS=OFF` | 产出静态库 | 产出 `.so`，第 23 章的选择就变了 |
| `-DMNN_SEP_BUILD=OFF` | 各模块合并进主库，`llm` 变成 OBJECT library | 若取 `ON`：拆成多个独立库，`llm` 不再是 OBJECT library，第 28.3.3 的补丁分支不生效 |
| `-DMNN_BUILD_LLM=ON` | 编 LLM 引擎 | 没有 `MNN::Transformer::Llm`，示例必然链接失败 |
| `-DMNN_LLM_BUILD_DEMO=OFF` | 不编 demo 可执行文件 | 多编 6 个 demo，时间与磁盘白花 |
| `-DLLM_SUPPORT_HTTP_RESOURCE=OFF` | 关闭 HTTP 资源加载 | 拉入 httplib，增加依赖与编译量 |
| `-DMNN_KLEIDIAI=OFF` | 关闭 KleidiAI 加速库 | 在 Android 上有 stdout/stderr 符号链接问题（脚本注释说明了这一点） |

**注意 `MNN_SEP_BUILD`**：本次构建取 `OFF`。它在第 28.3.3 节会再次出现——因为 `llm` target 的类型取决于它。

#### 28.3.3 `POST_BUILD` 报错：原因与两种修法

**报错原文**：

```
Target "llm" is an OBJECT library that may not have PRE_BUILD, PRE_LINK, or POST_BUILD commands.
```

**原因链**：

1. `MNN_SEP_BUILD=OFF` 时，`transformers/llm/engine/CMakeLists.txt` 把 LLM 源文件组织成一个 **OBJECT library** 名叫 `llm`；
2. 同一份文件里又给它挂了 `add_custom_command(TARGET llm POST_BUILD COMMAND ${CMAKE_COMMAND} ARGS -E copy_directory ...)`，本意是“构建完成后把头文件复制到输出目录”；
3. 旧版 CMake 对 OBJECT library 的这条限制执行得比较宽松，新版严格执行 → configure 阶段直接报错。

**修法 A（依赖包采用的方式，已验证）**：把“构建后复制”改成“配置时复制”。

```cmake
IF(NOT NATIVE_INCLUDE_OUTPUT)
  set(NATIVE_INCLUDE_OUTPUT ".")
ENDIF()
IF(NOT MNN_SEP_BUILD)
  # mnn-rs workaround: `llm` is an OBJECT library when MNN_SEP_BUILD is OFF,
  # and CMake forbids POST_BUILD on OBJECT libraries. Copy at configure time.
  file(COPY ${CMAKE_CURRENT_LIST_DIR}/include/ DESTINATION ${NATIVE_INCLUDE_OUTPUT})
ELSE()
  add_custom_command(
    TARGET llm
    POST_BUILD
    COMMAND ${CMAKE_COMMAND}
    ARGS -E copy_directory ${CMAKE_CURRENT_LIST_DIR}/include ${NATIVE_INCLUDE_OUTPUT}
  )
ENDIF()
```

（`[依赖源码已核实]`，见 `build.rs` 中的 `patch_llm_cmake_for_object_library()`，第 810–892 行；其中的 `NEEDLE`/`REPLACEMENT` 常量就是上面这段的原文）

机制解释：

- `file(COPY ...)` 在 **configure 阶段**执行，此时没有“链接后”的概念，因此不违反 OBJECT library 的限制；
- `IF(NOT MNN_SEP_BUILD)` 保证只在“llm 是 OBJECT library”的分支走新逻辑；`MNN_SEP_BUILD=ON` 时 `llm` 是真正的库，`POST_BUILD` 合法，保持原样；
- 补丁是**幂等**的：它先检查文件里是否已含 `file(COPY ${CMAKE_CURRENT_LIST_DIR}/include/ DESTINATION` 这行标记，有就直接返回，所以重复构建不会反复改写。

**修法 B（手工方式，历史记录）**：直接在 MNN 源码树里改同一处 CMakeLists，效果等价。项目早期用过手工补丁 `[历史记录]`，具体 diff 未留存；如果要复现，用上面的 `NEEDLE`/`REPLACEMENT` 做一次文本替换即可，改完记得 `git diff` 确认只动了这一处。

**为什么补丁打在源码树上而不是构建目录里**：`cmake` 的 configure 阶段读的是源码树里的 `CMakeLists.txt`；构建目录里的副本不参与解析。所以补丁必须落在 `<mnn-src>/transformers/llm/engine/CMakeLists.txt`。

### 28.4 常见坑与判别方法

| 错误信息 | 原因 | 排查路径 |
|---|---|---|
| `Target "llm" is an OBJECT library that may not have PRE_BUILD, PRE_LINK, or POST_BUILD commands.` | OBJECT library + `POST_BUILD` | 用 `MNN_SEP_BUILD=ON`，或按 28.3.3 打补丁 |
| `CMake Error: Could not find CMAKE_ROOT` / `cmake: command not found` | CMake 不在 PATH | `build-android.mjs` 的 `ensureBuildTools()` 会去 Visual Studio 目录找；或手动把 `...\CMake\CMake\bin` 加进 PATH |
| `Could not find toolchain file: .../android.toolchain.cmake` | NDK 不完整（新版 NDK 有时只装了部分组件） | 用 `pickNdk()` 的逻辑：只接受含该文件的 NDK；`Get-ChildItem "$env:LOCALAPPDATA\Android\Sdk\ndk"` 逐个检查 |
| `install` 后 `include/llm` 不存在 | MNN 的 install 规则没覆盖 LLM 头 | 手工补，或确认 28.3.3 的补丁已生效 |
| `CMAKE_BUILD_TYPE` 为空，产物很慢 | 没写 `-DCMAKE_BUILD_TYPE=Release` | 检查 CMakeCache.txt 里的 `CMAKE_BUILD_TYPE` |
| 反复构建后 CMake 报变量冲突 | `CMakeCache.txt` 里残留旧值（改了 toolchain 但没清缓存） | 删除整个 build 目录重配，而不是只改 `-D` |
| 改了 `CMakeLists.txt` 但构建没反应 | Ninja 的 mtime 精度/时钟问题 | `ninja -C <build> -d explain` 看它为什么认为目标是最新的 |

### 28.5 小结

1. CMake 只负责“配置 + 生成”，真正干活的是 Ninja/编译器；三阶段边界要分清。
2. target 类型决定产物与可用命令：OBJECT library 没有链接步骤，不能挂 `POST_BUILD`。
3. 那条 `llm` 报错的根因是 `MNN_SEP_BUILD=OFF` 让 `llm` 变成 OBJECT library；修法是把“构建后复制”改成“配置时 `file(COPY)`”。
4. `install` 规则决定 staging 内容；install 漏了 LLM 头，就必须手工补 `llm/llm.hpp`。
5. 从源码构建时，`libMNN.a → libmnn.a` 由脚本自动完成；手工 staging 才需要自己复制。

### 28.6 练习题

**第 1 题**：为什么 `file(COPY ...)` 可以替代 `POST_BUILD` 的 `copy_directory`，而不会导致头文件缺失？

**参考答案要点**：
- `file(COPY)` 在 configure 阶段执行，只要 configure 成功，头文件就已经在目标目录；
- `POST_BUILD` 的目的是“构建完再拷”，但它依赖“构建”这个事件；OBJECT library 没有这个事件；
- 副作用差异：`file(COPY)` 在增量构建时不会重复触发，但因为头文件不常变，问题不大。

**第 2 题**：把 `MNN_BUILD_SHARED_LIBS=OFF` 改成 `ON`，同时保持 `MNN_SEP_BUILD=OFF`，`llm` target 的类型会变吗？

**参考答案要点**：
- `MNN_BUILD_SHARED_LIBS` 控制最终产物是静态还是动态；`MNN_SEP_BUILD` 控制是否把各模块拆成独立库；
- 在 `MNN_SEP_BUILD=OFF` 下，`llm` 仍可能是 OBJECT library（被合并进主库），所以补丁分支仍会生效；
- **未验证**：具体类型需要看该版本 `CMakeLists.txt` 的实际分支；验证方式是在 configure 日志里搜 `llm` 的 target 类型，或 `ninja -t targets | Select-String "llm"`。

**第 3 题**：`cmake --install` 成功了，但 staging 里只有 `lib/libmnn.a` 没有 `include/llm`。给出两种处理方式。

**参考答案要点**：
- 从 MNN 源码树手工复制 `transformers/llm/engine/include/llm` 到 staging 的 `include/`；
- 或给 MNN 的 `install` 规则补一条 `install(DIRECTORY ... DESTINATION include)`（属于改上游代码，需要维护补丁）；
- 推荐前者用于实验，后者只在长期维护时使用。

## 第 29 章 Ninja：459 个 target 是怎么被调度的

### 29.1 本章要解决什么问题

CMake 生成 `build.ninja` 之后，构建由 Ninja 执行。你会遇到三类问题：

- 为什么并行度开太高会“编译进程被杀”；
- 为什么“只改了一个文件”，Ninja 却重编了一大片；
- 为什么构建日志里全是 `[1/459]`，而你不知道哪个 target 最慢。

### 29.2 概念

#### 29.2.1 Ninja 的设计哲学

**定义**：Ninja 是一个“极简、只关心依赖图与命令”的构建执行器。它不理解 CMake 语法，也不理解 C++；它只读 `build.ninja` 里的 `rule`、`build`、`depfile` 声明。

**类比**：Ninja 是流水线的 PLC 控制器——不设计产品，只保证“上一步没完成就不许进下一步”。

**关键文件**：

| 文件 | 作用 |
|---|---|
| `build.ninja` | 依赖图与命令（由 CMake 生成，不要手改） |
| `.ninja_log` | 每个 target 的构建耗时历史（`-t stats` 会读它） |
| `.ninja_deps` | 头文件依赖（用于“改了 .h 要重编谁”） |
| `.ninja_deps` + `depfile` | 由编译器 `-MD` 生成的依赖清单 |

#### 29.2.2 并行度

`ninja -j N` 最多同时跑 N 条命令。默认值通常是 CPU 核数 + 2。

**为什么会“被杀”**：C++ 编译是内存密集型。每个 clang 进程可能占几百 MB 到 1 GB；`-j 16` 在 16 GB 内存的机器上很容易触发 OOM，Windows 上表现为 `clang++.exe` 直接消失、Ninja 报 `FAILED: ...`、或系统卡死。

**经验值**：交叉编译 MNN 这类大工程，`-j` 取物理核数的一半到 2/3 更稳；先保证一次通过，再谈速度。

#### 29.2.3 增量构建为什么会“过度重编”

Ninja 的判定依据是 **mtime + 依赖清单**。常见误判来源：

- 生成的头文件被每次 configure 重写（mtime 变化）→ 所有依赖它的 `.o` 重编；
- 时钟不同步（WSL 与 Windows 共享目录）→ mtime 看起来“在未来”；
- 文件系统精度（某些网络盘只到 2 秒）→ 改了文件但 mtime 没变，Ninja 认为没改。

**为什么 Android 一定要 Ninja**：NDK 的 `android.toolchain.cmake` 在跨平台场景下对 Make 生成器的支持并不可靠（路径、命令行长度、并行语义都有坑）；Ninja 的 `build.ninja` 是纯文本命令列表，跨平台一致性最好。

#### 29.3.2 常用诊断命令

```powershell
# 列出所有目标（含内部目标），用于核对规模
ninja -C <build-dir> -t targets all

# 只打印将要执行的命令，不真的执行
ninja -C <build-dir> -n

# 解释“为什么这个目标要重编”
ninja -C <build-dir> -d explain <target>

# 看某次构建各 target 的耗时排名
ninja -C <build-dir> -t stats
```

逐参数说明：

- `-C <build-dir>`：切换工作目录到构建目录（Ninja 只认相对路径）；
- `-t targets all`：`-t` 是 tool 子命令，`targets` 列出目标，`all` 包含内部目标；
- `-n`：dry run；
- `-d explain`：输出判定细节，适合排查“为什么又重编了”；
- `-t stats`：读 `.ninja_log`，给出耗时统计。

#### 29.3.3 459 个 target 的构成（如何自己核对）

“459”是本次构建报告的总目标数 `[历史记录]`。它包含：

- MNN 的核心算子库与各模块（`MNN/core`、`MNN/backend/cpu`、`MNN/express` 等）；
- LLM 引擎（`llm` 及其依赖）；
- 第三方依赖（flatbuffers、protobuf 相关目标等）；
- 大量“只编译不链接”的 OBJECT library（这也是为什么 target 数远大于最终产物数）。

核对方式：`ninja -C <build-dir> -t targets all | Measure-Object -Line`，并抽样看名字：

```powershell
ninja -C <build-dir> -t targets all | Select-String "llm|MNNCore|cpu"
```

### 29.4 常见坑与判别方法

| 现象 | 原因 | 处理 |
|---|---|---|
| `ninja: error: loading 'build.ninja': No such file or directory` | 没有先跑 CMake configure，或 `-C` 指错目录 | 先 `cmake -S ... -B ... -G Ninja`，再 `ninja -C ...` |
| `FAILED: ... clang++.exe ...` 且无编译器报错文本 | 进程被 OOM 杀掉 | 降 `-j`（例如 8 → 4）；关掉其他吃内存的程序；看 Windows 事件日志 |
| 构建日志里同一条命令出现两次 | 两个 target 生成了同一个输出文件 | 查 CMake 的 `add_custom_command` 的 `OUTPUT`/`DEPENDS` 是否重复声明 |
| 改了头文件，只重编了很少文件 | `.ninja_deps` 损坏或 `depfile` 缺失 | 删除 `.ninja_deps` 后全量重建一次 |
| `ninja -t stats` 没有数据 | `.ninja_log` 被删或构建用的不是该目录 | 重新构建一次再统计 |
| 路径含中文/空格导致奇怪失败 | 部分工具链对非 ASCII 路径处理不佳 | 把构建目录放到纯 ASCII、无空格路径（例如 `C:\mnn-build`） |

### 29.5 小结

1. CMake 出图，Ninja 施工；`build.ninja` 是生成物，不要手改。
2. Android 交叉编译通常用 Ninja；本项目的包装脚本显式设置 `CMAKE_GENERATOR=Ninja`，但第 32 章 E 组实验显示它并非必需（只设 `ANDROID_NDK` 也能构建成功）。
3. 并行度不是越高越好，C++ 编译的内存压力常常先于 CPU 成为瓶颈。
4. `-d explain` 是排查“为什么又重编”的第一工具，比反复 `clean` 有效。
5. target 数远大于产物数，是因为大量 OBJECT library 与内部目标；核对规模用 `-t targets all`。

### 29.6 练习题

**第 1 题**：`ninja -C build -n` 和 `cmake --build build --dry-run` 有什么区别？

**参考答案要点**：
- 两者都是“只打印不执行”；`ninja -n` 只处理 Ninja 层，`cmake --build` 会先做一层生成器封装再转发；
- 在 Ninja 生成器下结果基本一致；
- 如果构建目录不是 Ninja（例如 Make），`ninja -n` 直接失败。

**第 2 题**：16 GB 内存、8 核 CPU，交叉编译 MNN 时 `-j` 设多少更稳？给出理由与调整策略。

**参考答案要点**：
- 建议从 `-j 4` 开始；每个 clang 进程峰值可能数百 MB，加上链接阶段的内存峰值，8 并发容易 OOM；
- 策略：先 `-j 4` 跑通，再逐步加；观察任务管理器/`Get-Process clang++` 的峰值内存；
- 链接大静态库时并发不是瓶颈，单线程链接可能更稳。

**第 3 题**：如何证明“改了某个头文件之后，重编的 `.o` 数量符合预期”？

**参考答案要点**：
- 改头文件前 `ninja -n` 记录待执行命令数；
- 改完后 `ninja -n | Measure-Object -Line` 对比；
- 若数量异常大，检查该头文件是否被“聚合头”（把所有头都 include 进来）引入；
- `-d explain` 可定位是谁依赖了它。

## 第 30 章 NDK toolchain、ABI/API level 与 16 KB page

### 30.1 本章要解决什么问题

你在 Windows 上编译，目标却是 ARM64 的 Android。这中间有三个必须显式回答的问题：

1. 用哪套编译器、哪套系统头文件？（NDK toolchain）
2. 产出给哪种 CPU 架构？（ABI）
3. 最低支持哪个 Android 版本？页面大小是多少？（API level 与 16 KB page）

答错任何一个，产物都可能在“链接成功、安装失败、启动即崩”的某一环倒下。

### 30.2 概念

#### 30.2.1 NDK 是什么

**定义**：NDK（Native Development Kit）是一套“给 Android 编原生代码”的工具集合，包含：

- **交叉编译器**：`clang` / `clang++`（目标三元组形如 `aarch64-linux-android24`）；
- **sysroot**：目标平台的系统头文件与库（`libc.so`、`libm.so`、`liblog.so` 等）；
- **STL**：libc++ 的静态/共享形态；
- **CMake 工具链文件**：`build/cmake/android.toolchain.cmake`；
- **构建工具**：`llvm-ar`、`llvm-nm`、`llvm-readelf`、`llvm-strip` 等。

**类比**：NDK 是一个“出国施工工具箱”——里面的工具都按目的地（Android/ARM64）校准过，不能拿国内的工具凑合。

**NDK 版本**：本项目使用 `28.2.13676358` `[历史记录]`。这个目录名由“主版本.次版本.构建号”组成，安装后位于 `%LOCALAPPDATA%\Android\Sdk\ndk\`。

#### 30.2.2 ABI、架构与三元组

| ABI 名（Android） | 架构 | Rust 目标三元组 | 说明 |
|---|---|---|---|
| `arm64-v8a` | ARMv8-A 64 位 | `aarch64-linux-android` | 本项目唯一目标 |
| `armeabi-v7a` | ARMv7 32 位 | `armv7-linux-androideabi` | 老设备 |
| `x86_64` | x86-64 | `x86_64-linux-android` | 模拟器 |
| `x86` | x86 32 位 | `i686-linux-android` | 老模拟器 |

**ABI 不是“CPU 型号”**，而是“二进制接口约定”：指令集子版本、浮点调用约定、库搜索路径。两个都叫 ARM64 的库，如果一个按 `arm64-v8a` 编、一个按 `arm64-v8a` + 不同 API 编，仍可能不兼容。

#### 30.2.3 API level：不只是“版本号”

**定义**：`ANDROID_PLATFORM=android-24` 里的 24 是 API level（Android 7.0）。它同时决定：

- 编译器能看到的系统头文件集合（新 API 的函数声明在旧 level 下不可见）；
- 链接时使用的 stub 库版本（决定你能引用哪些系统符号）；
- 产物的 `minSdkVersion` 约束（低于它的设备装不上）。

**机制**：如果库按 `android-26` 编译并引用了 26 才有的符号，而你把它装到 API 24 的设备上，链接期不会报错（stub 库里有），运行期 `dlopen` 会因符号缺失失败。

#### 30.2.4 16 KB page

**定义**：Android 的内存页大小传统是 4 KB。Android 15 起，部分设备使用 16 KB 页。可执行文件与 `.so` 的 `LOAD` 段对齐必须匹配页大小，否则加载失败。

**机制**：ELF 的 program header 里有 `Align` 字段；加载器要求 `Align` 至少等于页大小（或为其整数倍）。4 KB 对齐的 `.so` 在 16 KB 页设备上会被拒绝映射。

**类比**：页是“集装箱”，你的货（代码段）必须按集装箱尺寸打包；用 4 KB 的箱子去装 16 KB 的仓位，装不进去。

**NDK 侧**：NDK r28 起，默认的链接对齐已经按 16 KB 处理（这是官方为 Android 15 做的调整）`[通用原理]`。本项目用的正是 28.2，理论上满足要求；但**是否真的对齐，必须以产物为准**：

```powershell
& "$TOOLS\llvm-readelf.exe" -l libMNN.a | Select-String "LOAD"
```

静态库本身没有 program header（`.a` 是归档，不是 ELF），所以要检查最终产物：

```powershell
& "$TOOLS\llvm-readelf.exe" -l .\mnn_smoke | Select-String "LOAD"
```

看 `Align` 列：`0x4000` 表示 16 KB 对齐，`0x1000` 表示 4 KB。本次产物的对齐值没有留存记录 `[未复核]`。

### 30.3 本项目实例

#### 30.3.1 NDK 选择的真实逻辑

`build-android.mjs` 的 `pickNdk()` 做了一件很关键的事：**只接受真正完整的 NDK**。

```javascript
const versions = readdirSync(ndkRoot).filter((name) =>
  existsSync(join(ndkRoot, name, "build", "cmake", "android.toolchain.cmake")),
);
```

（`[仓库已核实]`，第 41–43 行）

原因写在文件头部注释里：这台机器上最新版 NDK（30.x）是一次不完整的安装，缺少 `android.toolchain.cmake`，而 `llama-cpp-sys-2` 会“自动挑最新 NDK”，于是直接 panic。

**排查思路**：当构建报“找不到 toolchain file”时，不要先怀疑路径拼错，先确认这个 NDK 目录是否完整：

```powershell
$ndkRoot = "$env:LOCALAPPDATA\Android\Sdk\ndk"
Get-ChildItem $ndkRoot | ForEach-Object {
  "$($_.Name)  toolchain=$(Test-Path (Join-Path $_.FullName 'build\cmake\android.toolchain.cmake'))"
}
```

#### 30.3.2 API level 的三个来源

| 来源 | 值 | 依据 |
|---|---|---|
| `mnn-rs-sys` 的 wrapper 编译 | 24（硬编码） | `[依赖源码已核实]`，`build.rs` 第 435 行 |
| `mnn-rs-sys` 给 MNN 的 CMake | `android-24` | `[依赖源码已核实]`，第 1167 行 |
| 项目脚本的 `minSdkVersion()` | 读 `tauri.conf.json`，缺失则 24 | `[仓库已核实]`，第 58–68 行 |

当前 `src-tauri/tauri.conf.json` 的 `bundle.android` 里只有 `debugApplicationIdSuffix`，没有 `minSdkVersion`（`[仓库已核实]`，见 [tauri.conf.json](file:///C:/Users/16412/Documents/Github_Repositories/Notes_App-mnn-engine/src-tauri/tauri.conf.json#L43-L45)），所以脚本回落到 24，与 MNN 的编译 API 一致。

**这是一个隐式契约**：三处必须一致。只要有一处漂到 26，而设备或应用仍按 24 发布，就会出现“编译过、装得上、跑不起来”的经典故障。

#### 30.3.3 16 KB page 的检查点

需要检查的产物有两类：

1. `mnn_smoke`（可执行文件，PIE）；
2. 应用侧的 `libapp_lib.so`（Rust 的 `cdylib`，最终进 APK）。

检查脚本：

```powershell
foreach ($f in @(".\mnn_smoke", ".\libapp_lib.so")) {
  if (Test-Path $f) {
    "== $f"
    & "$TOOLS\llvm-readelf.exe" -l $f | Select-String "LOAD"
  }
}
```

如果 `Align` 是 `0x1000`，需要在链接参数里补：

```
-Wl,-z,max-page-size=16384
```

这条参数告诉链接器“按 16 KB 对齐生成 LOAD 段”。静态库本身不需要这个，最终链接可执行文件/`.so` 时才需要。

### 30.4 常见坑与判别方法

| 错误/现象 | 原因 | 排查路径 |
|---|---|---|
| `Android NDK toolchain not found. Expected at: ...\toolchains\llvm\prebuilt\windows-x86_64\bin` | NDK 不完整，或环境变量未指向它 | 检查 `toolchains\llvm\prebuilt\<host>\bin` 是否存在；确认 `ANDROID_NDK` 指向完整 NDK（第 32 章：探测链会优先读它，否则可能扫到残缺的最大版本） |
| `CMAKE_TOOLCHAIN_FILE` 找不到 | 同上，或缺 `build/cmake/android.toolchain.cmake` | `Test-Path` 逐个验证 |
| 设备上 `INSTALL_FAILED_NO_MATCHING_ABIS` | APK 里没有 `arm64-v8a` | `unzip -l app.apk \| Select-String "lib/"` |
| Android 15 设备上装不上或加载失败 | 16 KB 对齐不满足 | `llvm-readelf -l` 看 `Align` |
| `dlopen failed: cannot locate symbol "__android_log_print"` | API level 不匹配或没链 `liblog` | 检查 `-llog`；确认 API level 一致 |
| 编出的库在模拟器上能跑、真机不能 | ABI 不匹配（x86_64 vs arm64-v8a） | `llvm-readelf -h` 看 `Machine` |

### 30.5 小结

1. NDK 是“校准过的出国工具箱”：编译器、sysroot、STL、toolchain 文件缺一不可。
2. ABI、三元组、API level 是三个不同维度；它们决定产物的兼容边界。
3. API level 必须三处一致（wrapper 编译、MNN 构建、应用 `minSdk`），否则会出现“链接过、运行崩”。
4. 16 KB page 是 Android 15 的硬要求，检查点在最终产物的 LOAD 段 `Align` 是否 `0x4000`。
5. 本项目的 NDK 选择逻辑（只接受含 toolchain 文件的版本）是踩坑后的防御性设计，值得直接复用。

### 30.6 练习题

**第 1 题**：为什么 `libMNN.a` 不能用 `llvm-readelf -l` 检查对齐，而必须检查最终产物？

**参考答案要点**：
- `.a` 是 ar 归档，不是 ELF 文件；`llvm-readelf` 对归档只能列成员，不能读 program header；
- 对齐是链接阶段决定的；
- 正确做法：`llvm-ar t` 列出成员后对成员单独检查，或直接检查链接产物。

**第 2 题**：设备是 API 24，你的库按 API 26 编译并用了 26 才有的符号。会在哪一步报错？为什么？

**参考答案要点**：
- 链接期不会报错（NDK 的 stub 库按 26 提供符号）；
- 运行期 `dlopen`/加载时报 `cannot locate symbol`，因为设备上 24 的 libc 没有该符号；
- 预防：在 CI 里对产物跑 `llvm-readelf --dyn-syms`，对照目标 API 的符号清单。

**第 3 题**：写出一条命令，一次性列出某个 NDK 里所有可用的 ABI 与对应工具链前缀。

**参考答案要点**：
```powershell

dir "$NDK\toolchains\llvm\prebuilt\windows-x86_64\bin\*linux-android*clang.exe"
```
- 第二种更直接：文件名里就带 `aarch64-linux-android24-clang.exe` 这类前缀；
- 也可 `llvm-readelf` 查看 sysroot 下的库目录。

## 第 31 章 CMake 4.x policy 与旧工程兼容

### 31.1 本章要解决什么问题

同一个 CMakeLists，在 CMake 3.20 上能 configure，在 CMake 4.x 上直接报错退出。这不是你的代码坏了，而是 CMake 收紧了“向后兼容”的边界。

本章要让你能：

- 读懂 `cmake_minimum_required(VERSION x.y)` 到底声明了什么；
- 认出“Compatibility with CMake < 3.5 has been removed”这条报错；
- 用最小改动让老工程在新 CMake 上跑起来。

### 31.2 概念

#### 31.2.1 `cmake_minimum_required` 不是“建议”，是“政策开关”

**定义**：每个 `CMakeLists.txt` 开头都要写 `cmake_minimum_required(VERSION x.y)`。它做两件事：

1. 声明“本工程至少需要哪个 CMake 版本”；
2. 把该版本及之前引入的所有 **policy**（`CMPxxxx`）设为“旧行为”或“新行为”。

**policy 是什么**：CMake 在演进中改变了某些命令的默认行为（比如 `if()` 的字符串比较规则、`INCLUDE_DIRECTORIES` 的传播方式）。为了不破坏老工程，它给每个变化编了号（`CMP0000`…），并允许工程通过 `cmake_minimum_required` 或 `cmake_policy(SET CMPxxxx OLD/NEW)` 选择行为。

**类比**：policy 是“法律生效日期”。老工程声明“我按 2012 年的法律办事”，CMake 就尽量按老规矩解释；但法律不能无限追溯。

#### 31.2.2 CMake 4.0 的断点：< 3.5 不再兼容

CMake 4.0 移除了对 `cmake_minimum_required(VERSION <3.5)` 的兼容。典型报错：

```
CMake Error at CMakeLists.txt:1 (cmake_minimum_required):
  Compatibility with CMake < 3.5 has been removed from CMake.

  Update the VERSION argument <min> value.  Or, use the <min>...<max> syntax
  to tell CMake that the project requires at least <min> but has been updated
  to work with policies introduced by <max> or earlier.

  Or, add -DCMAKE_POLICY_VERSION_MINIMUM=3.5 to try configuring anyway.
```

（这是 CMake 4.x 的标准文案 `[通用原理]`）

**注意最后一行**：CMake 自己给了逃生舱 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`。它不会真的把政策改对，只是让 configure 不再因版本检查而中止——所以它可能“侥幸通过”，也可能在后面某个命令上出现行为差异。

#### 31.2.3 三种处理方式

| 方式 | 做法 | 适用场景 | 风险 |
|---|---|---|---|
| 升声明 | 把 `VERSION 3.1` 改成 `3.10` 或更高 | 你自己的工程 | 若有代码依赖旧政策，行为会变 |
| 加逃生舱 | `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` | 第三方依赖无法改 | 只是跳过检查，行为仍可能是旧的 |
| 降 CMake | 用 3.x 版本构建 | 一次性复现历史结果 | 环境里要维护两套 CMake |

### 31.3 本项目实例

#### 31.3.1 现象与状态

MNN 3.6.1 的 CMake 树里有若干子目录声明了较旧的 `cmake_minimum_required`，在 CMake 4.x 下会触发上述政策报错 `[历史记录]`（具体的 CMake 版本号与完整日志未留存，`[未复核]`）。

本次构建最终成功产出了 `libMNN.a`，说明问题被绕过了。**绕过方式没有记录**（可能是改用 CMake 3.x，或加了 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`）。书中不把任何一种说成“本项目采用的方法”。

#### 31.3.2 如何自己判断走哪条路

```powershell
cmake --version
```

先看主版本：

- 若是 **3.x**：不会遇到这个报错，继续排查其他原因；
- 若是 **4.x**：在 configure 日志里搜 `Compatibility with CMake < 3.5`，并记录是哪个 `CMakeLists.txt` 第几行报的。

```powershell
cmake -S <mnn-src> -B <build-dir> -G Ninja <其他参数> 2>&1 |
  Tee-Object -FilePath .\configure.log
Select-String "Compatibility with CMake" .\configure.log -Context 3,3
```

`-Context 3,3` 会显示报错前后各 3 行，方便定位是哪个子工程。

**推荐做法**：

1. 先用 CMake 3.x 把链路跑通（保证“能构建”这个基线）；
2. 再在 4.x 上复现报错，确认报错来源；
3. 对第三方源码只加 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`，不改源码（改源码会让补丁越滚越多）；
4. 把 CMake 版本写进构建文档，别让它成为“某台机器上能过”的隐变量。

#### 31.3.3 为什么这条报错特别容易误判

因为它出现在 **configure 的第一个命令**，看起来像“工程文件损坏”。常见的误判与纠正：

| 误判 | 实际 |
|---|---|
| “MNN 源码坏了，重新 clone” | 源码没问题，是 CMake 版本变了 |
| “是我传的某个 `-D` 参数有问题” | 报错发生在读参数之前的版本检查 |
| “重装 CMake 就好了” | 重装成同一个 4.x 仍然报错 |
| “加 `-Wno-dev` 能压掉” | 这是 `CMake Error`，不是 warning |

### 31.4 常见坑与判别方法

| 错误信息 | 原因 | 处理 |
|---|---|---|
| `Compatibility with CMake < 3.5 has been removed from CMake.` | 子工程的 `cmake_minimum_required` 过旧 + CMake 4.x | 升声明 / 加 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` / 降 CMake |
| `Policy CMP0135 is not set` 之类的警告 | 某些行为（如 `ExternalProject` 的时间戳）未显式选择 | 在顶层 `cmake_policy(SET CMP0135 NEW)`，或忽略（只是 warning） |
| 同一工程在两台机器上行为不同 | CMake 版本不同，政策默认值不同 | `cmake --version` 写进构建记录；用 `cmake_policy(VERSION ...)` 显式固定 |
| 加了逃生舱后构建过了，但产物行为异常 | 旧政策的副作用被保留（例如库搜索顺序、rpath 处理） | 优先升声明；逃生舱只当临时手段 |
| `CMake Warning (dev) ...` 被当成错误 | 有些 CI 把 warning 当 error | 检查 CI 的 `-Werror=dev` 配置，而不是改工程 |

### 31.5 小结

1. `cmake_minimum_required` 是政策开关，不是版本备注。
2. CMake 4.x 不再兼容声明低于 3.5 的工程；报错文案里自带逃生舱 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`。
3. 对第三方源码优先用命令行参数绕过，不要改源码；改源码意味着你要长期维护补丁。
4. 本项目遇到过这条报错，但最终绕过方式未留存，标注 `[未复核]`；书中给出两条可复现的路径而不是唯一答案。
5. 把工具版本写进文档，是避免“玄学构建失败”最便宜的手段。

### 31.6 练习题

**第 1 题**：为什么“升 `cmake_minimum_required` 的版本号”可能改变构建结果，而不只是消除报错？

**参考答案要点**：
- 版本号提升会把一批 policy 切到 NEW 行为；
- NEW 行为可能改变库搜索、rpath、`if()` 比较、依赖传播等；
- 所以升版本后必须重跑构建与运行验证，不能只看 configure 是否通过。

**第 2 题**：给出一条命令，用于在不改源码的前提下，让一个声明 `cmake_minimum_required(VERSION 2.8)` 的第三方工程在 CMake 4.x 上 configure。

**参考答案要点**：
```powershell
cmake -S <src> -B <build> -G Ninja -DCMAKE_POLICY_VERSION_MINIMUM=3.5
```
- 说明这只是跳过版本检查，行为仍是老政策；需要验证产物。

**第 3 题**：如何在一个多目录工程里快速定位“是哪一行触发了政策报错”？

**参考答案要点**：
- 把 configure 输出写入文件；
- `Select-String "Compatibility with CMake" -Context 3,3`；
- 报错行里的 `CMakeLists.txt:N (cmake_minimum_required)` 直接给出行号；
- 若是 `add_subdirectory` 引入的子工程，按目录顺序逐个排查。

## 第 32 章 Windows 构建与 NDK 探测：`0x80070005` 到底是谁拒绝的

### 32.1 本章要解决什么问题

在 Windows 上构建 Android 包时，你会遇到三类现象：

1. 直接敲 `pnpm tauri android build`，约 38 秒后失败，C++ 侧报 `Android NDK toolchain file not found: ...\ndk\30.0.16248370`；
2. 在受管终端（例如 AI 的命令执行环境）里构建，报 `os error 5`，或它的 HRESULT 写法 `0x80070005`（十进制 `-2147024891`）；
3. 增量构建时 `jniLibs` 里的链接报错——旧资料把这一类解释成“两个写入者抢同一个文件”。

**本章的结论已经更新。** 2026-11-02 下午做了一组 A–G 对照实验（真实终端、非管理员、非沙箱、同一份工作副本），日志留在 `%TEMP%\notes-android-control\`，汇总在 `summary.txt` `[已验证]`。实验推翻了本书旧版“`0x80070005` = 覆盖冲突 + Gradle 双写入者”的写法。真实情况是两件事：

- **唯一的硬失败**：不设 NDK 变量时，探测链会扫到 SDK 里版本号最大、但内容残缺的 NDK 30.0，于是报 toolchain 文件找不到；
- **`os error 5` 是执行环境的假阳性**：它只在 AI 命令沙箱里出现，真实终端 6 次构建一次都没有复现。

本章先把机制讲清，再给最小可用方案，最后保留一节“常见误解”——因为这两个错误结论当年都看起来非常有道理。理解它们为什么错，比背下正确答案更有用。

### 32.2 概念

#### 32.2.1 NDK 探测顺序：谁决定用哪个 NDK

**定义**：探测顺序（probe order）指一个工具启动时，按固定优先级依次检查多个候选位置，取第一个“看起来可用”的作为结果。

**类比**：出门找钥匙。先摸自己的口袋（显式设置的环境变量），再翻玄关的公共抽屉（SDK 安装目录）。口袋里没有，就抓抽屉里最上面那把——而“最上面”通常按版本号排序，不等于“最能开这扇门”。

`llama-cpp-sys-2` 的 `build.rs` 使用的顺序是 `[已验证]`（日志在 `%TEMP%\notes-android-control\`）：

```
ANDROID_NDK
  └→ ANDROID_NDK_ROOT
      └→ NDK_ROOT
          └→ CARGO_NDK_ANDROID_NDK
              └→ 扫描 <SDK>\ndk\*，取版本号最大者
```

A 组实验里，前四个都没设，于是走到最后一步：本机 `ndk` 目录下版本号最大的是 `30.0.16248370`，但该目录残缺（缺完整的 toolchain 文件），于是报：

```
Android NDK toolchain file not found: ...\ndk\30.0.16248370
```

注意措辞：它说的是 **toolchain file not found**，不是 **NDK not found**。区别很重要：

| 措辞 | 含义 |
|---|---|
| `NDK not found` | 连目录都没找到 |
| `toolchain file not found` | 目录找到了，但里面没有 `build\cmake\android.toolchain.cmake` |

**判据**：对本项目而言，一个 NDK 目录“可用”的前提是下面这个文件存在：

```powershell
Test-Path "$env:ANDROID_NDK\build\cmake\android.toolchain.cmake"
```

这正是 `build-android.mjs` 里 `pickNdk()` 的过滤条件 `[仓库已核实]`：它只接受含 toolchain 文件的 NDK。换句话说，脚本早就知道“目录存在 ≠ NDK 可用”，只是这个知识在旧版第 32 章里被符号链接的叙事盖住了。

#### 32.2.2 `0x80070005`、`os error 5`、`-2147024891` 是同一个数字

这三个写法经常让人以为是三件事，其实是同一件事的三件外衣：

| 写法 | 出处 | 构成 |
|---|---|---|
| `5` | Win32 错误码 `ERROR_ACCESS_DENIED` | 原始值 |
| `0x80070005` | HRESULT | 高 16 位 `0x8007` 表示“来自 Win32”，低 16 位 `0x0005` 就是上面那个 5 |
| `-2147024891` | 带符号十进制 | `0x80070005` 按 32 位有符号解释的结果 |
| `os error 5` | Rust `std::io::Error` 的 Display | Windows 上的 raw OS error 就是 5 |

`[通用原理]`

**类比**：同一个人穿警服、便服、工装。衣服不同，人还是同一个。不能因为看到三种衣服就断定有三个嫌疑人。

**这决定了排查方向**：错误码只告诉你“被拒绝”，**不告诉你“谁拒绝、为什么拒绝”**。必须回到失败的那一行代码看上下文。

#### 32.2.3 两类真实的拒绝来源

| 来源 | 触发条件 | 判别特征 |
|---|---|---|
| NDK 版本选择错误 | 未设 `ANDROID_NDK`，探测命中残缺的最大版本 | 报 `toolchain file not found`；约 38 秒内失败（A 组） |
| 命令沙箱写限制 | 在 AI 命令执行环境里跑构建 | 只在受管终端失败；真实终端同一命令成功（B、F 组） |
| 历史现象：目录已存在 | 插件目录“先删后建”，删除失败后创建时目标仍在 | `os error 183`（`ERROR_ALREADY_EXISTS`）；本项目 6 次真实构建未复现 `[未复核]` |

第二条需要解释。命令沙箱为了隔离，会做两件事（机制说明属 `[未复核]`，因为沙箱内部行为无法从构建日志直接观察）：

1. **重写符号链接的目标**：把原本指向工作区外的链接改指向沙箱内的映射路径；调用方随后按原目标校验，就会看到“不一致”；
2. **把工作区外的文件标为 restricted**：NDK 通常装在 `%LOCALAPPDATA%` 下，属于工作区外，读取时被限制。

这两件事都会表现为“创建/覆盖链接被拒”，也就是 `os error 5`。**可以确认的是现象本身** `[已验证]`：A–G 七组里只有沙箱内的尝试出现过该错误；真实终端 6 次构建（B、C、D、E、F、G）无一次复现。至于“沙箱内部具体怎么改写”，属于 `[未复核]`——本章只把“换真实终端就能过”作为可操作结论。

#### 32.2.4 `jniLibs` 到底有几个写入者

**定义**：写入者（writer）指对同一个路径实际执行创建、覆盖、删除的主体。只有“真的往里写”的才算。

事实是**只有一个**：

```
        Rust cdylib（libapp_lib.so）
                 │
                 │ tauri-cli 建立/覆盖符号链接     ← 唯一的写入者
                 ▼
   src-tauri/gen/android/app/src/main/jniLibs/arm64-v8a/
                 │
                 │ Gradle mergeJniFolders 只读收集
                 ▼
   build/intermediates/.../merged_native_libs/...   ← 中间产物，不回写源码树
```

`[通用原理]` + `[已验证]`（C 组）。

**类比**：一个人往信箱里放信（tauri-cli），另一个人每天从信箱取信去分发（Gradle）。取信的人不会覆盖你刚放进去的信。把“读的人”算成“写的人”，就会凭空造出一个冲突。

旧版解释错在把 `mergeJniFolders` 这个名字读成了“合并后写回”。它的实际语义是“把多个 native 源目录收集到中间产物目录”，源目录只读。

C 组实验直接检验了这一点：第二次增量构建、**完全不清理 `jniLibs`**，健康的符号链接被直接覆写，75 秒成功，没有 `os error 183` `[已验证]`。

**仍成立的那半句**：Windows 上创建符号链接通常需要开发者模式或 `SeCreateSymbolicLinkPrivilege` `[通用原理]`。但本机 6 次真实终端构建全部成功，说明该策略在本机已经满足。**不能**由此推断“任何机器都不需要这项特权”——换一台没开开发者模式的机器，仍可能卡在创建链接这一步。这是本章唯一保留的“权限”因素，与 `0x80070005` 在本项目里的首因无关。

#### 32.2.5 ABI 由 `--target` 决定，不由 `abiFilters` 决定

`--target aarch64` 传给 rustc 的目标是 `aarch64-linux-android`，产物只会落在 `arm64-v8a`。D 组实验把 `abiFilters` 注入整个去掉，APK 仍然只有 `arm64-v8a` `[已验证]`。

另一个容易忽略的点：Tauri 的 `RustPlugin.kt` 里有一个 universal flavor，**在未指定 target 时它自己会加 4 个 ABI**。所以“APK 里有 4 个 ABI”往往不是 `abiFilters` 失效，而是你根本没传 `--target`。

**类比**：`abiFilters` 像在门口贴一张“只许 arm64 进入”的纸条；`--target` 才是真正只放一种人进来的门禁。纸条可能被保洁撕掉（`gen/` 重新生成），门禁不会。

（`[仓库已核实]`，脚本注释记录了 `os error 183` 与 `0x80070005` 两个历史错误，见 [prepare-android-plugins.mjs](file:///C:/Users/16412/Documents/Github_Repositories/Notes_App/scripts/prepare-android-plugins.mjs#L5-L17)；但“它们代表冲突”的解释已被 32.3 的实验推翻。）

#### 32.3.2 最小可用方案：两步

```powershell
# 1) 指向完整的 NDK（写入当前用户环境，新开的终端才生效）
setx ANDROID_NDK "C:\Users\<你的用户名>\AppData\Local\Android\Sdk\ndk\28.2.13676358"
```

- `setx`：把变量写入当前用户的持久环境（注册表 `HKCU\Environment`）。**只影响之后新启动的进程**；当前窗口里 `$env:ANDROID_NDK` 仍是旧值——这是“我明明设了却没生效”的最常见原因。
- `ANDROID_NDK`：名字必须逐字一致。它是探测链的第一位；写成 `ANDROID_NDK_HOME` 之类会直接掉到扫描分支。
- 路径：指向 **NDK 根目录**，不是 `toolchains` 子目录。判据是该目录下存在 `build\cmake\android.toolchain.cmake`。
- 版本号：`28.2.13676358` 是本次实验验证可用的版本 `[已验证]`；其它版本只要目录完整也可用，但需自己跑一次上面的 `Test-Path` 检查。

```powershell
# 2) 新开一个终端，构建
pnpm tauri android build --target aarch64 --features local-llm
```

逐段解释：

| 片段 | 作用 | 为什么不能省 |
|---|---|---|
| `pnpm` | 读 `package.json`，调用项目本地的 `tauri` CLI | 避免全局 CLI 版本与项目不匹配 |
| `tauri` | CLI 主命令入口 | — |
| `android build` | 走 Android 链路：生成/复用 `gen/android`、调 Gradle、打 APK | 只有它才会去读 NDK、拉起 Gradle |
| `--target aarch64` | 只编 `aarch64-linux-android` | 决定 APK 里只有 `arm64-v8a`（D 组） |
| `--features local-llm` | 打开主线仓库的 `local-llm` feature | `local-llm = ["dep:llama-cpp-2"]` `[仓库已核实]`；不开就不编 llama.cpp，APK 里没有推理能力 |

验证三步：

```powershell
echo $env:ANDROID_NDK                                                # 新终端里应打印 28.2 的路径
Test-Path "$env:ANDROID_NDK\build\cmake\android.toolchain.cmake"     # 应为 True
tar -tf <产物>.apk | Select-String "lib/"                            # 应看到 lib/arm64-v8a/ 与 libc++_shared.so
```

（APK 文件名以实际产物为准；Windows 10+ 自带 `tar`，可直接列 zip 内容。）

#### 32.3.3 两个 `.mjs` 脚本现在还剩什么

结论：**只有“固定 NDK”这一项是必需的** `[已验证]`。

| 脚本动作 | 现在是否必需 | 依据 |
|---|---|---|
| `pickNdk()` 选中完整 NDK 并设 `ANDROID_NDK`（第 33–56 行） | **必需** | A 失败 / B、E、F 成功 |
| 同步 `NDK_HOME`、`ANDROID_NDK_HOME` | 非必需（兼容冗余） | E 只设 `ANDROID_NDK` 即成功 |
| cmake/ninja 加进 PATH、`LIBCLANG_PATH` | 非必需 | E |
| `CC_aarch64_linux_android`、`CXX_*`、`AR_*`、`CARGO_TARGET_*_LINKER` | 非必需 | E |
| `API_LEVEL`、`CMAKE_GENERATOR=Ninja` | 非必需 | E |
| `ensureArm64Only()` 注入 `abiFilters`（第 121–124 行） | 非必需，且会失效 | D 组 + `gen/` 每次可能被重新生成 |
| `clearJniLibs()` 清坏链接（第 72–103 行） | 非必需（防御性） | C：不清理也成功 |
| `clearFolder()` 改名兜底（第 40–54 行） | 非必需（文件被占用时仍有用） | Windows 通用文件语义 |

**为什么 `abiFilters` 注入会失效**：脚本改的是 `src-tauri/gen/android/app/build.gradle.kts`，而 `gen/` 是 Tauri 生成物（被 git 忽略）。`tauri android build` 在需要时会重新生成它，脚本的批注就随旧文件一起消失。

**类比**：在打印出来的纸上做批注。下次重新打印一份，批注就没了。要改模板，就改模板，不是改打印件。

**那脚本还值得留吗？** 值得，但理由变了：它把“唯一必需的一步”固化成代码，省去每台机器手工 `setx`。风险是它同时写死了一堆非必需项，容易让人以为“少一项都不行”——A 组的失败其实只缺一个正确的 `ANDROID_NDK`。

#### 32.3.4 旧脚本代码里仍值得读的三处

1. `pickNdk()` 的过滤条件——把“目录存在 ≠ NDK 可用”写成了代码。
2. `clearFolder()` 的 rename 兜底——文件被占用时不能删、但能改名。这与访问拒绝无关，是 Windows 文件语义的通用技巧 `[通用原理]`。
3. `clearJniLibs()` 只删坏链接——设计意图正确（避免全量重编），只是在本机实验中它不再是“必需步骤”。

#### 32.3.5 一个失败的尝试：把 `libc++_shared.so` 复制进 target

有人会想：既然找不到 `libc++_shared.so`，那就从 NDK 里复制一份到 `target/<triple>/...` 旁边，让链接器就近找到。

实验结果：**无效** `[已验证]`。`cargo-mobile2` 只从 NDK sysroot 建立链接搜索路径，项目内复制的副本不会被采用。正确做法是让 `ANDROID_NDK` 指向完整 NDK（B、E、G 组证明这样 `libc++_shared.so` 会正常链接并被打进 APK）。

**类比**：门禁系统只认它自己数据库里的名单；你在门口贴一张“我也在名单里”的纸，机器不会读。

### 32.4 常见坑与判别方法

#### 32.4.1 四个常见误解

下面四条都是被实验修正过的判断。保留它们，是因为每一个都曾“证据充分”。

##### 误解一：“这是权限问题，用管理员运行”

**为什么看起来成立**：

- 错误码字面就是 `ACCESS_DENIED`；
- 失败点在“创建符号链接”，而 Windows 创建链接确实受策略限制；
- 有人“用管理员跑一次就过了”——那多半是因为同时换了终端或清了目录，或者那次恰好是首次构建。

**反证**：A–G 全在非管理员真实终端完成，B–G 六次成功 `[已验证]`；`os error 5` 只在 AI 命令沙箱出现，真实终端 6 次构建 0 次复现 `[已验证]`。

**处理**：先查 NDK，再查执行环境，最后才考虑权限。

##### 误解二：“两个写入者在抢 `jniLibs`（覆盖冲突）”

**为什么看起来成立**：

- `mergeJniFolders` 名字里有 merge，直觉上像“合并后写回”；
- 确实遇到过“第二次构建失败”，失败点又正好在 `jniLibs`；
- 符号链接覆盖失败确实可能返回 `0x80070005`——这半句是真的，只是不是本项目的主因。

**反证**：C 组增量构建、完全不清理 `jniLibs`，直接覆写健康链接，75s 成功，无 183 `[已验证]`；`mergeJniFolders` 只把 native 目录收集到 intermediates，不回写源码树 `[通用原理]`。

**处理**：不要为了“防冲突”而全删 `jniLibs`——那只会触发全量重编。

##### 误解三：“必须注入 `abiFilters` 才能只出 arm64”

**反证**：D 组去掉注入，APK 仍只有 `arm64-v8a` `[已验证]`。真正限定的是 `--target aarch64`；未指定 target 时，`RustPlugin.kt` 的 universal flavor 会自己加 4 个 ABI。

**副作用**：注入写在生成物上，下次生成即失效——花了力气却留不住。

##### 误解四：“把 NDK 的 `libc++_shared.so` 复制进 target 就能解决”

**反证**：见 32.3.5，`cargo-mobile2` 只从 NDK sysroot 建链 `[已验证]`。

#### 32.4.2 判别流程

```
构建失败
├─ 报 "Android NDK toolchain file not found"
│   └→ echo $env:ANDROID_NDK
│        ├─ 空 / 指向残缺版本 → setx 到完整 NDK → 新终端重跑     （A 型）
│        └─ 已指向完整 NDK → 核对报错里打印的具体路径            （路径拼接错）
├─ 报 os error 5 / 0x80070005 / -2147024891
│   ├─ 当前终端是 AI 命令沙箱？ → 是 → 换真实终端复跑            （假阳性）
│   └─ 否 → 看失败路径：创建 vs 覆盖 → 查链接目标与 SymlinkEvaluation
├─ 报 os error 183
│   └─ 本项目 6 次未复现 → 仍按“目录已存在”处理（删除或改名后重试）
└─ 构建成功但 APK 没有 arm64-v8a
    └→ 先查有没有传 --target aarch64，再查 universal flavor，最后才查 abiFilters
```

#### 32.4.3 常见错误对照

| 现象 | 原因 | 处理 |
|---|---|---|
| `Android NDK toolchain file not found: ...\ndk\30.0.16248370` | 未设 `ANDROID_NDK`，扫描命中残缺的最大版本 | `setx ANDROID_NDK <完整 NDK>`，新终端重跑；判据是 `android.toolchain.cmake` 存在（A 组） |
| `os error 5` / `0x80070005` 只在受管终端出现 | 命令沙箱写限制：重写链接目标、工作区外文件标 restricted | 换真实终端复跑；不要加管理员（B/F 组） |
| 同一命令真实终端 6 次成功、沙箱必失败 | 同上 | 把“执行环境”当作一个变量记录下来，不要改工程 |
| `os error 183`（`ERROR_ALREADY_EXISTS`） | 目录“先删后建”，删除失败后创建时目标仍在 | 本次未复现；仍按目录已存在处理：删除或改名后重试 `[未复核]` |
| `mergeJniFolders` 报 `Duplicate files` | 同一个 `.so` 出现在多个 native 源目录 | 只保留一个来源；确认只传一个 `--target` |
| `abiFilters` 注入后下次构建消失 | `gen/android` 被 Tauri 重新生成 | 不要依赖注入；用 `--target aarch64`（D 组） |
| APK 里没有 `libc++_shared.so` | NDK 不完整，动态 STL 未被正确链接 | 检查 `ANDROID_NDK` 指向；G 组证明完整 NDK 下会打包 |
| 构建成功但安装后跑的是旧库 | Gradle 复用旧 APK | 先删 APK 重打（G 组）；项目文档也记录过 `assembleArm64Debug -x rustBuildArm64Debug` 强制重打包（`[仓库已核实]`，见 `docs/LifeOS_下一步执行计划_v1.3.0.md` §11.6） |

### 32.5 小结

1. `0x80070005` = `HRESULT_FROM_WIN32(5)`，与 Rust 的 `os error 5`、十进制的 `-2147024891` 是同一个“访问被拒”；错误码本身不告诉你原因。
2. 本书旧结论“覆盖冲突 + Gradle 双写入者”已被 A–G 实验推翻 `[已验证]`。真实首因是 NDK 探测顺序命中了残缺的 30.0；`os error 5` 是命令沙箱的假阳性，真实终端未复现。
3. 最小可用方案只有两步：`setx ANDROID_NDK <完整 NDK 路径>`，然后在新终端里 `pnpm tauri android build --target aarch64 --features local-llm`。
4. `jniLibs` 只有一个写入者（tauri-cli）；`mergeJniFolders` 只收集不回写；增量构建可以直接覆写健康链接。
5. ABI 由 `--target aarch64` 决定；`abiFilters` 注入非必需，且会因 `gen/` 重新生成而丢失。

### 32.6 练习题

**第 1 题**：A 组报的是 `toolchain file not found` 而不是 `NDK not found`。这两种措辞差在哪？用一条命令如何确认属于哪一种？

**参考答案要点**：
- 前者：目录找到了，但 `build\cmake\android.toolchain.cmake` 不存在；
- 后者：连 NDK 根目录都没找到；
- 确认：`Test-Path "$env:ANDROID_NDK\build\cmake\android.toolchain.cmake"`；若 `$env:ANDROID_NDK` 为空，再 `Get-ChildItem <SDK>\ndk` 逐个版本检查。

**第 2 题**：旧结论说“第二次构建必失败”，C 组却 75s 成功。如何设计实验区分“环境假阳性”和“真冲突”？

**参考答案要点**：
- 同一命令在两个环境各跑两次：受管终端（沙箱）与真实终端；
- 记录每组的退出码、失败路径、日志位置；
- 若只有沙箱失败 → 环境假阳性，改环境而不是改工程；
- 若真实终端也失败 → 再看失败点是创建还是覆盖、链接目标是否有效；
- 关键是只改变一个变量（执行环境），其余条件固定。

**第 3 题**：CI 机器上明明传了 `--target aarch64`，APK 里却有 4 个 ABI。按什么顺序排查？

**参考答案要点**：
1. 先确认参数真的传到了 CLI（包装脚本是否吞掉/改写了参数，CLI 版本是否不同）；
2. 再查是否用了 universal flavor——未指定 target 时 `RustPlugin.kt` 会自己加 4 个 ABI；
3. 最后才查 `abiFilters` 与 `splits`；
4. 用 `tar -tf <apk> | Select-String "lib/"` 看实际目录，而不是靠猜测。
