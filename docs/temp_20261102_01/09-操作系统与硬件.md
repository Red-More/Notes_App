## 第 33 章 ELF 与 PIE：`DYN` 不等于“动态库”

### 33.1 本章要解决什么问题

`llvm-readelf -h mnn_smoke` 会告诉你：

```
Class:      ELF64
Data:       2's complement, little endian
Type:       DYN (Position-Independent Executable file)
Machine:    AArch64
```

`[历史记录]`（本次产物的头部信息）

很多人看到 `DYN` 就以为“这是动态库”，然后怀疑自己是不是编错了。本章要让你准确读懂 ELF 头部与程序头，分清三件事：

- 这个文件是**可执行文件**还是**共享库**；
- 它是不是 **PIE**（位置无关可执行文件）；
- 它被加载到内存时，分成了哪几段、每段有什么权限。

### 33.2 概念

#### 33.2.1 ELF 是什么

**定义**：ELF（Executable and Linkable Format，可执行与可链接格式）是 Unix 系（含 Android、Linux）使用的二进制文件格式。它不只描述“可执行文件”，也描述目标文件 `.o`、静态库成员、共享库 `.so`、core dump。

**类比**：ELF 是“集装箱的装箱单 + 货物本身”。装箱单告诉你货物分几层、每层装什么、从哪开始；货物是真正的机器码和数据。

**三层结构**：

```
┌─────────────────────────────────────────────┐
│ ELF header（文件头）                          │  ← 我是谁：64 位？ARM64？什么类型？
├─────────────────────────────────────────────┤
│ Program header table（程序头表）               │  ← 加载器看：怎么映射到内存（段）
├─────────────────────────────────────────────┤
│ Section header table（节头表）                 │  ← 链接器/工具看：代码、数据、符号、调试
├─────────────────────────────────────────────┤
│ .text / .rodata / .data / .bss / .symtab ... │  ← 真正的内容
└─────────────────────────────────────────────┘
```

**关键区别**：**程序头（program header）面向运行时**，描述“段”（segment）；**节头（section header）面向链接与调试**，描述“节”（section）。一个段可以包含多个节。

#### 33.2.2 ELF header 的字段逐个读

| 字段 | 本项目取值 | 含义 |
|---|---|---|
| `Class` | `ELF64` | 64 位地址空间 |
| `Data` | `2's complement, little endian` | 小端字节序（ARM64 常用） |
| `Type` | `DYN` | `ET_DYN`：位置无关的映像（**PIE 可执行文件或共享库**） |
| `Machine` | `AArch64` | ARM 64 位 |
| `Entry point address` | 非 0 | 程序入口（通常是 `_start`，不是 `main`） |
| `Number of program headers` | 若干 | 加载器要处理几个段 |
| `Flags` | 架构相关 | ARM64 上常见 `Tag_ABI_VFP_args` 等 |

**`ET_DYN` 为什么容易误会**：

- `ET_EXEC`：固定地址加载（传统可执行文件，Android 不允许）；
- `ET_DYN`：可重定位加载。**共享库**和 **PIE 可执行文件**都用它，因为它们都需要“加载到哪由加载器决定”。
- `ET_REL`：可重定位目标文件（`.o`）。

**怎么区分 PIE 和共享库**（三个判据，任一即可）：

1. **有没有 `PT_INTERP`**：PIE 可执行文件有（指向 `linker64`），共享库没有；
2. **有没有 `_start`/入口点**：PIE 有真正的入口，共享库入口一般为 0；
3. **`.dynamic` 里有没有 `FLAGS_1 PIE`**：PIE 会标记。

```powershell
& "$TOOLS\llvm-readelf.exe" -l .\mnn_smoke | Select-String "INTERP"
& "$TOOLS\llvm-readelf.exe" -h .\mnn_smoke | Select-String "Entry"
& "$TOOLS\llvm-readelf.exe" -d .\mnn_smoke | Select-String "FLAGS"
```

#### 33.2.3 PIE 与 ASLR：为什么 Android 强制 PIE

**定义**：PIE（Position-Independent Executable，位置无关可执行文件）是“可以被加载到任意地址、通过相对寻址访问自身数据”的可执行文件。

**ASLR**（Address Space Layout Randomization，地址空间布局随机化）是操作系统每次启动进程时把代码、栈、堆、库放到随机地址的安全机制。

**关系**：ASLR 对可执行文件生效的前提是 PIE。固定地址的 `ET_EXEC` 无法随机化自己的主映像。

**Android 的时间线（通用知识）**：

- Android 5.0（API 21）起要求 PIE；
- Android 10（API 29）起进一步限制“应用私有目录里的可执行文件”执行（W^X 相关策略），这也解释了第 36 章为什么要把测试程序推到 `/data/local/tmp`。

**类比**：PIE 是“可折叠家具”，进门时按房间大小摆放；`ET_EXEC` 是“整体浇筑的水泥台”，只能放在图纸标注的那个位置。

#### 33.2.4 程序头里的段

`llvm-readelf -l` 会列出 `LOAD`、`DYNAMIC`、`INTERP`、`GNU_STACK`、`GNU_RELRO` 等段：

| 段类型 | 作用 | 关注点 |
|---|---|---|
| `LOAD` | 需要映射到内存的段 | `Align`（页对齐，第 30 章）、`Flg`（R/E、RW） |
| `INTERP` | 指定动态加载器路径 | PIE 可执行文件必备 |
| `DYNAMIC` | 动态链接信息 | 与 `-d` 输出对应 |
| `GNU_STACK` | 栈是否可执行 | 现代系统要求 `RW`（不可执行） |
| `GNU_RELRO` | 只读重定位区 | 安全加固，加载后把部分区域设为只读 |

**代码段与数据段的权限分离**：`LOAD` 段的 `Flg` 为 `R E`（读+执行）的是代码，`RW`（读+写）的是数据。这解释了“为什么不能往代码段写数据”——硬件页表直接禁止。

### 33.3 本项目实例

#### 33.3.1 `mnn_smoke` 的真实形态

历史记录：

```
ELF64 AArch64 DYN
```

`[历史记录]`。它的含义是：

- 64 位；
- ARM64；
- `ET_DYN`，且带 `PT_INTERP` → **PIE 可执行文件**，不是共享库。

佐证：它能被 `adb shell` 直接执行，并且 `NEEDED` 里只有系统库（第 25 章）——共享库不会作为“命令”运行。

#### 33.3.2 一次完整的头部检查

```powershell
& "$TOOLS\llvm-readelf.exe" -h .\mnn_smoke
& "$TOOLS\llvm-readelf.exe" -l .\mnn_smoke | Select-Object -First 30
```

逐参数：

- `-h`：只读 ELF header（最快判断“这是什么”）；
- `-l`：读 program headers（判断“怎么加载”）；
- `Select-Object -First 30`：只取前 30 行，避免输出淹没屏幕。

**判读清单**：

| 你想确认 | 看哪里 | 期望 |
|---|---|---|
| 架构对不对 | `-h` 的 `Machine` | `AArch64` |
| 是不是 PIE | `-h` 的 `Type` + `-l` 的 `INTERP` | `DYN` + 有 INTERP |
| 有没有动态依赖 | `-d` 的 `NEEDED` | 5 个系统库 `[历史记录]` |
| 页对齐 | `-l` 的 `LOAD` `Align` | 16 KB 设备要求 `0x4000` |
| 栈是否可执行 | `-l` 的 `GNU_STACK` | `RW`，不含 `E` |

#### 33.3.3 为什么“PIE”对性能数据没有影响

有人担心 PIE 会拖慢推理。实际上：

- PIE 影响的是**寻址方式**（相对寻址、GOT/PLT 间接跳转），对大规模矩阵运算影响极小；
- 真正的性能决定因素是后端内核（NEON/FP16/量化）与线程数（第 38、39 章）；
- 用 `ET_EXEC` 换来的一点寻址开销，远不足以抵消“Android 不允许安装”的代价。

### 33.4 常见坑与判别方法

| 现象 | 原因 | 处理 |
|---|---|---|
| 看到 `DYN` 就以为编成了 `.so` | `ET_DYN` 同时覆盖 PIE 与共享库 | 查 `INTERP` 与入口点；有 INTERP = PIE |
| `llvm-readelf: ... not an ELF file` | 给的是 `.a` 归档、Windows PE 或文本 | `.a` 用 `llvm-ar t` 展开；PE 用 `dumpbin` |
| 设备上 `Permission denied`（不是 `not found`） | 文件没有执行位，或 SELinux 拒绝 | `ls -l`、`ls -Z`（第 36 章） |
| `cannot execute: required file not found` | `PT_INTERP` 指向的加载器不存在（罕见，通常是拿 x86 产物） | `-l` 看 INTERP 路径；`-h` 看 Machine |
| 安装后崩溃在启动早期 | 段对齐/权限异常 | `-l` 看 LOAD 的 `Align` 与 `Flg` |

### 33.5 小结

1. ELF 有三张表：文件头（身份）、程序头（加载）、节头（链接与调试）。
2. `ET_DYN` 是“位置无关映像”，既可以是 PIE 可执行文件，也可以是共享库；用 `PT_INTERP` 与入口点区分。
3. Android 强制 PIE，所以 `mnn_smoke` 是 `ELF64 AArch64 DYN`，这是**正确**的形态。
4. `LOAD` 段决定内存权限与页对齐；16 KB 设备看 `Align` 是否 `0x4000`。
5. 判断二进制“能不能跑”，顺序是：架构 → 类型/PIE → 依赖 → 权限 → 对齐。

### 33.6 练习题

**第 1 题**：一个文件 `Type` 是 `DYN`、没有 `PT_INTERP`、入口点为 0。它最可能是什么？能直接执行吗？

**参考答案要点**：
- 共享库（`.so`）；
- 不能作为命令直接执行（没有入口），只能被加载；
- 验证：`-d` 看 `SONAME`；`-s` 看有没有 `_start`。

**第 2 题**：为什么“把可执行文件改成 `ET_EXEC`”在 Android 上行不通？

**参考答案要点**：
- Android 自 API 21 起要求 PIE；
- `ET_EXEC` 无法参与 ASLR，且加载器/系统校验会拒绝；
- 实际表现可能是安装失败或运行被拒。

**第 3 题**：给出命令，判断一个 ARM64 可执行文件的栈是否可执行，并解释为什么这很重要。

**参考答案要点**：
```powershell
& "$TOOLS\llvm-readelf.exe" -l .\mnn_smoke | Select-String "GNU_STACK"
```
- 期望 `Flg` 为 `RW`（无 `E`）；可执行栈是老式漏洞利用的温床，现代系统默认禁止；
- 若出现 `RWE`，说明链接参数有问题（例如显式 `-z execstack`），应修正。

## 第 34 章 动态库加载与 `LD_LIBRARY_PATH`

### 34.1 本章要解决什么问题

程序启动的第一毫秒，Android 的 `linker64` 就开始工作。它要回答一个问题：**这个可执行文件声明的依赖，分别在哪里？**

答不上来，你的程序会停在“还没进 `main`”的地方，甚至连一行日志都来不及打。

本章要讲清：

- `DT_NEEDED` 是什么，谁写的；
- 加载器的搜索顺序；
- `LD_LIBRARY_PATH` 在什么场景下有效、什么场景下无效；
- 为什么本项目的静态产物其实不需要它，但历史上仍然写了 `LD_LIBRARY_PATH=.`。

### 34.2 概念

#### 34.2.1 `DT_NEEDED`：依赖清单

**定义**：`.dynamic` 段里的一系列 `DT_NEEDED` 条目，每个记录一个“我需要的共享库名字”（通常是 `SONAME`，不是完整路径）。

**类比**：`DT_NEEDED` 是餐厅的采购清单，写的是“需要 5 公斤面粉”，不是“去某某仓库 3 号货架拿”。

**谁写的**：链接器。你在命令行写 `-lfoo`，链接器把 `libfoo.so` 的 `SONAME` 写进 `DT_NEEDED`。

#### 34.2.2 `SONAME`：库的“身份证名”

**定义**：`SONAME` 是共享库自报的名字（`DT_SONAME`），通常是 `libfoo.so.1` 这种带版本号的形式。加载器按 `SONAME` 匹配 `DT_NEEDED`。

**常见错误**：库没设 `SONAME`，链接器就把**路径**写进 `DT_NEEDED`。产物换台机器就找不到库。

#### 34.2.3 搜索顺序（Android/bionic 的简化模型）

```
① DT_RPATH / DT_RUNPATH（如果存在，且未被禁用）
② LD_LIBRARY_PATH 指定的目录（仅对"不受命名空间限制"的进程有效）
③ 应用的 native 库目录（APK 内 lib/<abi>/，由加载器按命名空间提供）
④ 系统目录：/system/lib64、/vendor/lib64 等
```

**关键限制**：Android 7 起引入 **linker namespace**（链接器命名空间）。普通应用的加载器只允许在“自己的命名空间”里找库（APK 内的 native 库 + 部分系统库），`LD_LIBRARY_PATH` 对应用进程**基本无效**。

**这就解释了一个常见困惑**：`adb shell` 里跑的程序能用 `LD_LIBRARY_PATH=.`，装进 APK 的应用不能。因为前者是 shell 进程（不受应用命名空间约束），后者受。

#### 34.2.4 静态产物为什么也可能有 `NEEDED`

完全静态（`-static`）的程序没有 `PT_INTERP`，也没有 `DT_NEEDED`。但本项目的 `mnn_smoke` **不是**完全静态：

- MNN 是静态链接进来的；
- 但 C/C++ 运行时、日志库等仍然动态依赖系统库（`libc.so`、`liblog.so`、`libm.so`、`libdl.so`，以及记录中的 `libc++_shared.so`）。

**术语澄清**：“静态链接”通常指“第三方库以 `.a` 形式合并”，不等于“完全静态（无任何动态依赖）”。两者要分开说。

### 34.3 本项目实例

#### 34.3.1 依赖清单

```powershell
& "$TOOLS\llvm-readelf.exe" -d .\mnn_smoke | Select-String "NEEDED|SONAME|RPATH|RUNPATH"
```

历史记录结果：`libc++_shared.so`、`liblog.so`、`libc.so`、`libdl.so`、`libm.so` `[历史记录]`。

**解读**：

- 这五个都是“系统或随包提供”的库，设备上必然存在（`libc++_shared.so` 需随 APK 提供，见第 26 章）；
- 没有 `libMNN.so` → 静态链接成功；
- 没有 `RPATH`/`RUNPATH` → 加载器只按默认规则找，不依赖构建机路径。

#### 34.3.2 真机上的运行方式

历史流程是：

```powershell
adb push .\mnn_smoke /data/local/tmp/mnn/
adb push .\Qwen3-0.6B-MNN /data/local/tmp/mnn/
adb shell "cd /data/local/tmp/mnn && chmod 755 mnn_smoke && LD_LIBRARY_PATH=. ./mnn_smoke ./Qwen3-0.6B-MNN '用一句话介绍你自己。' 128 4"
```

（`[历史记录]`，命令形式按当时流程还原；模型体积约 433 MB）

逐段解释：

| 片段 | 作用 |
|---|---|
| `cd /data/local/tmp/mnn` | 切到工作目录；后续的相对路径都基于它 |
| `chmod 755 mnn_smoke` | 加执行位（`adb push` 不一定保留源文件权限） |
| `LD_LIBRARY_PATH=.` | 让加载器优先在当前目录找 `.so`；对静态产物不是必需，但可兜底临时依赖 |
| `./mnn_smoke` | 执行；`./` 不能省，当前目录不在 `PATH` 里 |
| `./Qwen3-0.6B-MNN` | 第一个参数：模型 bundle 目录（内含 `config.json`） |
| `'用一句话介绍你自己。'` | 第二个参数：prompt |
| `128` | 第三个参数：`max_tokens` |
| `4` | 第四个参数：线程数 |

这些参数与 `examples/mnn_smoke.rs` 的解析逻辑完全对应（`[仓库已核实]`，见 [mnn_smoke.rs](file:///C:/Users/16412/Documents/Github_Repositories/Notes_App-mnn-engine/src-tauri/examples/mnn_smoke.rs#L12-L22)）：缺省 prompt 是“用一句话介绍你自己。”，缺省 `max_tokens=128`，缺省 `threads=4`。

#### 34.3.3 `LD_LIBRARY_PATH` 什么时候真的有用

| 场景 | 是否有效 | 原因 |
|---|---|---|
| `adb shell` 直接跑 `/data/local/tmp` 里的程序 | 有效 | shell 进程的命名空间允许 |
| APK 内的应用进程 | **基本无效** | linker namespace 限制 |
| 用 `run-as` 跑应用私有目录的程序 | 通常无效/被拒 | 应用域 + W^X 限制（第 36 章） |
| 宿主 Linux 上跑 | 有效 | 无 Android 命名空间 |

**结论**：不要用 `LD_LIBRARY_PATH` 去解决 APK 内的加载失败。APK 内正确的做法是“把 `.so` 放进 `jniLibs/<abi>/`，让加载器在命名空间内找到它”。

#### 34.3.4 加载失败时的排查顺序

```
程序起不来
  ├─ 有日志吗？
  │   ├─ 无任何输出 → 加载阶段失败（依赖/对齐/权限）
  │   └─ 有 Rust panic → 进入 main 了，是逻辑问题
  ├─ adb shell 直接跑：报什么？
  │   ├─ "not found" → 文件不存在，或 PT_INTERP 缺失
  │   ├─ "Permission denied" → 执行位/SELinux
  │   ├─ "cannot link executable" / "library ... not found" → NEEDED 缺失
  │   └─ "cannot locate symbol" → 依赖存在但符号版本不对
  └─ logcat 有用信息吗？
      └─ debuggerd / linker 会打印具体库名与搜索路径
```

### 34.4 常见坑与判别方法

| 错误信息 | 原因 | 处理 |
|---|---|---|
| `error: library "libc++_shared.so" not found` | APK 未打包该库，或 ABI 目录不对 | 解包 APK 检查 `lib/arm64-v8a/`；第 26 章 |
| `cannot locate symbol "__android_log_print"` | 没链 `liblog`，或 API level 太低 | 检查 `-llog`；确认 API 一致 |
| `CANNOT LINK EXECUTABLE ...: library "libMNN.so" not found` | 动态方案下 `.so` 没推上去/没进 APK | `adb shell ls /data/local/tmp/mnn`；APK 解包 |
| `dlopen failed: ... is 32-bit instead of 64-bit` | 混了 32 位库 | `-h` 看 Class；清理旧的 `armeabi-v7a` 目录 |
| `loaded ... but ... has text relocations` | 老式不可重定位代码 | 重编（现代工具链默认 PIE/ PIC） |
| 改了 `.so` 但行为没变 | 加载的是另一份同名库（系统目录/APK 内） | `logcat` 里 linker 会打印实际加载路径 |

### 34.5 小结

1. `DT_NEEDED` 是链接器写进 `.dynamic` 的依赖清单，记录的是 `SONAME`，不是路径。
2. Android 的加载器受 linker namespace 约束；`LD_LIBRARY_PATH` 只对 shell 等不受限进程有效。
3. “静态链接第三方库”不等于“没有动态依赖”；本项目的 `mnn_smoke` 仍依赖 5 个系统库。
4. 加载失败的排查顺序是：文件存在 → 执行权限 → 依赖齐全 → 符号版本 → 页对齐。
5. 真机实验用 `/data/local/tmp` + `LD_LIBRARY_PATH=.` 是合理的；但不要把这套做法套到 APK 内。

### 34.6 练习题

**第 1 题**：一个 `.so` 没有 `SONAME`，链接进程序后 `NEEDED` 里会出现什么？会带来什么问题？

**参考答案要点**：
- 链接器会退而记录**路径**（或文件名），而不是稳定的 `SONAME`；
- 换目录/换机器后加载器按路径找不到；
- 修复：构建 `.so` 时加 `-Wl,-soname,libfoo.so`。

**第 2 题**：为什么 `adb shell` 能跑 `/data/local/tmp` 里的程序，而应用进程不能跑同一路径的文件？

**参考答案要点**：
- shell 进程的 uid/域（shell）与 SELinux 域允许读/执行该目录；
- 应用进程是 `untrusted_app` 域，私有数据目录外的路径不可访问；
- Android 10+ 还限制应用执行可写目录里的文件（W^X）。

**第 3 题**：写出两条命令，分别确认“程序依赖哪些库”和“设备上实际加载了哪个路径的库”。

**参考答案要点**：
```powershell
& "$TOOLS\llvm-readelf.exe" -d .\mnn_smoke | Select-String "NEEDED"
adb logcat -d | Select-String "linker|dlopen"
```
- 前者看清单，后者看运行时实际路径（需要程序刚启动过，日志还在缓冲区）。

## 第 35 章 Android 沙箱与路径：`/data/user/0/<pkg>` vs `/data/local/tmp`

### 35.1 本章要解决什么问题

同一台手机上，同一个文件放在两个目录，一个能读、一个不能；一个能执行、一个不能。不了解 Android 的目录模型，你会把“权限问题”误判成“代码问题”。

本章要让你能回答：

- 应用的“私有目录”到底在哪，谁有权限？
- `app_data_dir()` 返回的路径在 Android 上映射到哪里？
- 为什么模型要放在应用的私有目录，而测试程序要放在 `/data/local/tmp`？
- `run-as` 能做什么、不能做什么？

### 35.2 概念

#### 35.2.1 每个应用一个 uid

**定义**：Android 在安装应用时给它分配一个**独立的 Linux 用户 ID**（uid），并为其创建一个私有数据目录。

**类比**：每个应用是一个独立的合租房间，房门钥匙（uid）只有它自己和服务管理方有。

**目录结构（简化）**：

```
/data/
├─ app/                              ← APK 的安装位置（只读）
│  └─ <pkg>-<随机后缀>/
│     ├─ base.apk
│     └─ lib/arm64/                  ← native 库（由包管理器释放）
├─ user/0/                           ← 用户 0（绝大多数单用户设备）的"用户空间"
│  └─ <pkg>/                         ← 应用私有数据目录（app_data_dir）
│     ├─ files/
│     ├─ cache/
│     └─ ...（应用自建子目录，如 models/）
└─ local/
   └─ tmp/                           ← shell 的临时目录，不属于任何应用
```

**`/data/data` 与 `/data/user/0`**：`/data/data` 在多数设备上是指向 `/data/user/0` 的符号链接。两者通常等价，但脚本里写 `/data/user/0` 更明确（多用户设备上会有 `/data/user/10` 等）。

#### 35.2.2 `app_data_dir()` 的映射

**定义**：Tauri 的 `app_data_dir()` 返回“应用私有数据目录”。在 Android 上，它直接映射到 `/data/user/0/<package>`，**不拼 `identifier` 子目录**。

**这一点与桌面不同**：桌面上 `app_data_dir()` 通常返回 `~/.local/share/<identifier>` 或 `%APPDATA%\<identifier>`；Android 上包名本身就是唯一标识，所以没有额外的 `identifier` 层。

**本项目的实际用法**：

```rust
let mnn_root = app.path().app_data_dir()?.join("models").join("mnn");
app.manage(agent::local_mnn::LocalMnnState::new(mnn_root));
```

（`[仓库已核实]`，见 [lib.rs](file:///C:/Users/16412/Documents/Github_Repositories/Notes_App-mnn-engine/src-tauri/src/lib.rs#L63-L65)）

所以模型根目录在设备上是：

```
/data/user/0/com.mynotes.desktop/models/mnn/          ← release 包
/data/user/0/com.mynotes.desktop.debug/models/mnn/    ← debug 包（applicationIdSuffix=".debug"）
```

包名依据：`tauri.conf.json` 的 `identifier` 为 `com.mynotes.desktop`，`bundle.android.debugApplicationIdSuffix` 为 `.debug`（`[仓库已核实]`，见 [tauri.conf.json](file:///C:/Users/16412/Documents/Github_Repositories/Notes_App-mnn-engine/src-tauri/tauri.conf.json#L5-L5) 与第 43–45 行）。

**一个常见错误**：把模型推到 `/data/user/0/<pkg>/models/mnn` 却忘了 debug 包用的是 `.debug` 后缀，于是应用始终“看不到模型”。

#### 35.2.3 `/data/local/tmp` 是什么

**定义**：`/data/local/tmp` 是 `adb shell`（uid 2000，shell 用户）可读写的临时目录。它不属于任何应用，也没有应用沙箱保护。

**特点**：

- 权限通常是 `0771`，属主 `shell`；
- `adb push` 可以直接写；
- 里面的可执行文件在 `adb shell` 下可以运行；
- 重启后可能被清理（不保证持久）。

**类比**：应用私有目录是“你家”，`/data/local/tmp` 是“公共工作台”。工具放在工作台上用，成品放进家里。

#### 35.2.4 三条路径的权限对比

| 路径 | 谁能读 | 谁能写 | 谁能执行 |
|---|---|---|---|
| `/data/user/0/<pkg>/` | 该应用（及其 `run-as`） | 该应用 | 受限（API 29+ 基本禁止执行应用可写目录） |
| `/data/app/<pkg>-.../lib/arm64/` | 该应用 | 包管理器（安装时） | 该应用（但这属于“已安装 native 库”） |
| `/data/local/tmp/` | shell | shell | shell 可执行 |

这张表解释了第 34 章的核心矛盾：**“能推上去”与“能执行”是两件事**。

### 35.3 本项目实例

#### 35.3.1 两条完全不同的部署路径

```
路径 A：应用内（给 Tauri 前端用）
  模型目录 → 应用私有目录 /data/user/0/<pkg>/models/mnn/<bundle>/
  访问方式 → Rust 代码调用 app_data_dir()，前端通过 Tauri 命令触发
  优点 → 受沙箱保护，用户数据不裸露
  缺点 → adb 不能直接写（需要 run-as 或应用内导入）

路径 B：真机实验（给 mnn_smoke 用）
  可执行文件 + 模型 → /data/local/tmp/mnn/
  访问方式 → adb shell 直接运行
  优点 → 迭代快，不依赖应用安装/打包
  缺点 → 不受保护，重启可能丢；不能当作产品形态
```

**为什么实验不直接把 `mnn_smoke` 放进应用私有目录**：

1. `adb push` 默认写不进 `/data/user/0/<pkg>`（权限不足），需要 `run-as` + 管道，麻烦且易错；
2. 即使推得进去，Android 10+ 对“应用可写目录中的可执行文件”有执行限制（W^X），大概率 `Permission denied`；
3. `/data/local/tmp` 是 shell 域，执行模型简单，适合做“引擎是否可用”的隔离验证。

#### 35.3.2 模型怎么进应用私有目录

三种常见方式（本项目采用哪一种取决于是否有导入 UI）：

| 方式 | 做法 | 适用 |
|---|---|---|
| `run-as` + `cat` | `adb shell "run-as <pkg> sh -c 'cat > files/model.bin'" < local.bin` | 调试、单文件 |
| 应用内导入 | 前端选文件 → Tauri 命令复制到 `app_data_dir()` | 正式产品 |
| `adb push` 到 `/data/local/tmp` 再 `run-as` 复制 | 两步 | 大目录（如 433 MB 的模型 bundle） |

**大目录的现实问题**：433 MB 的模型通过 `run-as` 管道复制很慢，而且 `run-as` 的子进程能力有限。工程上更常见的是“先在 `/data/local/tmp` 放好，再用一条 `run-as` 的 `cp -r`”。是否可行取决于设备与 `run-as` 的实现，属于**需要在目标设备上验证**的项，本项目没有留存这条命令的执行记录 `[未复核]`。

**验证方法**：

```powershell
# 看应用私有目录里到底有什么
adb shell run-as com.mynotes.desktop ls -l /data/user/0/com.mynotes.desktop/models/mnn

# 看 debug 包（注意 .debug 后缀）
adb shell run-as com.mynotes.desktop.debug ls -l /data/user/0/com.mynotes.desktop.debug/models/mnn
```

`run-as` 的作用是“以该应用的 uid 身份执行一条命令”，因此能绕过“adb shell 无法读应用目录”的限制。它只对 **debuggable 应用**有效（release 包通常不行），这是它的硬限制。

#### 35.3.3 项目代码里的路径安全

`LocalMnnState::resolve_bundle()` 只接受“目录名”，拒绝包含 `/`、`\`、以 `.` 开头的名字：

```rust
!trimmed.starts_with('.') && !trimmed.contains(['/', '\\'])
```

（`[仓库已核实]`，见 [local_mnn/mod.rs](file:///C:/Users/16412/Documents/Github_Repositories/Notes_App-mnn-engine/src-tauri/src/agent/local_mnn/mod.rs#L62-L72)）

**为什么这与本章有关**：即使沙箱保护了目录，应用内部仍要防止“用户传一个 `../../` 的模型名把路径逃逸到别处”。沙箱是外层防线，路径校验是内层防线，两者不替代。

### 35.4 常见坑与判别方法

| 现象 | 原因 | 排查路径 |
|---|---|---|
| `adb push` 到 `/data/user/0/<pkg>/` 报 `Permission denied` | shell uid 无权写应用目录 | 用 `run-as`；或先推 `/data/local/tmp` |
| 应用提示“模型不存在”，但文件明明在 | 包名后缀（`.debug`）搞错；或目录层级不对（少 `models/mnn`） | `run-as <正确包名> ls -l` |
| `run-as: package not debuggable` | release 包 | 用 debug 包；或用应用内导入 |
| 文件在 `/data/local/tmp` 里，应用读不到 | 跨沙箱 | 设计导入流程，而不是让应用直接读 tmp |
| `adb shell` 里 `ls /data/data` 被拒 | shell 无权遍历其他 uid 目录 | 正常现象；用 `run-as` 或 root |
| 重启后 tmp 里的文件消失 | `/data/local/tmp` 不保证持久 | 重新 push；或改用应用私有目录 |

### 35.5 小结

1. Android 每个应用一个 uid、一个私有目录；`/data/user/0/<pkg>` 就是它。
2. Tauri 的 `app_data_dir()` 在 Android 上直接映射到该目录，不拼 identifier；本项目模型根是 `.../models/mnn`。
3. `/data/local/tmp` 属于 shell，不属于任何应用；它适合“实验”，不适合“产品数据”。
4. debug 包与 release 包目录不同（`.debug` 后缀），这是最常见的“文件明明在”的假象来源。
5. 沙箱之外还要有路径校验；`resolve_bundle()` 就是内层防线。

### 35.6 练习题

**第 1 题**：为什么把 433 MB 的模型用 `adb push` 推到 `/data/user/0/<pkg>/` 会失败，而推到 `/data/local/tmp` 不会？

**参考答案要点**：
- 前者属主是该应用 uid，shell 没有写权限；
- 后者属主是 shell（0771），adb push 以 shell 身份运行；
- 解决：`run-as` 复制，或应用内导入。

**第 2 题**：`app_data_dir()` 在桌面与 Android 上的返回值有什么结构性差异？这会影响什么代码？

**参考答案要点**：
- 桌面上是“用户数据根 + identifier”；Android 上是“`/data/user/0/<pkg>`”，包名已含标识；
- 影响“路径拼接假设”：若代码手动拼 `identifier` 子目录，Android 上会多一层，导致找不到文件；
- 正确做法：只依赖 `app_data_dir()` 的返回值，不再拼 identifier。

**第 3 题**：写出命令，确认 debug 包里的模型目录是否存在、模型 bundle 有多大。

**参考答案要点**：
```powershell

adb shell run-as com.mynotes.desktop.debug du -sh /data/user/0/com.mynotes.desktop.debug/models/mnn
```
- `run-as` 只对 debuggable 包有效；
- `du -sh` 给人类可读总量。

## 第 36 章 uid 与 SELinux：能读、能写、不能执行

### 36.1 本章要解决什么问题

你已经把文件推到 `/data/local/tmp/mnn`，`ls` 能看到，`cat` 能读，但执行时报 `Permission denied`。文件权限是 `755`，用户也是自己，为什么还不行？

答案通常在 **SELinux**，而不是传统 Unix 权限。本章要让你能：

- 分清 uid/gid（传统权限）与 SELinux 标签（强制访问控制）；
- 用 `ls -Z` 看标签，用 `logcat`/`dmesg` 找 `avc: denied`；
- 判断“执行失败”到底是权限位、挂载选项，还是 SELinux 域。

### 36.2 概念

#### 36.2.1 传统 Unix 权限：三个数字

`ls -l` 的 `-rwxr-xr-x` 是“属主/属组/其他人”的读、写、执行位。`chmod 755` 就是给所有人执行权。

**类比**：这是“房门钥匙”——你有没有这把钥匙。

#### 36.2.2 SELinux：门卫的名单

**定义**：SELinux（Security-Enhanced Linux）是 Linux 内核的强制访问控制（MAC）机制。每个进程有一个**域**（domain），每个文件有一个**标签**（label），策略规定“哪个域能以什么方式访问哪个标签”。

**类比**：即使你有钥匙，门卫还要查名单：“你是外卖员，这栋楼只允许你把东西放前台，不许进电梯。”

**查看方式**：

```powershell
adb shell ls -Z /data/local/tmp/mnn
```

输出形如：

```
u:object_r:shell_data_file:s0  mnn_smoke
```

各部分：

- `u`：用户（SELinux user）；
- `object_r`：角色；
- `shell_data_file`：**类型**（最关键）；
- `s0`：级别（MLS/MCS）。

进程的域可以从 `ps -Z` 看：

```powershell
adb shell ps -Z | Select-String "mnn_smoke|shell"
```

应用进程的域通常是 `untrusted_app`（可能带 `c` 分类，如 `untrusted_app_27`）。

#### 36.2.3 为什么“应用不能执行自己的文件”

Android 10（API 29）起，对“应用可写目录中的可执行文件”施加限制（常被概括为 W^X 策略的一部分）。含义：

- 应用可以把数据写进私有目录；
- 但**不能**从该目录执行代码（防止动态下发可执行代码绕过商店审核）。

**这就解释了**：

- `mnn_smoke` 必须放在 `/data/local/tmp`（shell 域），由 `adb shell` 执行；
- 你也不能指望“把 `mnn_smoke` 塞进 APK 的 assets，运行时释放到 files/ 再执行”——大概率被拒；
- 正确形态是：**引擎编译成 `.so` 随 APK 打包**（第 26、27 章），**测试程序留在 tmp**。

#### 36.2.4 `avc: denied` 怎么读

SELinux 拒绝时，内核审计日志会打印：

```
avc: denied { execute } for pid=1234 comm="mnn_smoke" name="mnn_smoke"
  dev="dm-3" ino=... scontext=u:r:shell:s0 tcontext=u:object_r:shell_data_file:s0 tclass=file
```

读法：

- `{ execute }`：被拒的操作；
- `scontext`：发起方域（`shell`）；
- `tcontext`：目标标签（`shell_data_file`）；
- `tclass`：目标类型（`file`）。

**排查命令**：

```powershell
adb logcat -d | Select-String "avc: denied"
adb shell dmesg | Select-String "avc"      # 部分设备需要 root 才能读 dmesg
```

如果 `avc: denied` 里出现你的文件名，基本可以确定是 SELinux；如果没有，先查权限位与文件系统挂载（`/data` 可能是 `noexec`？在 Android 上 `/data/local/tmp` 通常允许执行，但仍以实测为准）。

### 36.3 本项目实例

#### 36.3.1 为什么用 `/data/local/tmp` 而不是应用目录

历史流程把 `mnn_smoke` 推到 `/data/local/tmp/mnn` 并用 `LD_LIBRARY_PATH=.` 启动 `[历史记录]`。这个选择的三个理由：

1. **域匹配**：`adb shell` 的域允许执行 `shell_data_file` 标签的文件；
2. **避开 W^X**：应用私有目录的可执行限制不适用；
3. **迭代快**：不需要重装 APK。

#### 36.3.2 一次“执行失败”的完整判别流程

```
./mnn_smoke: Permission denied
  ├─ ls -l → 有 x 位吗？
  │    └─ 没有 → chmod 755（或 700）
  ├─ ls -Z → 标签是什么？
  │    ├─ shell_data_file → 正常（shell 可执行）
  │    └─ 其他标签 → 可能是复制方式导致标签继承错
  ├─ mount | Select-String "/data" → 是否 noexec？
  │    └─ 是 → 换目录（少见）
  └─ logcat 有 avc: denied 吗？
       ├─ 有 → SELinux 域/标签问题
       └─ 无 → 回到权限位与文件完整性（是否 0 字节、是否被截断）
```

**一个容易忽略的点**：`adb push` 后文件的 SELinux 标签由目标目录决定（类型继承），一般没问题；但如果用 `run-as` 复制到应用目录，标签会变成应用的私有标签，之后从 shell 执行就会被拒。

#### 36.3.3 与应用内 `.so` 的对比

| 形态 | 文件位置 | 标签/域 | 能否执行 |
|---|---|---|---|
| `mnn_smoke`（实验） | `/data/local/tmp/mnn/` | `shell_data_file` / `shell` | 能（adb shell 下） |
| `libapp_lib.so`（产品） | APK 内 `lib/arm64-v8a/`，安装后 `/data/app/.../lib/arm64/` | 系统管理的 native 库标签 / `untrusted_app` | 能（由加载器加载，不是 exec） |
| 释放到 `files/` 的可执行文件 | `/data/user/0/<pkg>/files/` | 应用私有标签 / `untrusted_app` | 通常不能（W^X） |

### 36.4 常见坑与判别方法

| 现象 | 原因 | 处理 |
|---|---|---|
| `chmod 755` 后仍 `Permission denied` | SELinux 拒绝，或目录 noexec | `logcat` 找 `avc: denied`；`ls -Z` 看标签 |
| `run-as` 里能读，shell 里不能执行 | 标签/域不匹配 | 不要在应用目录里放实验程序；回到 tmp |
| `avc: denied { read }` 但文件可读 | 应用域访问了不属于自己的标签 | 让文件进入 `app_data_dir()`，不要跨域访问 |
| 安装后 `.so` 加载失败且无 avc 记录 | 依赖缺失或对齐问题 | 回到第 34 章 |
| 复制文件后标签异常 | `cp` 到不同目录会继承目标目录标签 | 用 `adb push`（目标目录决定标签），而非跨域 `cp` |

### 36.5 小结

1. uid/gid 决定“有没有钥匙”，SELinux 决定“门卫让不让进”。
2. `ls -Z` 看文件标签，`ps -Z` 看进程域，`avc: denied` 是判定 SELinux 的直接证据。
3. Android 10+ 限制应用执行自己可写目录里的文件，所以测试程序必须放 `/data/local/tmp`。
4. 产品形态应当是“`.so` 随 APK 打包”，而不是“运行时释放可执行文件”。
5. 排查顺序：权限位 → 挂载选项 → SELinux → 文件完整性。

### 36.6 练习题

**第 1 题**：`ls -l` 显示 `-rwxr-xr-x`，`ls -Z` 显示 `u:object_r:app_data_file:s0`，你在 shell 里执行它，会发生什么？为什么？

**参考答案要点**：
- 大概率 `Permission denied`；
- shell 域没有权限执行 `app_data_file` 标签；
- 同时应用可写目录受 W^X 限制；
- 结论：权限位“看起来够”，但 MAC 策略不允许。

**第 2 题**：`avc: denied` 一条记录里，`scontext` 与 `tcontext` 分别代表什么？如何据此判断是谁被拒？

**参考答案要点**：
- `scontext`：发起访问的进程域；
- `tcontext`：被访问对象的标签；
- 若 `scontext` 是 `untrusted_app`，说明是应用被拒（应用试图访问不该访问的标签）；若是 `shell`，说明是 shell 被拒。

**第 3 题**：如果必须让应用在运行时使用一个“外部下载的 `.so`”，Android 的约束是什么？给出合规思路。

**参考答案要点**：
- 应用不能从可写目录 `dlopen`/执行任意代码（W^X + 商店政策）；
- 合规做法是把 native 库随 APK 打包（`jniLibs`），或使用系统允许的插件机制；
- 模型文件（数据）可以下载，代码（可执行）不可以动态下发——这是边界。

## 第 37 章 adb 工作流：从推送到看到输出

### 37.1 本章要解决什么问题

`adb` 是连接“你的电脑”和“那台手机”的唯一常用通道。它有一堆子命令，每个解决不同问题。本章按一次真实实验的顺序，把命令串起来，并逐个解释参数：

```
确认设备 → 建目录 → 推文件 → 设权限 → 执行 → 看日志 → 取回产物 → 清理
```

### 37.2 概念：adb 是什么

**定义**：adb（Android Debug Bridge）是一个客户端-服务端-守护进程三件套：

- **client**：你在终端敲的 `adb` 命令；
- **server**：电脑上的后台进程（默认端口 5037），负责与设备通信；
- **daemon（adbd）**：设备上的守护进程，以 shell 身份执行你发过去的命令。

**类比**：adb 是一部对讲机。你说话（client），中继站转发（server），对面的人执行（adbd）。

**关键含义**：`adb shell` 里的命令以 **shell 用户（uid 2000）** 运行，不是 root，也不是你的应用。这决定了上一章的所有权限结论。

### 37.3 本项目实例：一次完整的真机实验

#### 37.3.1 第 1 步：确认设备在线

```powershell
adb devices -l
```

- `devices`：列出已连接设备；
- `-l`：显示详细信息（型号、传输方式、设备名）。

正常输出：

```
List of devices attached
<序列号>   device product:... model:... device:... transport_id:1
```

若显示 `unauthorized`：在手机上点“允许 USB 调试”。若显示 `offline`：`adb kill-server` 后重试，或换线。

**本项目的目标设备**：Redmi 22101317C（sunstone），Android 14，arm64-v8a `[仓库已核实]`（见 `docs/LifeOS_下一步执行计划_v1.3.0.md` §11.6）。当前设备是否在线取决于你的环境；历史运行时设备已离线，运行时数字因此未复核。

#### 37.3.2 第 2 步：建工作目录

```powershell
adb shell mkdir -p /data/local/tmp/mnn
```

- `shell`：在设备上执行一条命令；
- `mkdir -p`：目录不存在就建，已存在不报错。

#### 37.3.3 第 3 步：推送可执行文件与模型

```powershell
adb push .\mnn_smoke /data/local/tmp/mnn/
adb push .\Qwen3-0.6B-MNN /data/local/tmp/mnn/
```

- `push`：本地 → 设备；
- 第一个参数：本地路径；
- 第二个参数：设备路径（以 `/` 开头，相对于设备根）。

**注意**：

- 目录推送是递归的，433 MB 的模型会明显耗时；
- 传输中断会留下半个目录，重推前先 `ls`/`du` 确认；
- `adb push` 不会保留可执行位（多数版本），下一步必须 `chmod`。

**验证**：

```powershell
adb shell "du -sh /data/local/tmp/mnn/Qwen3-0.6B-MNN"
adb shell "ls -l /data/local/tmp/mnn"
```

`du -sh` 的第一列是“人类可读大小”，与本地模型体积（约 433 MB）对比，可快速判断是否传完整。

#### 37.3.4 第 4 步：设权限

```powershell
adb shell "chmod 755 /data/local/tmp/mnn/mnn_smoke"
```

- `755`：属主读/写/执行，其他读/执行；
- 对实验程序，`700` 也够（只有 shell 用）；`755` 更直观。

#### 37.3.5 第 5 步：执行

```powershell
adb shell "cd /data/local/tmp/mnn && LD_LIBRARY_PATH=. ./mnn_smoke ./Qwen3-0.6B-MNN '用一句话介绍你自己。' 128 4"
```

参数见第 34.3.2 节。**注意 PowerShell 的引号**：

- 外层双引号包住整条设备命令；
- prompt 里有中文和句号，用单引号包住，避免被 shell 拆分；
- 如果 prompt 里有单引号，需要转义（Android shell 是 `sh`，转义规则与 bash 类似）。

#### 37.3.6 第 6 步：看日志

```powershell
adb logcat -d -s "mnn_smoke:*" "DEBUG:*"
```

- `-d`：dump 当前缓冲区后退出（不加会一直刷）；
- `-s`：只显示指定 tag（`tag:级别`）；
- `"mnn_smoke:*"`：这个 tag 的所有级别。

**更实用的做法**：先拿到 pid，再按 pid 过滤：

```powershell
adb shell "pidof mnn_smoke"
adb logcat -d --pid=<pid>
```

- `pidof`：查进程号；
- `--pid`：只显示该进程日志（Android 7+ 支持）。

**本项目产物的输出格式**（来自源码，`[仓库已核实]`）：

```
summary load_ms=... chunks=... first_chunk_ms=... total_ms=...
perf prompt_tokens=... output_tokens=... prefill_ms=... decode_ms=... sample_ms=... load_us=... decode_tok_s=...
```

（见 [mnn_smoke.rs](file:///C:/Users/16412/Documents/Github_Repositories/Notes_App-mnn-engine/src-tauri/examples/mnn_smoke.rs#L56-L80)）

**历史运行时数值**：`load 1385 ms`、首 chunk `252 ms`、decode `≈16.7 tok/s` `[历史记录]`，无日志留存、设备离线，**未复核**。引用时必须带上这个限定。

#### 37.3.7 第 7 步：取回产物（如果需要）

```powershell
adb pull /data/local/tmp/mnn/out.txt .\out.txt
```

- `pull`：设备 → 本地；
- 第一个参数：设备路径；第二个：本地目标。

#### 37.3.8 第 8 步：清理

```powershell
adb shell "rm -rf /data/local/tmp/mnn"
```

- `rm -rf`：递归强制删除；这是破坏性操作，确认路径后再执行。

### 37.4 其他常用子命令

| 命令 | 作用 | 注意 |

### 37.5 常见坑与判别方法

| 现象 | 原因 | 处理 |
|---|---|---|
| `adb: command not found` | platform-tools 不在 PATH | 用绝对路径 `%LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe` |

1. adb 的 shell 以 uid 2000 运行，这决定了“能做什么、不能做什么”。
2. 一次实验的最小流程：`devices` → `mkdir` → `push` → `chmod` → `shell` 执行 → `logcat`。

4. `logcat -d -s <tag>:*` 与 `--pid` 是定位输出的两个最有效参数。

## 第 38 章 ARM64、NEON 与 FP16：手机 CPU 到底能做什么

### 38.1 本章要解决什么问题

大模型推理在手机上是“算力与带宽的拉扯”：矩阵乘要读大量权重，CPU 要尽量一次处理更多数据。ARM64 提供了两类加速手段：

- **NEON/SIMD**：一条指令处理多个数据（向量化）；
- **低精度算术（FP16/INT8）**：用更少的位表示数，减少内存带宽与计算量。

本章要让你理解：

- ARM64 的寄存器与 NEON 是什么；
- 为什么量化模型能跑得动；
- 哪些指令是“ARMv8.2 才有”的，老设备可能不支持；
- 怎么在设备上确认 CPU 能力，而不是猜。

### 38.2 概念

#### 38.2.1 ARM64 的基础结构

**定义**：AArch64（ARM64）是 ARM 的 64 位指令集架构。几个关键点：

- **通用寄存器**：`x0`–`x30`（64 位），`w0`–`w30` 是它们的 32 位视图；`sp` 是栈指针；`xzr`/`wzr` 是零寄存器。
- **向量寄存器**：`v0`–`v31`，每个 128 位（16 字节）。NEON 指令在这些寄存器的不同视图上操作（`b`/`h`/`s`/`d`/`q` 分别表示 8/16/32/64/128 位元素）。
- **调用约定**：参数主要走 `x0`–`x7` 与 `v0`–`v7`，返回值在 `x0`/`v0`。这就是 ABI 的一部分（第 26 章）。

**类比**：通用寄存器是“手上的几个盒子”，向量寄存器是“一个能装 16 个小格的大抽屉”。

#### 38.2.2 NEON 与 SIMD

**定义**：SIMD（Single Instruction, Multiple Data，单指令多数据）是一条指令同时处理多个数据元素。ARM 的 SIMD 实现叫 NEON。

**例子**：把 16 个 `int8` 相加，标量需要 16 条加法；NEON 可以一条 `add v0.16b, v0.16b, v1.16b` 完成。

**为什么对推理重要**：量化后的权重是 `int8` 或 4-bit，矩阵乘可以按“块”做点积。NEON 的 `SDOT`（Signed Dot Product，ARMv8.2 的整数点积指令）一条指令做 4 组 8 位点积并累加，是量化推理的核心加速之一。

**注意**：`SDOT` 属于 ARMv8.2 的可选扩展（通常写作 `dotprod`）。不是所有 ARM64 设备都有；老设备上只能用 `vmull`/`vpadal` 等等价组合。

#### 38.2.3 FP16：半精度浮点

**定义**：FP16 是 16 位浮点（1 符号 + 5 指数 + 10 尾数），相比 FP32（32 位）精度低、范围小，但内存占用和带宽减半。

**对推理的意义**：

- 权重可以用 FP16 存，减少内存带宽（手机推理常常是带宽瓶颈）；
- 部分 CPU 有 FP16 向量指令（ARMv8.2 的 `FP16` 扩展），一次处理更多元素；
- 激活值用 FP16 累加可能掉精度，工程上常混合使用（FP16 存、FP32 累加）。

**重要澄清**：模型“4-bit 量化”与“FP16”是两件不同的事。4-bit 量化是把权重压到 4 位整数 + 缩放因子（第 21 章）；FP16 是浮点精度选择。两者可以叠加（4-bit 权重反量化到 FP16 再算），但不是替代关系。

#### 38.2.4 怎么确认设备能力

**系统属性**：

```powershell
adb shell getprop ro.product.cpu.abi          # arm64-v8a
adb shell getprop ro.product.cpu.abilist      # 支持的 ABI 列表
adb shell getprop ro.board.platform           # 平台代号
```

**CPU 信息**：

```powershell
adb shell cat /proc/cpuinfo | Select-Object -First 30
```

关注：

- `CPU architecture` / `Features`：是否含 `asimd`（NEON 的 64 位标志）、`fp`、`fphp`（FP16 运算）、`asimdhp`（FP16 向量）、`asimddp`（点积）。
- `processor` 条目数量：逻辑核数。

**频率与拓扑**：

```powershell
adb shell "ls /sys/devices/system/cpu/"
adb shell "cat /sys/devices/system/cpu/cpu0/cpufreq/cpuinfo_max_freq"
```

不同簇（大核/小核）的 `cpuinfo_max_freq` 不同，这是判断 big.LITTLE 的直接证据。

### 38.3 本项目实例

#### 38.3.1 构建参数与硬件加速的关系

本次 MNN 构建的关键开关里，**没有**显式打开 FP16：

- `mnn-rs` 的 `fp16` feature 才会给 CMake 传 `-DMNN_SUPPORT_FP16=ON`（`[依赖源码已核实]`，`build.rs` 第 1055–1057 行）；
- 本项目 `Cargo.toml` 用的是 `features = ["cpu", "static", "llm"]`，不含 `fp16`（`[仓库已核实]`）。

所以“本次产物是否使用 FP16 内核”取决于 MNN 自身的默认值与运行时探测，**不能**从 Cargo feature 推断 `[未复核]`。验证方法：

1. 看 MNN 构建日志里 `MNN_SUPPORT_FP16` 的 cache 值（`CMakeCache.txt`）；
2. 看运行时日志是否有后端/精度选择信息；
3. 对比同一模型在 `fp16` 开/关下的 `decode_tok_s`。

#### 38.3.2 模型是 4-bit，为什么还需要 NEON

4-bit 量化减少的是**内存占用与带宽**，但计算时仍要把权重“反量化”成更宽的整数/浮点，再做乘加。这个反量化 + 点积的过程正是 SIMD 发挥作用的地方：

```
4-bit 权重块（含 scale）
   → 反量化到 int8/fp16
   → NEON 点积（SDOT / FMLA）
   → 累加到 fp32
```

**类比**：把压缩饼干（4-bit）泡开（反量化）需要热水和容器（SIMD 指令），泡开后才能吃（计算）。

#### 38.3.3 线程数与核型

`mnn_smoke` 的第四个参数就是线程数（默认 4，`[仓库已核实]`）：

```rust
let threads = args.next().and_then(|v| v.parse::<u32>().ok()).unwrap_or(4);
```

（见 [mnn_smoke.rs](file:///C:/Users/16412/Documents/Github_Repositories/Notes_App-mnn-engine/src-tauri/examples/mnn_smoke.rs#L21-L21)）

它在运行时被写进配置：

```rust
let config = format!(r#"{{"backend_type":"cpu","thread_num":{threads},"max_new_tokens":{max_tokens}}}"#);
```

（第 35–39 行）

**为什么默认是 4 而不是“核数”**：手机 SoC 通常是“4 小核 + 4 大核”或“2+6”等组合，推理负载放到小核上会拖慢整体；线程数超过大核数后，收益递减且发热上升。默认 4 是一个保守起点，具体最优值必须在目标设备上测（第 39 章）。

### 38.4 常见坑与判别方法

| 现象 | 原因 | 处理 |
|---|---|---|
| 在模拟器上很快，真机上慢 | 模拟器是 x86_64 + 主机 CPU，指令集完全不同 | 所有性能结论必须在目标 ARM64 设备上得出 |
| `Illegal instruction`（SIGILL） | 用了设备不支持的扩展（如 `dotprod`） | 查 `/proc/cpuinfo` 的 `Features`；改用通用内核或运行时分派 |
| 开了 FP16 反而更慢 | 反量化/转换开销大于收益，或设备无 FP16 向量指令 | 用 A/B 测量；不要凭直觉开 |
| 线程数加到 8，速度不升反降 | 小核参与、调度迁移、发热降频 | 测 2/4/6 三档；结合第 39 章 |
| `/proc/cpuinfo` 显示 8 核，但频率只有两档 | 大小核架构 | 用 `cpuinfo_max_freq` 区分簇 |

### 38.5 小结

1. ARM64 有 31 个通用寄存器与 32 个 128 位向量寄存器；NEON 是 SIMD 的实现。
2. SIMD 的价值在于“一条指令处理多个数据”，这是量化推理能跑动的前提之一。
3. FP16 与 4-bit 量化是不同层次的手段，可叠加但不能互相替代。
4. 设备能力要用 `getprop` 与 `/proc/cpuinfo` 的 `Features` 确认，不能假设。
5. 本次构建未显式开启 `fp16` feature；是否实际使用 FP16 内核属于未复核项，给出三步验证法。

### 38.6 练习题

**第 1 题**：为什么“模拟器跑得快”不能作为手机性能结论？

**参考答案要点**：
- 模拟器通常把 ARM 指令翻译到 x86，或直接跑 x86_64 版本；
- 主机 CPU 的缓存、频率、向量宽度与手机完全不同；
- 结论必须来自目标设备实测。

**第 2 题**：`/proc/cpuinfo` 的 `Features` 里没有 `asimddp`，对量化推理意味着什么？

**参考答案要点**：
- 没有整数点积指令（`SDOT`），MNN 只能走通用内核（`vmull`+`vpadal` 等），吞吐下降；
- 不代表不能跑，只是慢；
- 验证：对比同模型在同代设备（有/无 `asimddp`）上的 `decode_tok_s`。

**第 3 题**：给出命令，判断设备是否存在大小核，并说明看什么。

**参考答案要点**：
```powershell
adb shell "for c in /sys/devices/system/cpu/cpu[0-9]*; do echo -n \"$c \"; cat $c/cpufreq/cpuinfo_max_freq; done"
```
- 看各核 `cpuinfo_max_freq` 是否成组不同；
- 结合 `cpu_capacity`（若存在）判断相对算力。

## 第 39 章 线程调度与散热降频：为什么基准测试不可信

### 39.1 本章要解决什么问题

你测出 16.7 tok/s，第二次测变成 12 tok/s，第三次 9 tok/s。硬件没换、代码没改，为什么？

因为手机不是台式机：它有**大小核调度**、**功耗墙**、**温度墙**，还有一个会随时来抢 CPU 的 Android 系统。

本章要让你：

- 理解“线程数 → 实际跑在哪些核上”的调度链路；
- 知道温度/功耗如何改变结果；
- 设计一个**可复现**的测量流程，而不是记下一个数字。

### 39.2 概念

#### 39.2.1 big.LITTLE 与调度

**定义**：手机 SoC 常把核心分成两类：性能核（大核，频率高、功耗高）与能效核（小核，频率低、省电）。Linux 调度器（Android 上通常是 EAS，Energy Aware Scheduling）会根据负载与功耗预算把任务放到不同核上。

**类比**：大核是“力气大的壮汉”，小核是“省电的学徒”。调度器是工头，按工作量分配人手，还要考虑“别把壮汉累趴下”。

**对推理的影响**：

- 线程数 ≤ 大核数时，任务更可能全在大核上跑；
- 线程数超过大核数，部分线程落到小核，**整体完成时间可能变长**（木桶效应）；
- 线程在核间迁移会丢缓存局部性，进一步拖慢。

#### 39.2.2 功耗墙与温度墙

**定义**：

- **功耗墙**（power limit）：SoC 允许的瞬时/持续功率上限；
- **温度墙**（thermal limit）：结温达到阈值后，系统降频（throttling）。

**机制**：手机没有风扇，持续满载几分钟就会升温；一旦触发，调度器降低大核频率，你的吞吐量随之下降。这是**物理约束**，不是软件 bug。

**查看温度**：

```powershell
adb shell "cat /sys/class/thermal/thermal_zone*/type"
adb shell "cat /sys/class/thermal/thermal_zone*/temp"
```

- `type` 给出传感器名（如 `cpu-0-0`、`gpu`、`battery`）；
- `temp` 通常以“毫摄氏度”为单位（如 `45000` 表示 45℃），但不同厂商可能不同，需对照判断。

#### 39.2.3 为什么基准测试必须“分段 + 重复”

一次运行的数字包含：冷启动、缓存预热、调度爬坡、发热降频。可靠的做法：

1. **预热**：先跑一次不计入；
2. **分段**：分别记录 load / prefill / decode（本项目 `mnn_smoke` 已经这样输出）；
3. **重复**：至少 3 次，看中位数与波动；
4. **记录环境**：机型、Android 版本、电量、温度、是否充电、后台应用。

### 39.3 本项目实例

#### 39.3.1 三段计时口径

`mnn_smoke` 输出三段：

- `load_ms`：从 `Llm::create` 到 `load()` 完成；
- `first_chunk_ms`：从开始 `generate_stream` 到第一个 chunk 回调；
- `total_ms`：整个生成过程；
- `perf` 行：`prefill_ms`、`decode_ms`、`sample_ms`、`decode_tok_s`。

（`[仓库已核实]`，见 [mnn_smoke.rs](file:///C:/Users/16412/Documents/Github_Repositories/Notes_App-mnn-engine/src-tauri/examples/mnn_smoke.rs#L28-L80)）

**为什么这样分段**：

- `load` 主要受磁盘 I/O 与内存分配影响；
- `prefill` 受 prompt 长度与算力影响；
- `decode` 是稳态吞吐，最能反映“跑得快不快”；
- `sample` 是采样开销，通常很小，但温度/调度抖动会放大它。

#### 39.3.2 历史数字与它们的可信度

| 指标 | 历史值 | 可信度 |
|---|---|---|
| load | 1385 ms | `[历史记录]`，未复核 |
| 首 chunk | 252 ms | `[历史记录]`，未复核 |
| decode | ≈16.7 tok/s | `[历史记录]`，未复核 |

**为什么不能当基线**：

- 没有留存原始日志；
- 设备当前离线；
- 没有记录温度、电量、后台负载、线程数（虽然默认 4，但实际命令行是否传 4 未记录）；
- 没有重复次数与方差。

**复核流程**（可直接照做）：

```powershell
# 1. 固定环境：飞行模式、清后台、电量 50%~80%、不充电
# 2. 清日志
adb logcat -c
# 3. 连跑 3 次，每次之间等待 60 秒让温度回落
1..3 | ForEach-Object {
  adb shell "cd /data/local/tmp/mnn && LD_LIBRARY_PATH=. ./mnn_smoke ./Qwen3-0.6B-MNN '用一句话介绍你自己。' 128 4"
  Start-Sleep -Seconds 60
}
# 4. 记录每次输出 + 温度
adb shell "cat /sys/class/thermal/thermal_zone*/temp"
```

判读：

- 若三次 `decode_tok_s` 单调下降 → 典型降频；
- 若第一次明显低、后两次接近 → 冷启动/预热效应；
- 若波动很大 → 后台干扰或调度不稳定。

### 39.4 线程数的实验设计

`thread_num` 在 `mnn_smoke` 里是第四个参数。做一组对照：

| 组 | 线程数 | 预期 |
|---|---|---|
| A | 2 | 更省电、可能更稳，适合长文本 |
| B | 4（默认） | 常用折中 |
| C | 6 或 8 | 短时间可能更快，长时间易降频 |

**控制变量**：同一模型、同一 prompt、同一 `max_tokens`、同一温度区间、同一电量区间。

**记录表模板**：

| 轮次 | 线程 | load_ms | first_chunk_ms | decode_tok_s | 起始温度 | 结束温度 |
|---|---|---|---|---|---|---|
| 1 | 2 | | | | | |
| 2 | 4 | | | | | |
| 3 | 8 | | | | | |

**不要做的事**：只测一组就下结论；在充电时测（充电本身发热）；在后台同步/更新时测。

### 39.5 常见坑与判别方法

| 现象 | 原因 | 处理 |
|---|---|---|
| 越跑越慢 | 温度墙降频 | 记录温度；每轮之间冷却；报告里写“稳态/峰值”两组数 |
| 线程越多越慢 | 小核拖累 / 调度迁移 | 限制线程数到“大核数”；用 `taskset`（需权限）绑核做对照 |
| 首轮特别慢 | 冷启动、页缓存未命中、动态库首次加载 | 预热一轮，不计入 |
| 数字与别人差异巨大 | 机型/系统/后台/模型版本不同 | 报告必须带环境信息 |
| 设备休眠导致中途降速 | 屏幕熄灭后 CPU 降频/限流 | 测试时保持屏幕常亮（`adb shell svc power stayon true`） |
| 结果“太整齐” | 只看了一次或抄了旧数据 | 至少 3 次，保留原始输出文件 |

### 39.6 小结

1. 手机性能由“调度 + 功耗 + 温度”共同决定，不是单纯的 CPU 频率。
2. 线程数超过大核数通常不划算；4 是一个合理起点，最优值要实测。
3. 可靠的测量必须：预热、分段、重复、记录环境。
4. 本项目的 `load 1385 ms`、首 chunk `252 ms`、`≈16.7 tok/s` 全部是 `[历史记录]` 且**未复核**，不可作为验收基线。
5. 报告性能时，写清“峰值/稳态”“温度区间”“线程数”，比写一个孤立的 tok/s 有价值得多。

### 39.7 练习题

**第 1 题**：为什么“连续跑 5 次取平均”可能比“跑 1 次”更不可信？

**参考答案要点**：
- 连续跑会让设备持续升温，后几次是降频后的数据，平均值混合了不同状态；
- 正确做法是每轮间隔冷却，并分别报告冷/热两组；
- 或取“第一次（冷）”“第三次（稳态）”两个数，而不是平均。

**第 2 题**：设计一个实验，判断“8 线程比 4 线程慢”是因为小核拖累还是因为降频。

**参考答案要点**：
- 记录每轮的起始/结束温度：若 8 线程起始温度低但结束高、且耗时递增 → 降频；
- 若温度相近但 8 线程始终慢 → 小核拖累/调度迁移；
- 进一步：用绑核（`taskset`，需权限）把 8 线程限制在大核上对照。

**第 3 题**：为什么模型加载时间（`load_ms`）也会受温度影响？

**参考答案要点**：
- 加载过程包含反序列化、内存分配、可能的反量化/预处理，都是 CPU 密集；
- 降频时这些阶段同样变慢；
- 另外磁盘 I/O 与页缓存命中率影响更大，需与温度因素分开看。

## 本部分收束：从“文件”到“能跑”

七章下来，一条完整的判断链已经形成：

```
拿到一个二进制
  ├─ 它是 ELF 吗？什么架构？PIE 吗？            → 第 33 章（readelf -h/-l）
  ├─ 它依赖什么？加载器找得到吗？                → 第 34 章（readelf -d）
  ├─ 它放在哪个目录？那个目录谁能读/执行？        → 第 35、36 章（ls -lZ / avc）
  ├─ 我能把它推上去并跑起来吗？                  → 第 37 章（adb）
  └─ 跑起来后，这个速度可信吗？                  → 第 38、39 章（CPU 能力与热约束）
```

这套链条不只适用于 MNN。换成 llama.cpp、ONNX Runtime、TFLite，问题会以同样的形状出现：架构、依赖、路径、权限、调度。把工具和判据记住，比记住任何一个具体报错更有用。
