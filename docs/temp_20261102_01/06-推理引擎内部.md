# 第四部分：推理引擎内部

> 本部分对应第 16–22 章。
> 前两部分讲的是“怎么把引擎接进来”。这一部分讲**引擎接进来之后到底在算什么**——为什么第一次输出慢、为什么后续快、为什么模型文件几百 MB、为什么调参数会改变“性格”。

先定义本部分的核心术语：

| 术语 | 定义 | 生活化类比 |
|---|---|---|
| **推理（inference）** | 用训练好的权重做前向计算，得到输出，不更新权重 | 用已经背熟的菜谱做菜，不重新研究菜谱 |
| **参数（parameter / weight）** | 模型里可学习的数值，通常是矩阵 | 菜谱里的每一行配比数字 |
| **计算图（computational graph）** | 把运算表示成“节点 + 有向边”的图，边表示数据流 | 工厂的工序流程图：每道工序是节点，传送带是边 |
| **算子（operator / op）** | 图上的一个基本运算，如矩阵乘、加法、softmax | 一道具体的工序 |
| **后端（backend）** | 真正执行算子的实现，如 CPU、GPU、NPU | 执行工序的车间；同一道工序可以换不同车间做 |
| **token** | 模型处理文本的最小单位，可以是一个词、一个词的一部分或一个标点 | 乐高积木块；文本是拼出来的 |
| **tokenizer** | 把文本切成 token、把 token 还原成文本的程序 | 切菜机 + 拼盘机 |
| **prefill** | 一次性处理整个 prompt，建立缓存 | 一次性把整段材料都预处理完 |
| **decode** | 每次只处理一个新 token，逐字往外吐 | 一道一道上菜 |
| **KV cache** | 缓存历史 token 的 Key/Value，避免重复计算 | 记住已经算过的账，不重复算 |
| **logits** | 模型对“下一个 token 是谁”的原始打分向量 | 考试的选择题得分，还没换算成概率 |
| **采样（sampling）** | 按某种策略从 logits 里挑出一个 token | 按规则从候选里抽签 |
| **量化（quantization）** | 用更低位宽（如 4 bit）存储权重，换取更小体积/更快速度 | 把高清照片压成 JPG，体积小、略有损失 |

## 第 16 章 模型加载

### 16.1 本章要解决什么问题

`Llm::create(&config_path)` 与 `Llm::load()` 只有两个调用，但背后发生了很多事：读配置、定位权重文件、分配内存、初始化后端、准备 tokenizer。为什么加载要花 1 秒多？为什么加载失败时错误信息往往很模糊？

本章把“加载”拆成可观察的阶段，让你在失败时能判断卡在哪一段。

### 16.2 概念：从直觉到机制

#### 16.2.1 直觉：加载 = 把菜谱和食材搬进厨房

**类比**：做菜前你要做四件事：

1. 看菜谱（读 `config.json`，知道模型结构、层数、隐藏维度）；
2. 清点食材（找到权重文件，确认大小和格式）；
3. 摆好灶台（初始化计算后端、线程池）；
4. 准备工具（tokenizer、chat template）。

任何一步缺失，都做不成菜。**加载阶段的错误几乎都能归到这四步之一。**

#### 16.2.2 机制：加载的四个阶段

```
┌───────────────────────────────────────────────────────────┐
│ 阶段 1：解析配置                                          │
│   config.json → 模型结构参数（层数/头数/隐藏维度/vocab）   │
│   失败表现：JSON 解析错误、字段缺失                        │
├───────────────────────────────────────────────────────────┤
│ 阶段 2：定位与映射权重                                    │
│   打开权重文件 → mmap 或 read → 建立张量索引               │
│   失败表现：文件不存在、大小不符、格式不支持               │
├───────────────────────────────────────────────────────────┤
│ 阶段 3：分配运行时内存                                    │
│   权重常驻内存 + KV cache 预留 + 临时工作区                │
│   失败表现：OOM、分配失败、进程被系统杀掉                  │
├───────────────────────────────────────────────────────────┤
│ 阶段 4：初始化后端与线程                                  │
│   CPU 后端线程池、算子实现选择、SIMD 能力探测              │
│   失败表现：后端不可用、线程创建失败                       │
└───────────────────────────────────────────────────────────┘
```

阶段 2 里的 **mmap（memory-mapped file，内存映射文件）** 值得单独解释：它把文件内容“映射”到进程虚拟地址空间，访问时由操作系统按需从磁盘调入页。好处是**不必一次性把几百 MB 读进堆内存**，多进程还能共享同一份物理页。代价是第一次访问会触发缺页中断，表现为“加载很快、首次推理慢”。

**类比**：mmap 像“把整本书的书架位置记下来，需要哪页再去取”，而不是“先把整本书复印一遍”。

#### 16.2.3 细节：`create` 与 `load` 的职责划分

本项目的调用顺序是：[仓库已核实：`worker.rs` 中 `create_and_load`]

```
Llm::create(config_path)
   → 构造引擎对象，记录配置路径
Llm::load()
   → 真正读权重、初始化后端（耗时主要在这里）
Llm::set_config({ backend_type: "cpu", thread_num: N })
   → 运行时参数
```

**为什么拆成两步？** 因为“创建对象”和“加载资源”失败的语义不同：前者通常是路径/参数错误，后者是资源/格式问题。拆开便于上层分别处理，也让同一对象可以重新 `load` 不同模型（本项目在 Load 请求里先把旧 `engine = None` 释放，再新建，实际上避免了复用）。

**一个易错点**：`set_config` 里写 `"backend_type": "cpu"` 是字符串。写错大小写或写成 `"CPU"` 可能不被识别，最终回退到默认后端。**这类“配置被忽略但不报错”的问题最难查**——解法是查 MNN 文档确认取值，并用性能数字反证（例如 GPU 后端启用后 decode 速度应显著不同）。

### 16.3 本项目真实案例

#### 16.3.1 模型目录的形态

本项目加载的不是单个文件，而是一个**目录 bundle**：

```
D:\models\Qwen3-0.6B-MNN\
  ├── config.json          ← 必需：mnn_smoke 会先检查它
  ├── （权重文件）          ← 具体文件名由 MNN 导出工具决定
  └── （tokenizer 相关文件） ← 词表等
```

`mod.rs` 里的 `list_bundles` 只把**包含 `config.json` 的子目录**认作有效 bundle。[仓库已核实] 这条规则很实用：

- 它避免把“随手放的权重文件”误认为模型；
- 它让前端可以安全地列出可用模型，而不会因为半个模型目录而崩溃。

`mnn_smoke` 也在启动时检查 `config.json` 是否存在。[仓库已核实：`examples/mnn_smoke.rs`]

#### 16.3.2 真实规模与耗时

- 模型：Qwen3-0.6B-MNN，约 **433 MB**（目录整体大小）。[项目事实]
- 加载耗时：约 **1385 ms**（历史终端输出）。[历史记录，未复核]

用 433 MB / 1.385 s 粗算，等效读取速率约 313 MB/s。这个数量级与手机 UFS 顺序读性能相当，说明**加载耗时主要受存储 I/O 支配**，而不是计算。由此可以推出两条实践建议：

1. 把模型放在**应用私有目录**（`/data/user/0/<pkg>`）而不是外部存储，减少权限与路径问题，也避免 SD 卡低速；
2. 不要指望“多线程加速加载”——I/O 带宽是瓶颈，线程数增加收益有限。

> 上述 313 MB/s 是**由两个历史数字推算的估计值**，不是实测吞吐；仅用于建立量级直觉。

#### 16.3.3 加载失败时的分层排查

| 现象 | 可能的阶段 | 下一步 |
|---|---|---|
| 报 JSON 解析错误 | 阶段 1 | 打开 `config.json` 看是否被截断、是否 UTF-8 |
| 报文件不存在 | 阶段 2 | `adb shell ls -l` 确认目录与文件名 |
| 报大小/格式不符 | 阶段 2 | 确认模型是否为 MNN 格式（不是 GGUF，见第 22 章） |
| 进程被杀、无日志 | 阶段 3 | `adb logcat` 找 `lowmemorykiller`；查设备剩余内存 |
| 报后端初始化失败 | 阶段 4 | 换 `backend_type`，或用 `mnn_smoke` 最小化复现 |

**关键判别**：进程**没有报错直接消失**，通常是 OOM 被系统杀掉，而不是代码 bug。此时 Rust 层的 `Result` 根本来不及返回。

### 16.4 常见坑与判别方法

| 错误 / 现象 | 原因 | 处理 |
|---|---|---|
| `config.json not found` | 目录不对，或 bundle 不完整 | 打印实际路径；Android 上注意应用私有目录 vs `/data/local/tmp` |
| `failed to parse config` | JSON 损坏 / 编码问题 | 用 `Get-Content -Raw` 或 `cat` 检查；确认是 UTF-8 无 BOM |
| 加载成功但输出全是乱码 | tokenizer 文件缺失 | 检查 bundle 完整性；见第 22 章 |
| 加载耗时异常长（几十秒） | 模型放在慢速存储 / 远程挂载 | 换到内部存储；避免通过 `adb push` 到低速路径后直接跑 |
| 反复加载后内存持续上涨 | 旧对象未释放 | 确认 `Llm` 被 drop；本项目在 Load 前 `engine = None` 就是为了释放旧权重 |
| 加载后第一次推理特别慢 | mmap 缺页 + 后端预热 | 属正常现象；报告性能时应区分“冷启动”与“热态” |

### 16.5 小结

1. 加载分四阶段：解析配置、映射权重、分配内存、初始化后端；错误可按阶段定位。
2. `create` 负责对象，`load` 负责资源，二者失败语义不同。
3. mmap 让加载“看起来快”，但把成本转移到首次访问（缺页）。
4. 加载耗时主要由 I/O 决定；433 MB / 1.3 s 量级与手机存储带宽相符。
5. 进程无声消失优先怀疑 OOM，而不是逻辑错误。

### 16.6 练习题

**第 1 题**：为什么 `list_bundles` 用“是否存在 `config.json`”作为有效性判据，而不是检查权重文件大小？

> 参考答案要点：`config.json` 是引擎的入口元数据，缺失必然无法加载；权重文件命名因导出工具而异，难以硬编码判断；用入口文件做判据简单、稳定、误判率低。

**第 2 题**：mmap 加载为什么可能导致“加载很快、首 token 很慢”？如何验证？

> 参考答案要点：mmap 只建立映射，不预读数据；首次访问触发缺页从磁盘读入。验证方法：连续两次加载+推理，比较第一次与第二次的 `first_chunk_ms`；若第二次明显更低且文件已被页缓存，则可确认。

**第 3 题**：如果 `set_config` 里把 `thread_num` 写成字符串 `"4"` 而不是数字 `4`，可能发生什么？如何判断配置是否真的生效？

> 参考答案要点：可能被忽略或解析失败而不报错，实际仍用默认线程数。判断方法：对比不同 `thread_num` 下的 `decode_tok_s`，若完全无变化则配置未生效；同时查 MNN 日志/文档确认类型要求。

## 第 17 章 计算图、算子与后端调度

### 17.1 本章要解决什么问题

模型不是一个“大函数”，而是几百个运算按依赖关系排成的图。为什么理解这张图很重要？因为**性能问题几乎都发生在图上**：某个算子没有优化实现、某个形状触发了低效路径、线程没有喂饱。

本章要让你能：

- 说清“图、算子、后端”三层关系；
- 理解“算子融合”和“内存复用”为什么能提速；
- 知道该看哪些指标判断瓶颈。

### 17.2 概念：从直觉到机制

#### 17.2.1 直觉：图是工序流程，后端是车间

```
输入 token
   │
   ▼
[Embedding] ──► [Layer 0: Attention → MLP] ──► [Layer 1: ...] ──► ... ──► [Layer N]
                                                                          │
                                                                          ▼
                                                                     [LM Head]
                                                                          │
                                                                          ▼
                                                                       logits
```

- **节点**：一次运算（矩阵乘、LayerNorm、Softmax、RoPE 等）；
- **边**：数据依赖（上一层的输出是下一层的输入）；
- **后端**：给每个节点挑一个“在哪执行、用哪个 kernel”。

**类比**：一张工序图上有 20 道工序；车间可以选“手工台”“数控机床”“专用冲压机”。同一张图，换车间就是换后端。

#### 17.2.2 机制：三个优化层次

| 层次 | 手段 | 收益来源 | 风险 |
|---|---|---|---|
| **图级** | 常量折叠、算子融合、死代码消除 | 减少节点数与中间结果 | 融合规则不匹配时回退，收益消失 |
| **算子级** | 选更快的 kernel（SIMD、分块、Winograd） | 单算子吞吐 | 某些形状/尺寸没有优化路径 |
| **调度级** | 多线程切分、任务顺序、内存复用 | 并行度、缓存命中 | 线程过多导致争抢、降频 |

**算子融合（operator fusion）** 的定义：把多个小算子合成一个 kernel，避免中间结果写回内存。例如 `MatMul + Bias + Activation` 合成一个 kernel，省掉两次内存往返。

**类比**：本来要“切菜→装盘→下锅”三个工位来回搬，融合后一个工位全做完，省掉搬运时间。

**为什么内存搬运是大头**：现代 CPU 算浮点很快，但内存带宽有限。一个 4096×4096 的矩阵乘，如果中间结果反复落内存，带宽会成为瓶颈。融合的价值就在这里。

#### 17.2.3 细节：CPU 后端在手机上怎么并行

典型策略是把输出矩阵按行/列切块，分给多个线程，每个线程算一块。关键参数：

| 参数 | 作用 | 过大/过小的后果 |
|---|---|---|
| 线程数 | 并行度 | 过多：线程争抢、调度开销、降频；过少：算力闲置 |
| 分块大小 | 缓存局部性 | 过大：cache 溢出；过小：循环开销占比高 |
| 绑定策略 | 线程绑核 | 不绑核：线程在大小核间迁移，缓存失效 |

[通用原理]

**手机与服务器的关键差异**：手机是**大小核异构**。调度器可能把线程放到小核上，或者在大核小核之间来回迁移。这会让“4 线程一定比 2 线程快”的直觉失效（第 39 章详述）。

#### 17.2.4 细节：`backend_type` 的实际含义

本项目 `set_config` 传：

```json
{"backend_type": "cpu", "thread_num": 4}
```

[仓库已核实：`worker.rs` 里构造的配置]

| 键 | 含义 | 可选值（以 MNN 文档为准） |
|---|---|---|
| `backend_type` | 用哪个后端执行 | `cpu`、`opencl`、`vulkan`、`metal` 等（依编译开关而定） |
| `thread_num` | CPU 后端线程数 | 正整数；手机通常 2–4 |

**注意**：后端必须在**编译时**就编进去。若构建 MNN 时关掉了 OpenCL，运行时写 `"opencl"` 只会失败或回退。这再次呼应第 7 章：**feature 决定能力，配置只能选择已具备的能力**。

### 17.3 本项目真实案例

#### 17.3.1 为什么选 CPU 后端

| 因素 | CPU | GPU（OpenCL/Vulkan） |
|---|---|---|
| 兼容性 | 几乎所有设备可用 | 驱动差异大，部分机型不可用 |
| 小模型效率 | 0.6B 模型在 CPU 上已可交互 | 小模型难以喂饱 GPU，启动开销占比高 |
| 构建复杂度 | 低 | 需要额外编译开关、额外库 |
| 调试难度 | 低（可 perf/火焰图） | 高（shader 编译、驱动黑盒） |

**判断逻辑**：模型小（0.6B）+ 目标“能跑通并可比对” → CPU 是正确起点。等模型变大或要求更高吞吐，再评估 GPU/NPU。

#### 17.3.2 用 `performance()` 判断瓶颈在哪

`mnn_smoke` 会打印 `performance()` 的字段：[仓库已核实：`examples/mnn_smoke.rs`]

| 字段 | 含义 | 高值说明 |
|---|---|---|
| `prompt_len` | prompt 的 token 数 | 只反映输入规模 |
| `gen_seq_len` | 生成的 token 数 | 只反映输出规模 |
| `prefill_us` | 处理 prompt 的总耗时（微秒） | 高 → 图级/算子级效率问题，或 prompt 太长 |
| `decode_us` | 逐 token 生成的总耗时 | 高 → 单步延迟高，多半是带宽/线程问题 |
| `sample_us` | 采样耗时 | 高 → 采样实现低效（通常占比很小） |
| `load_us` | 加载耗时 | 见第 16 章 |

**分析方法**：先算 `decode_us / gen_seq_len` 得到单 token 平均耗时，再与 `decode_tok_s` 对照（应为倒数关系）。若 `sample_us` 占比超过 10%，说明瓶颈在采样而非矩阵计算；若 `prefill_us` 远大于 `decode_us × 10`，说明 prompt 处理是主要成本。

#### 17.3.3 历史数据的定位

历史记录：`load 1385 ms`、`首 chunk 252 ms`、`decode ≈16.7 tok/s`。[历史记录，未复核]

用第 17 章的框架解释：

- `decode ≈16.7 tok/s` → 单 token 约 60 ms。这是**带宽受限**的典型量级：每生成一个 token 都要把权重读一遍（0.6B 4-bit ≈ 300 MB 量级），60 ms 对应约 5 GB/s 的有效带宽，接近手机内存带宽的下限区间。
- `首 chunk 252 ms` → 包含 prefill + 第一次 decode + 可能的缺页/预热。

**再次强调**：这些数字未复核。上面这段是**用数字做推理练习**，不是“已证明的结论”。正确的说法是“若该数字成立，则其量级与带宽受限模型相符”。

### 17.4 常见坑与判别方法

| 错误 / 现象 | 原因 | 处理 |
|---|---|---|
| 改 `thread_num` 完全没效果 | 配置未生效，或后端忽略该参数 | 用 `decode_tok_s` 对比；查 MNN 文档的参数名 |
| 4 线程比 2 线程更慢 | 降频/争抢/大小核迁移 | 测 1/2/3/4 线程，取拐点；注意设备温度 |
| 首次推理极慢，后续正常 | 缺页 + kernel 预热 | 分别报告冷/热数据 |
| 指定 GPU 后端启动失败 | 构建时未编入该后端 | 重新构建并开启对应开关 |
| 输出与 PC 上完全不一致 | 后端/量化路径差异 | 先用 CPU 后端对齐，再比较其他后端 |

### 17.5 小结

1. 模型是“图 + 算子 + 后端”的组合；性能问题要按这三层定位。
2. 图级融合减少内存搬运，是移动端提速的主要来源之一。
3. CPU 后端的瓶颈通常是**内存带宽**而非算力，这解释了“加线程收益有限”。
4. 后端必须在编译期编入，运行时配置只能选择已存在的能力。
5. 用 `prefill_us`/`decode_us`/`sample_us` 拆分耗时，比只看总时间有效得多。

### 17.6 练习题

**第 1 题**：为什么“算子融合”在手机端比在服务器端更重要？

> 参考答案要点：手机内存带宽相对算力更紧张，功耗/散热约束更强；减少中间结果落内存既省带宽也省能耗。服务器可用更大缓存和高带宽掩盖搬运成本。

**第 2 题**：`decode_tok_s = 16.7` 对应的单 token 延迟是多少？若模型 4-bit 权重约 300 MB，粗算所需有效带宽是多少？这个估算忽略了什么？

> 参考答案要点：约 60 ms/token；300 MB / 0.06 s ≈ 5 GB/s。忽略了 KV cache 读写、激活值、算子不融合时的额外流量、以及并非所有带宽都能跑满。

**第 3 题**：如果 `sample_us` 占总 decode 时间的 30%，你会先查什么？

> 参考答案要点：先确认采样参数是否极端（如 top-k 很大、top-p 接近 1 导致排序/归一化成本上升），再查是否每步都在做全词表 softmax；正常实现下采样占比应很小。

## 第 18 章 prefill 与 decode

### 18.1 本章要解决什么问题

同样是一个模型，为什么“读一段 200 字的 prompt”要几百毫秒，而“生成 200 个字”却能持续输出？

答案在于 LLM 推理的两个阶段：**prefill（预填充）** 和 **decode（解码）**。它们的计算模式完全不同，优化手段也完全不同。

### 18.2 概念：从直觉到机制

#### 18.2.1 直觉：先通读题目，再逐字作答

**类比**：考试时你先通读整道题（prompt），理解上下文；然后一个字一个字写答案。通读是一次性的大量阅读，写字是一小步一小步。

- **prefill** = 通读题目：一次性把 N 个 token 全喂进去；
- **decode** = 逐字作答：每次只喂 1 个新 token，输出 1 个 token。

#### 18.2.2 机制：为什么 prefill 能并行，decode 不能

```
prefill：输入 [t1, t2, t3, ..., tN]
   → 一次矩阵乘就能同时算出所有位置的表示（因为因果掩码保证位置 i 只看 ≤ i）
   → 计算量大，但【并行度高】，适合多线程/大矩阵 kernel

decode：输入 [t_{N+1}]
   → 只能算这一个位置
   → 计算量小，但【每一步都要等上一步完成】，是串行的
   → 瓶颈变成“读权重 + 读写 KV cache”的带宽
```

关键结论：

| 阶段 | 计算特征 | 主要瓶颈 | 优化方向 |
|---|---|---|---|
| prefill | 矩阵大、并行度高 | 算力 + 带宽 | 更大 batch、更好 kernel、多线程 |
| decode | 矩阵小（向量×矩阵）、串行 | **内存带宽** | 量化、减少权重读取、KV cache 优化 |

**这就是“首 token 慢、后续快”的根本原因**：首 token 必须等 prefill 完成；后续每个 token 只走一次轻量的 decode 步骤。

#### 18.2.3 细节：首 token 延迟（TTFT）的组成

**TTFT**（Time To First Token，首 token延迟）= 排队 + 加载（若未加载）+ prefill + 第一次 decode + 采样 + 网络/管道传输。

在 `mnn_smoke` 的输出里：

- `load_ms` 是加载；
- `first_chunk_ms` 是从开始生成到收到第一个 chunk 的时间；
- 若模型已加载，`first_chunk_ms` 近似等于 prefill + 首步 decode + 采样。

**这两个数字不能混为一谈**。报告“首 token 252 ms”时，必须说明**是否包含加载**，否则无法比较。

#### 18.2.4 细节：batch 与并发

prefill 的并行度可以用 batch 提升：一次处理多个请求（或一个请求的多个位置）。但手机端通常只有一个用户、一个请求，**batch = 1**，因此 prefill 的并行度只能靠“把 N 个 token 一起算”来获得。

decode 阶段 batch 也是 1，所以它天然是“薄矩阵乘”，GPU 的优势发挥不出来，CPU 反而更合适。

### 18.3 本项目真实案例

#### 18.3.1 `generate_stream` 的循环结构

`mnn-rs` 的 `generate_stream` 大致是：[仓库已核实：`llm.rs`]

```
mnn_llm_generate_init(handle, prompt)     ← prefill 在这里发生
loop {
    if mnn_llm_stoped(handle) { break }   ← 是否遇到停止条件
    mnn_llm_generate_step(handle, max_tokens)  ← 一次 decode 步
    取回文本 → 回调 on_chunk
}
```

要点：

- `init` 承担 prefill；
- `step` 是单步 decode；
- 回调是**流式**的：每步可能产出一个或多个字符。

这与“一次性返回全部文本”的 API 有本质区别：流式让用户在 prefill 完成后立刻看到第一个字，体验上的“等待感”大幅下降。

#### 18.3.2 历史观测的解读

历史记录：`首 chunk 252 ms`、`decode ≈16.7 tok/s`。[历史记录，未复核]

若 prompt 约几十个 token、模型 0.6B 4-bit：

- prefill 的 252 ms 里，大部分是“读权重 + 计算”；
- 后续 60 ms/token 是 decode 的带宽成本。

**对比意义**：如果换成更大的模型（如 1B），decode 的每 token 带宽成本会同比上升，tok/s 下降；prefill 也会变慢，但因为并行度更高，**相对**没那么敏感。这解释了为什么“小模型在手机上体验好”。

#### 18.3.3 本项目如何把两个阶段暴露给上层

`LocalMnnResult` 里同时有 `prefill_ms`、`decode_ms`、`sample_ms`、`decode_tok_s`、`first_chunk_ms`。[仓库已核实：`mod.rs`]

这是有意的设计：UI 层想显示“首字延迟”就用 `first_chunk_ms`，想显示“吐字速度”就用 `decode_tok_s`，两者不能互相替代。

### 18.4 常见坑与判别方法

| 错误 / 现象 | 原因 | 处理 |
|---|---|---|
| 首 token 很慢但 tok/s 正常 | prompt 太长 → prefill 成本高 | 缩短 prompt / 用 KV 复用（第 19 章） |
| 首 token 快但后续很慢 | decode 带宽瓶颈 / 降频 | 量化、减线程、检查温度 |
| 把 `load_ms` 算进首 token 延迟 | 口径混淆 | 明确“冷启动 TTFT”与“热态 TTFT” |
| `first_chunk_ms` 为 0 或异常小 | 回调时机/计时位置错误 | 检查计时起点是否在 `generate_init` 之前 |
| 生成的 token 数超过 `max_tokens` | 停止条件未生效 | 检查 `stoped` 与 `max_tokens` 传递 |
| 输出被截断但无错误 | `max_tokens` 太小 | 调大上限，或检查 stop 词 |

### 18.5 小结

1. prefill 一次处理整个 prompt，并行度高、算力受限；decode 每步一个 token，串行、带宽受限。
2. 首 token 慢是 prefill 的必然结果；后续速度由 decode 的带宽决定。
3. TTFT 的口径必须写清是否包含加载，否则数字不可比。
4. 手机端 batch=1，GPU 优势难以发挥，CPU 是合理起点。
5. 优化要对症：prefill 慢查 prompt 长度与 kernel，decode 慢查带宽与量化。

### 18.6 练习题

**第 1 题**：为什么 decode 阶段“矩阵很小”，却可能比 prefill 更耗总时间？

> 参考答案要点：decode 要重复 N 次，每次都要把权重从内存读一遍；总时间 = 单步延迟 × token 数。prefill 虽单次计算量大，但只做一次且并行度高。

**第 2 题**：一个 100 token 的 prompt，prefill 用了 300 ms，之后生成 50 token 用了 3 s。请分别算出 prefill 吞吐与 decode 速度，并判断瓶颈。

> 参考答案要点：prefill ≈ 333 token/s；decode ≈ 16.7 token/s（单 token 60 ms）。瓶颈在 decode 的带宽/串行性，而不是 prefill。

**第 3 题**：如果只报告“总耗时 3.3 s”，会掩盖哪些关键信息？请列出至少三项。

> 参考答案要点：首字延迟（用户体验）、prefill 与 decode 各自成本、加载是否计入、是否触发了降频、采样开销占比。

## 第 19 章 KV cache 复用

### 19.1 本章要解决什么问题

多轮对话时，第二轮为什么不该把第一轮的全部内容重算一遍？如果每轮都重算，10 轮对话的成本会怎样增长？

答案是 **KV cache**：把历史 token 的 Key/Value 缓存下来，后续只算新增部分。

### 19.2 概念：从直觉到机制

#### 19.2.1 直觉：已经算过的账不要再算

**类比**：你在做一张长报表。第一页的数据已经算好并记在草稿纸上。翻到第二页时，你只需要算新增部分，然后引用草稿纸上的结果——而不是把第一页重算一遍。

**定义**：KV cache 是 Transformer 注意力机制中，对历史 token 的 Key 矩阵与 Value 矩阵的缓存。因为因果注意力中，历史 token 的 K/V **不会随新 token 改变**，所以可以复用。

#### 19.2.2 机制：为什么 K/V 可以缓存，Q 不能

注意力计算（简化）：

```
Attention(Q, K, V) = softmax(Q·Kᵀ / √d) · V
```

- 对位置 i 的 token：`Q_i` 由当前 token 的表示算出；
- `K_j`、`V_j`（j ≤ i）由历史 token 算出，且**一旦算出就不再变**（因果掩码保证不看未来）。

所以：

| 量 | 能否缓存 | 原因 |
|---|---|---|
| K | 能 | 历史 token 的 K 固定 |
| V | 能 | 同上 |
| Q | 不需要长期缓存 | 每个新 token 只用自己的 Q |

**这就是名字的由来**：缓存的是 K 和 V。

#### 19.2.3 细节：KV cache 的内存成本

每层、每个 token 需要存：

```
2 × num_heads × head_dim × bytes_per_element
```

（K 和 V 各一份）

对一个 0.6B 级模型，粗算量级是**每 token 几十 KB**。1000 token 上下文 → 几十 MB。这就是为什么：

- 上下文越长，内存压力越大；
- 长上下文会挤占模型权重之外的空间；
- 手机端要限制最大上下文长度。

> 上面是**量级估算**，具体数值取决于层数、头数、head_dim、是否量化 KV cache。本项目未测量该值，标注为**未验证**。

#### 19.2.4 细节：复用的两种场景

| 场景 | 复用方式 | 收益 |
|---|---|---|
| 同一轮内 decode | 每步复用之前的 K/V | 必需，否则 decode 变 O(n²) |
| 多轮对话 | 复用上一轮整段前缀的 K/V | 省掉重复 prefill |
| 相同系统提示词 | 复用 system prompt 的 K/V | 多请求共享前缀 |

MNN 的 wrapper 里提供 `mnn_llm_reuse_kv`。[仓库已核实：`wrapper/mnn_llm_wrapper.h`]

**注意**：KV 复用的前提是“前缀完全一致”。一旦用户改了历史消息（编辑、删除、重新生成），前缀变了，缓存就必须失效并从变化点重算。这也是很多聊天应用“编辑消息后变慢”的原因。

### 19.3 本项目真实案例

#### 19.3.1 主线 llama.cpp 的对照实现

主线 `Notes_App` 的 `agent/local/engine.rs` 里，`Session` 持有 `tokens: Vec<LlamaToken>`，用于复用 KV 前缀。[仓库已核实]

设计要点：

- `ctx: LlamaContext<'static>` 常驻，不每次重建；
- `tokens` 记录已处理的 token 序列；
- 新请求时比较新旧前缀，找到共同前缀长度，只处理新增部分。

**为什么 `'static`**：`LlamaContext` 内部持有模型指针，生命周期实际由调用方保证；用 `'static` 是一种“把借用检查绕过、由人工保证”的写法。这是 FFI 封装的常见妥协，也说明“安全封装”并不等于“零 unsafe”。

#### 19.3.2 MNN 分支的处理方式

MNN 分支目前的设计更简单：

- worker 线程独占一个 `Option<Llm>`；
- 每次 `Generate` 直接调用 `generate_stream`；
- **没有在应用层显式维护多轮前缀复用**（是否内部复用取决于 `reuse_kv` 的调用与 MNN 自身策略）。

[仓库已核实：`worker.rs` 的 `generate` 路径未显式调用 `reuse_kv`]

这是一个**已知的能力差距**，也是“实验分支”与“主线”的区别之一。写作时不把它说成“已经实现多轮加速”。

**如果要补上，验证路径是**：

1. 在 `Generate` 请求里携带“对话历史”或“上一轮 token 序列”；
2. 在 worker 里判断前缀是否一致；
3. 一致则调用 `reuse_kv` 并只 prefill 新增部分；
4. 用 `prefill_ms` 对比验证：第二轮应显著低于第一轮。

### 19.4 常见坑与判别方法

| 错误 / 现象 | 原因 | 处理 |
|---|---|---|
| 第二轮对话和第一轮一样慢 | 未复用 KV，或前缀不一致 | 检查是否调用 `reuse_kv`；打印前缀哈希对比 |
| 复用后输出错乱 | 缓存与当前 prompt 不匹配 | 强制清空缓存，逐轮对比 |
| 内存随轮数增长不回收 | 旧会话缓存未释放 | 会话结束时重置/重建 `Llm` |
| 长上下文后变慢明显 | KV 变大，带宽压力上升 | 限制上下文；考虑 KV 量化 |
| 编辑历史消息后结果异常 | 前缀失效未处理 | 以变化点为界重建缓存 |

### 19.5 小结

1. KV cache 缓存历史 token 的 K/V，因为它们在因果注意力下不变。
2. 没有 KV cache，decode 会退化为每步重算全部历史，复杂度爆炸。
3. 多轮复用要求前缀完全一致；任何历史修改都会使缓存失效。
4. KV cache 的内存随上下文线性增长，是长上下文的主要成本。
5. 本项目 MNN 分支未在应用层显式实现多轮复用，这一点在评估时应如实标注。

### 19.6 练习题

**第 1 题**：为什么 Q 不需要长期缓存，而 K/V 需要？

> 参考答案要点：Q 是“当前 token 的查询”，每个位置只用自己的 Q 一次；K/V 是“历史 token 的索引与内容”，会被后续所有 token 反复使用，且不随新 token 改变。

**第 2 题**：用户在第三轮编辑了第一条消息，为什么缓存必须从第一条开始失效？

> 参考答案要点：第一条改变后，其后所有 token 的注意力上下文都变了，K/V 不再对应；只有编辑点之前的前缀仍可复用。

**第 3 题**：如何用现有 `performance()` 字段验证“多轮复用生效”？

> 参考答案要点：比较第一轮与第二轮的 `prefill_us`（或 `prefill_ms`）；前缀复用生效时，第二轮只处理新增 token，prefill 时间应显著下降。需保证两轮前缀长度可比。

## 第 20 章 采样参数

### 20.1 本章要解决什么问题

模型输出的是 **logits**——对词表中每个 token 的原始打分。怎么从这些分数里选出下一个 token，决定了输出的“性格”：是稳定保守，还是天马行空；是每次一样，还是每次不同。

本章讲清 `temperature`、`top-k`、`top-p`、`seed`、`max_tokens`、`stop` 的作用与相互关系。

### 20.2 概念：从直觉到机制

#### 20.2.1 直觉：从“分数”到“选择”

**类比**：考试选择题有 A/B/C/D 四个选项，每个都有得分。采样就是“按得分决定选哪个”的规则：

- 永远选最高分 → 稳定但呆板；
- 按得分比例随机 → 多样但可能跑偏；
- 只在最高几个里随机 → 折中。

#### 20.2.2 机制：标准采样流水线

```
logits（原始分数）
   │ 1. 除以 temperature
   ▼
缩放后的 logits
   │ 2. 可选：top-k 截断（只保留分数最高的 k 个）
   ▼
候选集合
   │ 3. 可选：top-p 截断（按累积概率保留，直到累计 ≥ p）
   ▼
候选集合
   │ 4. softmax 归一化为概率
   ▼
概率分布
   │ 5. 按概率随机抽样（受 seed 控制）
   ▼
选中的 token
```

**每一步都可能被“跳过”**：temperature=1 相当于不缩放；top-k=0 或超大相当于不截断；top-p=1 相当于不截断。

#### 20.2.3 细节：每个参数的实际效果

| 参数 | 定义 | 调高的效果 | 调低的效果 | 常用范围 |
|---|---|---|---|---|
| `temperature` | 温度，缩放 logits 的倒数系数 | 更随机、更发散、更易胡说 | 更确定、更保守、更重复 | 0.1–1.0 |
| `top-k` | 只保留分数最高的 k 个候选 | 更多样 | 更聚焦 | 20–100（0 表示不启用，以引擎实现为准） |
| `top-p`（核采样） | 按概率累积到 p 为止保留候选 | 更多样 | 更聚焦 | 0.8–0.95 |
| `seed` | 随机数种子 | 不同 seed 产生不同结果 | 固定 seed 可复现 | 任意整数 |
| `max_tokens` | 最多生成多少 token | 更长，但更慢、更耗内存 | 更短 | 按场景 |
| `stop` | 遇到这些字符串/ token 就停止 | — | — | 如 `"\n\n"`、`<eos>` |

**重要关系**：`temperature` 与 `top-k`/`top-p` **不是替代关系，而是串联**。常见误区是“调低 temperature 就不用 top-k”——实际上两者作用在不同环节：temperature 改变分布形状，top-k/top-p 改变候选集合。

#### 20.2.4 细节：temperature 的数学直觉

设某步 logits 为 `[2.0, 1.0, 0.1]`：

- `T=1`：`softmax([2, 1, 0.1])` → 大约 `[0.66, 0.24, 0.10]`；
- `T=0.5`：先除以 0.5 得 `[4, 2, 0.2]`，softmax 后更尖锐 → 最高项占比更大；
- `T=2`：先除以 2 得 `[1, 0.5, 0.05]`，softmax 后更平坦 → 三项更接近。

所以 **T 越小越“自信”**，越大越“犹豫”。T 趋近 0 时退化为贪心（永远选最大）。

**注意**：多数实现不允许 T=0（会除零），而是用“贪心”特殊处理或 clamp 到极小值。写配置时不要假设 T=0 一定可用。

#### 20.2.5 细节：`stop` 与 `max_tokens` 的优先关系

- 先到 `max_tokens` → 强制停；
- 先命中 `stop` 序列 → 提前停；
- 模型输出 EOS token → 也停。

**常见误解**：以为 `stop` 一定比 `max_tokens` 优先。实际取决于实现，但两者都会终止生成；差别在“谁先满足”。排查“为什么只生成了 3 个字”时，要同时检查 `max_tokens` 与 `stop`。

### 20.3 本项目真实案例

#### 20.3.1 主线 llama.cpp 的参数结构

主线 `Notes_App` 的 `LocalParams` 包含：[仓库已核实]

```rust
pub struct LocalParams {
    pub max_tokens: i32,
    pub temperature: f32,
    pub top_p: f32,
    pub top_k: i32,
    pub seed: u32,
    pub stop: Vec<String>,
}
```

这是一套完整的采样参数面：温度、核采样、top-k、种子、停止词全都有。

#### 20.3.2 MNN 分支的当前状态

MNN 分支的 `set_config` 只显式设置了两个键：`backend_type` 与 `thread_num`。[仓库已核实：`worker.rs`]

```json
{"backend_type": "cpu", "thread_num": 4}
```

这意味着：

- 采样参数**依赖 MNN 的默认值**；
- 上层 5 个 Tauri 命令中，`local_mnn_generate` 只接收 `prompt` 与 `max_tokens`，没有暴露 temperature/top-k/top-p。[仓库已核实：`commands/local_mnn.rs`]

**这是一个明确的能力边界**：MNN 分支目前只能控制“生成多长”，不能控制“生成风格”。评估“MNN 是否更好”时，如果两边采样参数不同，速度对比就不公平——这是第 0 章强调“对照要同口径”的具体原因。

#### 20.3.3 如何补上采样参数（验证路径）

`mnn-rs` 的 `set_config` 接受 JSON，`mnn-llm` 支持的键以 MNN 文档为准。[通用原理 + crate 文档]

实践步骤：

1. 查 MNN 文档确认键名（不同版本可能不同）；
2. 在 `create_and_load` 之后追加一次 `set_config`，写入采样参数；
3. 用相同 seed 连续生成两次，检查输出是否一致——**一致才说明 seed 生效**；
4. 把 temperature 从 0.2 调到 0.9，观察输出多样性变化——**有变化才说明参数被识别**。

**注意**：第 3 步极其重要。很多“参数没生效”的问题，都能用“固定 seed 是否可复现”一票判定。

### 20.4 常见坑与判别方法

| 错误 / 现象 | 原因 | 处理 |
|---|---|---|
| 两次生成结果完全相同 | seed 固定且 T 很低，或采样没启用 | 调高 T；换 seed |
| 输出重复、循环 | T 过低 / top-k 过小 | 提高 T 或放宽 top-k |
| 输出胡说、语句断裂 | T 过高 / top-p 过大 | 降低 T 或收紧 top-p |
| 设置参数后毫无变化 | 键名不对 / 类型不对 / 版本不支持 | 查文档；用固定 seed 验证生效性 |
| 一上来就结束 | `stop` 命中、EOS、或 `max_tokens` 太小 | 分别排查三个停止条件 |
| 中文输出被截断成半个词 | stop 匹配在 token 边界之外 | 用 token 级 stop，或后处理 |

### 20.5 小结

1. logits 是原始分数，采样是把分数变成“选谁”的过程。
2. temperature 改变分布形状，top-k/top-p 改变候选集合，它们是串联而非互斥。
3. seed 决定可复现性；固定 seed 是验证“参数是否生效”的最快手段。
4. `max_tokens`、`stop`、EOS 三个停止条件要同时排查。
5. 本项目 MNN 分支目前未暴露采样参数，对照实验时必须声明这一差异。

### 20.6 练习题

**第 1 题**：`temperature=0.1, top_k=1` 与 `temperature=1.0, top_k=1` 的结果会一样吗？为什么？

> 参考答案要点：会一样（都是贪心选最大）。top-k=1 已经把候选集缩到唯一一个，temperature 再怎么变，argmax 不变。这说明参数间有覆盖关系，不是简单叠加。

**第 2 题**：固定 seed 后两次输出仍然不同，可能有哪些原因？

> 参考答案要点：参数未生效；引擎内部仍用真随机/时间种子；多线程归约顺序不稳定导致浮点微小差异并改变 argmax；KV 复用状态残留；stop 条件不同。

**第 3 题**：为什么“比较 MNN 与 llama.cpp 的速度”时，必须同时比较采样参数？

> 参考答案要点：top-k/top-p 影响每步候选数量与排序成本，temperature 影响是否提前命中 EOS；若一边用贪心、一边用大 top-k，tok/s 与生成长度都会不同，速度对比失去意义。

## 第 21 章 量化：4-bit block

### 21.1 本章要解决什么问题

一个 0.6B 模型，如果用 FP32 存权重：`0.6 × 10⁹ × 4 字节 ≈ 2.4 GB`。手机装不下、也跑不动。实际项目里模型只有 433 MB 左右。差了一个数量级，靠的就是**量化**。

本章要让你理解：4-bit 量化怎么做到“体积缩到 1/8 还能用”，以及代价是什么。

### 21.2 概念：从直觉到机制

#### 21.2.1 直觉：把高清照片压成 JPG

**定义**：量化（quantization）是把连续的、高精度的数值（如 FP32）映射到离散的、低位宽的表示（如 INT4）。

**类比**：照片从 RAW 转 JPG。体积小很多，肉眼几乎看不出差别，但放大到像素级会有压缩痕迹。量化也是这样：模型“看起来还能用”，但精度有损。

#### 21.2.2 机制：为什么需要“block（块）”

如果整个矩阵共用一个缩放因子：

```
value_fp = scale × int4_value
```

那么当矩阵里数值范围差异很大时，小值会被压缩成 0，精度严重损失。

**block quantization（分块量化）** 的做法是：把一行/一组元素切成小块（如每 32 或 128 个元素一块），**每块单独存一个 scale（可能还有 zero point）**。

```
块 1： [w0..w31]  → scale1, [q0..q31]（4 bit 每个）
块 2： [w32..w63] → scale2, [q32..q63]
...
```

**类比**：一张大照片如果整体调亮度，暗部会全黑；分成小区域分别调，每块都能保留细节。

#### 21.2.3 细节：4-bit block 的体积账

以 0.6B 参数为例：

| 精度 | 每参数字节 | 权重大小（粗略） | 备注 |
|---|---|---|---|
| FP32 | 4 | ~2.4 GB | 服务器常见 |
| FP16 | 2 | ~1.2 GB | GPU 常见 |
| INT8 | 1 | ~0.6 GB | 移动端可用 |
| INT4 | 0.5 | ~0.3 GB | 加 scale 后略高 |
| INT4 + block scale | 0.5 + 少量 | ~0.3–0.4 GB | 本项目量级（433 MB 含其他文件） |

**注意**：433 MB 是**整个 bundle 目录**的大小，包含权重、`config.json`、tokenizer 等，不等于纯权重。把它当作“权重大小”会高估量化率。

#### 21.2.4 细节：量化的代价

| 代价 | 说明 |
|---|---|
| 精度损失 | 数学题、长链推理更容易出错 |
| 反量化开销 | 计算前要把 int4 还原成浮点，增加指令数 |
| 实现依赖 | 需要专门的 kernel 才能快；通用实现可能反而慢 |
| 格式绑定 | 量化方案与引擎强绑定，换引擎常要重新转换 |

**关键判断**：量化不是“免费加速”。它减少**带宽**（读权重更少），但可能增加**计算**（反量化）。在带宽受限的 decode 阶段，通常是净收益；在算力受限场景，收益可能被抵消。

这正好解释了第 17–18 章的结论：**decode 受带宽限制，所以 4-bit 量化对 decode 帮助最大**。

#### 21.2.5 细节：为什么 weight-only 量化最常见

| 量化对象 | 收益 | 风险 |
|---|---|---|
| 只量化权重（weight-only） | 权重体积小、带宽需求低；激活仍用浮点，精度损失可控 | 反量化有开销 |
| 权重 + 激活（W8A8 等） | 计算也能用整数指令，更快 | 精度损失更大，需要校准数据 |

移动端 LLM 常见选择是 **weight-only 4-bit**：先把最大的成本（权重带宽）砍掉，激活保持浮点，工程风险最低。本项目使用的 MNN 4-bit 模型属于这一类（具体方案以模型导出配置为准，**未逐项核实**）。

### 21.3 本项目真实案例

#### 21.3.1 主线 llama.cpp 的量化档位

主线使用 **Qwen3-0.6B IQ4_XS**。[项目事实]

`IQ4_XS` 是 llama.cpp 的量化档位命名，属于 4-bit 家族中的一种（`IQ` 表示 importance-aware 的量化思路，`XS` 表示更小的块/更激进的压缩）。**具体位宽、块大小、是否含 importance 矩阵，应以 llama.cpp 的量化文档为准**，本书不逐字段断言。

可以确定的是：它的体积量级与“4-bit 权重”一致，即 0.6B 参数约 300–400 MB 量级。

#### 21.3.2 MNN 的 4-bit 模型

MNN 使用的 `Qwen3-0.6B-MNN` 约为 433 MB。[项目事实]

**为什么两个引擎的“同一个模型”大小不同？** 三个原因：

1. 量化方案不同（块大小、是否混合精度、是否保留某些层为高精度）；
2. bundle 内容不同（MNN 目录含配置/tokenizer，GGUF 是单文件封装）；
3. 元数据与对齐差异。

所以**不能只比文件大小判断“谁压缩得更好”**，还要看精度表现和速度。

#### 21.3.3 一张对照表（用于建立直觉，不含未核实结论）

| 项目 | 主线 llama.cpp | MNN 分支 |
|---|---|---|
| 模型格式 | GGUF 单文件 | `.mnn` 目录 bundle |
| 量化档位 | IQ4_XS | 4-bit（具体方案以导出配置为准） |
| 模型体积 | 未在本项目文档中记录精确值 | 约 433 MB（目录整体） |
| 运行设备 | Redmi Note 12 Turbo / Android 14 | 同左 |
| decode 速度 | 约 5 tok/s（历史记录） | 约 16.7 tok/s（历史记录，未复核） |

> 两行速度均属 `[历史记录]`，且**采样参数、线程数、构建 profile 可能不同**，不能直接当作“引擎优劣”的结论。第 0 章与第 22 章都强调这一点。

### 21.4 常见坑与判别方法

| 错误 / 现象 | 原因 | 处理 |
|---|---|---|
| 模型加载报“不支持格式” | 拿 GGUF 直接喂 MNN | 用 MNN 的转换工具重新导出 |
| 量化后输出质量骤降 | 块太小/精度过低 | 换更保守的量化档位 |
| 量化模型反而更慢 | 反量化开销 > 带宽节省 | 换后端/kernel；对比 FP16 基线 |
| 体积与预期不符 | 把 bundle 总量当权重 | 分别统计权重文件与附属文件 |
| 换设备后结果不同 | 不同后端的量化 kernel 实现差异 | 固定后端做对照 |

### 21.5 小结

1. 量化用低位宽换体积与带宽，是有损压缩。
2. block 量化给每小块单独的 scale，避免全局 scale 造成的小值失真。
3. 4-bit 权重把 0.6B 模型从 GB 级降到几百 MB 级；decode 带宽需求同比降低。
4. 代价是精度损失与反量化开销；收益大小取决于瓶颈是带宽还是算力。
5. 不能只比文件大小判断量化优劣，要结合精度与速度。

### 21.6 练习题

**第 1 题**：为什么“整个矩阵一个 scale”在 LLM 权重上效果差？

> 参考答案要点：权重分布存在离群值/层级差异，全局 scale 会让小值量化为 0；分块后每块动态范围小，量化误差显著降低。

**第 2 题**：4-bit 量化把权重带宽降到 1/8，为什么 decode 速度不一定提升 8 倍？

> 参考答案要点：decode 还受 KV cache 读写、激活计算、反量化指令、线程调度、降频等因素限制；带宽只是其中一个瓶颈，Amdahl 定律决定整体提升有限。

**第 3 题**：如何在不解剖模型文件的情况下，粗略验证“模型确实是 4-bit”？

> 参考答案要点：用参数总量 × 理论位宽估算权重体积，与实际权重文件大小对比；若接近 0.5 字节/参数量级则支持 4-bit 判断；同时查模型导出配置中的量化字段（更可靠）。

## 第 22 章 tokenizer 与模型格式

### 22.1 本章要解决什么问题

模型只认数字，不认文字。`"你好"` 怎么变成一串整数？反过来，模型吐出整数，怎么变回文字？这就是 **tokenizer** 的工作。

另外，为什么 llama.cpp 用**一个** `.gguf` 文件，而 MNN 用**一个目录**？两种格式各解决了什么问题？

### 22.2 概念：从直觉到机制

#### 22.2.1 直觉：tokenizer 是“切菜机 + 拼盘机”

**定义**：tokenizer 负责两件事：

- **encode**：文本 → token 序列（每个 token 对应词表里的一个整数 ID）；
- **decode**：token 序列 → 文本。

**类比**：把一整棵白菜切成标准大小的块（encode），做熟后再拼回盘子里（decode）。切法必须和菜谱（模型训练时）一致，否则味道不对。

#### 22.2.2 机制：三种常见切法

| 类型 | 单位 | 优点 | 缺点 |
|---|---|---|---|
| 字符级 | 单个字符 | 词表小 | 序列长，效率低 |
| 词级 | 整词 | 序列短 | 词表爆炸，未登录词无法处理 |
| 子词级（BPE / SentencePiece） | 词片段 | 平衡：词表可控 + 能处理新词 | 需要训练/配套词表 |

现代 LLM 几乎都用子词级。**BPE（Byte Pair Encoding）** 的思路是：从字符开始，反复把最高频的相邻对合并成一个新符号，直到达到目标词表大小。

**关键事实**：tokenizer 与模型**必须配套**。用 A 模型的 tokenizer 去编码 B 模型的输入，得到的 ID 在 B 的词表里含义完全不同，输出必然是乱码。

#### 22.2.3 细节：中文为什么“一个词可能多个 token”

BPE 词表以训练语料的高频片段为单位。中文如果训练语料里以“我们”“可以”这类片段高频出现，它们可能各是一个 token；生僻字或新词会被拆成多个 token 甚至字节级片段。

后果：

- 同样长度的中文和英文，token 数不同；
- `max_tokens` 是 **token 数**，不是字数；
- 计费/限流若按 token 算，中文可能更“贵”。

#### 22.2.4 细节：GGUF 与 `.mnn` 的结构差异

```
GGUF（单文件）
┌──────────────────────────────────────────┐
│ magic + version + tensor 数量             │
├──────────────────────────────────────────┤
│ metadata KV（架构、超参、tokenizer 配置） │
├──────────────────────────────────────────┤
│ tokenizer 词表                            │
├──────────────────────────────────────────┤
│ 对齐填充                                  │
├──────────────────────────────────────────┤
│ tensor 数据（量化权重）                    │
└──────────────────────────────────────────┘
   一个文件 = 自描述 + 自包含

.mnn bundle（目录）
┌──────────────────────────────────────────┐
│ config.json     ← 结构/超参               │
│ 权重文件        ← 张量数据                │
│ tokenizer 相关  ← 词表等                  │
└──────────────────────────────────────────┘
   多个文件 = 分工明确，便于替换/复用
```

[通用原理 + 项目观察]

| 维度 | GGUF 单文件 | `.mnn` 目录 |
|---|---|---|
| 分发 | 一个文件，易拷贝 | 一个目录，需整体搬运 |
| 校验 | 单文件哈希即可 | 需逐文件校验或打包 |
| 可替换性 | 换 tokenizer 要重打包 | 可单独替换词表文件 |
| 加载 | 打开一个文件 | 打开多个文件 |
| 生态 | llama.cpp 主格式 | MNN 主格式 |

**为什么 MNN 选择目录**：MNN 的设计目标覆盖多种模型（CV、NLP、LLM），配置与权重分离更通用；此外 MNN 有自己的模型转换与优化流程，产物天然是多文件。

#### 22.2.5 细节：chat template 为什么单独存在

对话模型需要把多轮消息拼成一个 prompt。不同模型的模板不同：

```
Qwen 风格（示意）：
<im_start>system
你是助手<im_end>
<im_start>user
你好<im_end>
<im_start>assistant
```

**chat template（对话模板）** 就是这个拼接规则。它通常以字符串模板形式存放在 tokenizer 配置里。

wrapper 提供 `mnn_llm_apply_chat_template`。[仓库已核实] 这意味着应用层不必手工拼特殊标记——**手工拼错模板是“模型输出答非所问”的常见原因**。

### 22.3 本项目真实案例

#### 22.3.1 模型目录与有效性判据

本项目 bundle 的判据是“目录内有 `config.json`”。[仓库已核实：`list_bundles`]

这背后的假设是：`config.json` 是 MNN LLM 模型的**入口元数据**，它的存在意味着“这是一个完整的、可加载的 bundle”。如果 tokenizer 文件缺失，`config.json` 仍可能存在——此时加载会成功，但输出会乱。**这说明“入口判据”只能保证最小可加载性，不保证功能完整。**

#### 22.3.2 `mnn_smoke` 如何避免“格式错配”

`mnn_smoke` 启动即检查 `config.json`。[仓库已核实] 它**不会**去猜文件类型，也不会接受任意路径——路径必须是 bundle 目录。这避免了“把 GGUF 目录直接喂进去”的常见误用。

如果你确实把 GGUF 目录传给 MNN，典型表现是：

- 立刻报配置解析失败；或
- 加载成功但输出乱码（如果碰巧字段能解析）。

第二种情况更危险，因为它**不报错**。判别方法：检查输出是否与 prompt 有任何语义关联；完全无关则基本可判定 tokenizer/权重不匹配。

#### 22.3.3 中文场景的实际影响

本项目的提示词是中文（如“你好，请用一句话介绍你自己”）。这带来两个可直接观察的现象：

1. 相同字数下，中文 token 数与英文不同，`prompt_tokens` 不能按字数估算；
2. 若模板/词表不匹配，中文最容易先崩——因为中文子词切分对词表更敏感。

**建议的验证顺序**：

1. 用纯 ASCII 短 prompt（如 `"hello"`）验证链路；
2. 再用中文短句；
3. 最后用长中文 prompt。

这样能把“链路问题”和“编码/模板问题”分离。

### 22.4 常见坑与判别方法

| 错误 / 现象 | 原因 | 处理 |
|---|---|---|
| 输出全是乱码/特殊符号 | tokenizer 与模型不配套 | 用配套词表；检查 bundle 完整性 |
| 输出答非所问 | chat template 未套用或拼错 | 用 `apply_chat_template`，不要手拼 |
| 中文被截断成怪字 | 字节级 token 拼接/解码问题 | 用 decode 全量拼接，而非逐 token 打印 |
| `max_tokens` 到了但字很少 | 中文 token 密度不同 | 按 token 估，不按字数 |
| GGUF 直接喂 MNN 报错 | 格式不兼容 | 用 MNN 转换工具导出 |
| 目录里少一个文件就失败 | bundle 不完整 | 整体校验，不要只查 `config.json` |

### 22.5 小结

1. tokenizer 负责文本 ↔ token 的双向转换，必须与模型配套。
2. 现代 LLM 用子词级切分（BPE/SentencePiece），中文 token 密度与英文不同。
3. GGUF 是自描述单文件，`.mnn` 是分工明确的目录；两者不可混用。
4. chat template 决定多轮消息如何拼成 prompt，手工拼写极易出错。
5. “能加载”不等于“能正确输出”；乱码优先查词表与模板。

### 22.6 练习题

**第 1 题**：为什么同一个中文句子在不同模型上 `prompt_tokens` 可能不同？

> 参考答案要点：词表与切分规则不同，同一片段可能是一个 token 或被拆成多个；特殊标记（如 `<im_start>`）也计入 token 数。

**第 2 题**：GGUF 单文件相比 `.mnn` 目录，在分发和校验上有哪些优势与劣势？

> 参考答案要点：优势是拷贝简单、单哈希可校验、不易漏文件；劣势是替换局部内容需重打包、文件巨大不便增量更新、工具链绑定强。

**第 3 题**：如果模型输出“前言不搭后语”，你会按什么顺序排查？

> 参考答案要点：先确认模型与 tokenizer 配套；再确认 chat template 是否正确套用；再查采样参数是否极端；最后对比同 prompt 在 PC 端的结果，判断是否设备/后端问题。
