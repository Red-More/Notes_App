# 在 Android 上跑起本地大模型

## 副标题：以 Notes_App（Tauri 2 + Rust）接入 MNN 为真实案例，从零理解 FFI、交叉编译与端侧推理

---

## 这本书写给谁

你写过 JavaScript、TypeScript 或 Python，能做前端页面，也能照着文档跑几条命令；但一遇到下面这些东西就心里发虚：

- C++、头文件、链接器、`undefined reference`；
- NDK、ABI、`arm64-v8a`、`android-24`；
- `.a`、`.so`、ELF、`LD_LIBRARY_PATH`；
- 模型文件、量化、KV cache、prefill/decode。

这本书不要求你先学会 C++。它做的事情是：把上面这些词一个个拆开，给出定义、类比、机制、真实命令和真实报错，最后让你能独立完成一条完整链路——

> 在 Windows 上交叉编译 MNN（C++ 推理引擎）→ 产出 ARM64 静态库 → 让 Rust 通过 FFI 调用 → 打包/推送进 Android → 在手机上加载 Qwen3-0.6B 并流式输出。

## 全书目录（细目 + 一句话导读）

### 序言

- **序：这套东西为什么存在** —— 本地大模型不是“把云端 API 搬到本地”这么简单，它要求你同时理解模型、引擎、链接器和手机操作系统。

### 第 0 层：全景图与术语

- **第 0 章 全景图与术语表** —— 先用一张图把七层栈串起来，再给每个术语一个定义和一个生活化类比，后面每一章都回到这张图定位。

### 第一部分：Rust 语言与类型系统（第 1–5 章）

- **第 1 章 所有权、借用与生命周期** —— Rust 用“谁持有、谁借用、借多久”的规则，在编译期替代了 C++ 的手工内存管理。
- **第 2 章 `Result`、`?` 与错误处理** —— C 函数只返回一个布尔值或空指针，Rust 要把这些原始信号翻译成调用者能处理的错误。
- **第 3 章 闭包与回调** —— 流式生成每吐出一个 token 就要回调一次；闭包就是那只随叫随到、还能记住自己小本子的手。
- **第 4 章 `Send/Sync` 与 `!Send`** —— MNN 的 `Llm` 明确不允许跨线程共享，于是项目用一个独占 worker 线程和一个消息通道把它关起来。
- **第 5 章 `#[cfg]` 与条件编译** —— 同一份源码在桌面构建里没有 MNN，在 Android 构建里才有；这不是运行时开关，是编译期裁剪。

### 第二部分：包管理与构建（第 6–10 章）

- **第 6 章 crate、Cargo.toml 与 Cargo.lock** —— 一个 crate 是一块可编译的积木；manifest 说明它需要什么，lock 锁定它实际拿到了什么。
- **第 7 章 feature、optional 依赖与 `dep:`** —— 用 feature 把 NDK、C++ 编译器和 212 MB 静态库挡在默认桌面构建之外。
- **第 8 章 `[[example]]` 与 `required-features`** —— 为什么 `mnn_smoke` 平时不编译，只有显式打开 `local-mnn` 时才出现。
- **第 9 章 workspace 与锁文件** —— 这个项目不是 Cargo workspace；理解 workspace 的边界，才能看懂依赖和锁文件到底属于谁。
- **第 10 章 目标三元组与交叉编译** —— `aarch64-linux-android` 不是一句口号，它决定了编译器、链接器、系统库和指令集。

### 第三部分：Rust 调 C++（FFI，第 11–15 章）

- **第 11 章 `extern "C"` 与 C ABI** —— 两种语言握手，必须约定同一套调用约定、参数布局和返回值规则。
- **第 12 章 C++ name mangling 与 wrapper 层** —— C++ 编译器会把函数名改得面目全非；wrapper 用 `extern "C"` 把名字钉死，顺便把类和异常挡在边界外。
- **第 13 章 build.rs、链接搜索路径与链接顺序** —— `-lmnn` 不是魔法，它只是让链接器去若干目录里找 `libmnn.a`，而且顺序会影响成败。
- **第 14 章 指针与所有权跨语言** —— 谁创建、谁释放、释放几次、释放后还能不能用；跨语言边界上，这些都要写清楚。
- **第 15 章 bindgen** —— 自动生成绑定很诱人，但它读不懂 C++ 模板；本项目为什么选择“手写 C wrapper + 手写少量声明”。

### 第四部分：推理引擎内部（第 16–22 章）

- **第 16 章 模型加载** —— 从 `config.json` 到可用的 `Llm`，中间发生了配置解析、权重读取、内存分配和后端初始化。
- **第 17 章 计算图、算子与后端调度** —— 模型不是一堆矩阵，而是一张有依赖关系的图；后端负责把图上的算子排到 CPU 核上。
- **第 18 章 prefill 与 decode** —— 首 token 慢是因为要一次性读完整个 prompt；后续快是因为每步只处理一个新 token。
- **第 19 章 KV cache 复用** —— 多轮对话不必每次重算历史，键值缓存让“记住上文”变成内存换时间。
- **第 20 章 采样参数** —— logits 只是分数，temperature、top-k、top-p、seed 决定怎么从分数里挑出下一个 token。
- **第 21 章 量化：4-bit block** —— 每个参数只存 4 位，再按小块存缩放因子；0.6B 模型因此从 GB 级降到几百 MB。
- **第 22 章 tokenizer 与模型格式** —— GGUF 是“一个文件装下所有东西”，`.mnn` 是“一个目录装下一套配置、权重和词表”。

### 第五部分：原生库与链接（第 23–27 章）

- **第 23 章 `.a` 与 `.so`** —— `.a` 是零件箱，链接时才挑零件；`.so` 是成品模块，运行时才装载。
- **第 24 章 `-l<name>` 解析规则** —— `libMNN.a` 大写 M 不会被 `-lmnn` 找到；复制/改名是构建流程的一部分，不是多余动作。
- **第 25 章 符号表与裁剪** —— 212.07 MB 的静态库只产出 5.0 MB 程序，因为链接器只拿走真正被引用的目标文件，并丢弃无用 section。
- **第 26 章 头文件、ABI 与 STL 运行时** —— 编译通过只说明声明对得上；能不能链接、运行时能不能找到 `libc++_shared.so` 是另外两件事。
- **第 27 章 静态与动态的取舍** —— 把引擎静态链接进可执行文件，APK 更大但部署更简单；动态库更灵活但加载失败点更多。

### 第六部分：构建工具链（第 28–32 章）

- **第 28 章 CMake 语法要点** —— `target` 是 CMake 的中心；OBJECT library 是“只编译不打包”的零件箱，不能挂 `POST_BUILD`。
- **第 29 章 Ninja** —— 459 个 target 由 Ninja 并行调度；它只关心依赖图和命令，不关心“人类可读”。
- **第 30 章 NDK toolchain、ABI/API level 与 16 KB page** —— 交叉编译的三大开关，决定你的二进制能不能在 Android 15+ 上安装和运行。
- **第 31 章 CMake 4.x policy 与旧工程兼容** —— 新 CMake 不再容忍过旧的 `cmake_minimum_required`；这是策略问题，不是语法问题。
- **第 32 章 Windows 构建与 NDK 探测** —— 真实首因是 NDK 探测顺序命中了残缺版本，`0x80070005` 在真实终端并不出现；旧“覆盖冲突/双写入者”结论已被 A–G 对照实验推翻。

### 第七部分：操作系统与硬件（第 33–39 章）

- **第 33 章 ELF 与 PIE** —— Android 上的可执行文件是 ELF64 AArch64 DYN；`DYN` 不是“动态库”，而是“可重定位的 PIE 可执行文件”。
- **第 34 章 动态库加载与 `LD_LIBRARY_PATH`** —— 程序启动时，`linker64` 按 `DT_NEEDED` 和搜索路径找 `.so`；找不到就停在第一行。
- **第 35 章 Android 沙箱与路径** —— `/data/user/0/<pkg>` 是应用私宅，`/data/local/tmp` 是 shell 的临时工作台；两者权限模型不同。
- **第 36 章 uid 与 SELinux** —— 为什么 `adb push` 进去的文件有时能读不能执行；`ls -Z` 和 `dmesg` 里的 `avc` 是线索。
- **第 37 章 adb 工作流** —— `push`、`shell`、`logcat`、`run-as`、`install`、`am start` 各自解决什么问题。
- **第 38 章 ARM64、NEON 与 FP16** —— 手机 CPU 的向量指令和半精度浮点，决定了量化模型能不能跑得快。
- **第 39 章 线程调度与散热降频** —— 4 线程不一定比 2 线程快；大核、小核、温度墙和功耗墙会重写你的基准测试结论。

## 这本书不做什么

- 不教你训练模型，也不教你写 CUDA kernel。
- 不把 MNN 说成“全面优于 llama.cpp”。第 0 章和第 22 章会给出对照的边界：速度优势来自移动端调度，不代表所有模型、所有设备都更快。
- 不承诺每一个历史数字都能复现。相反，附录 E 会列出“必须重新测量才能引用”的项。
- 不提供“复制即上线”的脚本。构建脚本解决的是可重复性，不是安全审计；许可证、模型来源、内容安全仍需逐项处理。
