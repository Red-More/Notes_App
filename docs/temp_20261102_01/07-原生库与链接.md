## 第 23 章 `.a` 与 `.so`：引擎以什么形态交到你手里

### 23.1 本章要解决什么问题

你从 MNN 源码编出了一个库文件。它要么叫 `libMNN.a`（两百多 MB），要么叫 `libMNN.so`（几十 MB）。这两种文件都能让 Rust 调到 MNN 的函数，但它们的工作方式、出错时机、部署方式完全不同。

本章的目标是让你在看到任意一个 `.a` 或 `.so` 时，能回答四个问题：

- 它里面装的是什么？
- 什么时候被“合并”进我的程序？
- 如果它缺了，我会在哪一步、看到什么报错？
- 我能不能把它拆开看看里面有什么？

### 23.2 概念：从 `.o` 到 `.a`，再到 `.so`

#### 23.2.1 目标文件 `.o`：编译产物的最小单位

**定义**：编译器把一份 `.cpp` 编译成一个**目标文件**（object file，Linux/Android 上后缀 `.o`，Windows 上 `.obj`）。它包含三样东西：

1. **机器码**：真正要执行的指令；
2. **符号表**：这份文件“提供”了哪些函数/变量（已定义符号），又“需要”哪些（未定义符号）；
3. **重定位信息**：机器码里有些地址暂时是空的（比如“调用某个还没确定位置的函数”），链接器要根据最终布局把这些空填上。

**类比**：`.o` 是一道已经做好的菜，但还没装盘。菜本身是完整的，可它占了桌子上哪块位置、旁边配什么，得等摆盘的人（链接器）决定。

**机制上的关键点**：`.o` 里的地址是“相对于本文件”的，不是绝对地址。这就是为什么两个 `.o` 都能各自编译成功，却可能在链接时互相找不到对方——因为“找对方”这件事发生在链接期。

#### 23.2.2 静态库 `.a`：一堆 `.o` 的归档

**定义**：静态库（static library，Unix 上 `lib<name>.a`，Windows MSVC 上 `<name>.lib`）是用 `ar` 打包的一组 `.o`，外加一个**符号索引**（archive index），让你能快速查出“哪个成员定义了某个符号”。

**类比**：`.a` 是一个零件箱。箱子里的每个小盒是一个 `.o`。你要装一台机器（可执行文件），链接器打开箱子，按你列的清单（未定义符号）挑出需要的小盒，其余留在箱子里。

**关键细节（这条决定了第 25 章的全部内容）**：

> 链接器从静态库里“取零件”的最小单位是**整个 `.o`**，不是单个函数。

也就是说，如果 `llm.o` 里定义了 50 个函数、你只用了 1 个，链接器也会把 `llm.o` 整个搬进你的程序。想让“只保留用到的函数”成立，需要编译期配合（`-ffunction-sections`）和链接期配合（`--gc-sections`）。第 25 章会展开。

#### 23.2.3 动态库 `.so`：运行时才接上的共享对象

**定义**：动态库（shared object，Unix/Android 上 `lib<name>.so`，Windows 上 `.dll`）是一个**完整的 ELF 文件**，可以被多个进程在运行时共同装载。它内部保留了完整的符号表和依赖列表，但不预先决定自己会被装到内存的哪个地址。

**类比**：`.so` 是一台可插拔的家电，墙上得有插座（动态加载器 `linker64`），而且家电自己可能还要插别的插座（它的 `DT_NEEDED` 依赖）。

**机制**：程序启动时，内核把可执行文件映射进内存，然后控制权交给**动态加载器**（Android 上是 `/system/bin/linker64`）。加载器读可执行文件的 `.dynamic` 段，按 `DT_NEEDED` 一项项去找依赖的 `.so`，找到就映射、重定位、跑初始化函数；找不到就直接终止，你的 `main` 一行都不会执行。

#### 23.2.4 链接期与加载期：两条完全不同的时间线

```
静态库路线（本项目当前采用）
  源码 .cpp ──编译──> .o ──打包──> libMNN.a
                                      │
  Rust 源码 ──编译──> .o ─────────────┤
                                      ▼
                              链接器（ld / lld）
                                      │  只挑被引用的 .o，填地址
                                      ▼
                              mnn_smoke（一个自包含的可执行文件）

动态库路线（另一种选择）
  源码 .cpp ──编译链接──> libMNN.so ──(打包进 APK / 推送进手机)
                                            │
  Rust 源码 ──编译链接──> 可执行文件（只记录“我需要 libMNN.so”）
                                            │
                                     运行时加载器 linker64
                                            │  按 DT_NEEDED 找文件
                                            ▼
                                     进程真正跑起来
```

两条时间线带来的直接差别：

| 问题 | 静态库 | 动态库 |
|---|---|---|
| 缺库时何时报错 | 链接期（`undefined reference`） | 运行期（`dlopen failed` / 启动即死） |
| 报错离开发者多远 | 几秒内，在终端里 | 可能几小时后，在手机上 |
| 单文件体积 | 大（把用到的代码抄进来） | 小（只留引用） |
| 能否替换库而不重编程序 | 不能 | 能（但 ABI 必须兼容） |
| 多进程共享库代码 | 不能 | 能 |

### 23.3 本项目实例：为什么这里选 `.a`

**构建参数**：MNN 3.6.1 用 NDK `28.2.13676358`、`arm64-v8a`、`android-24` 交叉编译，关键开关是 `MNN_BUILD_SHARED_LIBS=OFF`、`MNN_SEP_BUILD=OFF`、`MNN_BUILD_LLM=ON`。在这一组参数下，产物是静态库 `libMNN.a`，大小 **212.07 MB** `[历史记录]`。

**Rust 侧的选择**：`src-tauri/Cargo.toml` 里写的是

```toml
mnn-rs = { version = "0.1.7", optional = true, default-features = false, features = ["cpu", "static", "llm"] }
```

（`[仓库已核实]`，见 [Cargo.toml](file:///C:/Users/16412/Documents/Github_Repositories/Notes_App-mnn-engine/src-tauri/Cargo.toml#L58-L59)）

这里的 `static` 是 `mnn-rs` 的 feature，最终会变成一条给链接器的指令：

```rust
// mnn-rs-sys build.rs（节选）
let link_type = if use_static { "static" } else { "dylib" };
println!("cargo:rustc-link-lib={}=mnn", link_type);
```

（`[依赖源码已核实]`，见 `mnn-rs-sys-0.1.7/build.rs` 第 545–552 行）

也就是说，实际传给链接器的是 `-l static=mnn`（Rust 的扩展写法），等价于让链接器去 `libmnn.a` 里挑零件。

**为什么这个项目选静态**：

1. **产物只有一个可执行文件**。`mnn_smoke` 是为了在真机上跟 llama.cpp 路线做同口径对照，越小越少变量越好：`adb push` 一个文件、`LD_LIBRARY_PATH=.` 只用来自 `.`，没有“少推一个 `.so` 就启动失败”的风险。
2. **APK 打包路径更短**。如果走动态库，Android 侧必须把 `libMNN.so` 放进 `src/main/jniLibs/arm64-v8a/`，还要保证它被 Gradle 的 `mergeJniFolders` 收进去、名字不被改写、16 KB 对齐满足要求。静态链接把这些检查点全部前置到了链接期。
3. **崩溃面更小**。动态库的失败点分布在“打包、安装、加载、符号解析”四个阶段；静态库只剩“链接”一个阶段。

**这个选择的代价**：

- 每次改引擎都要重新链接整个 Rust 程序，链接时间和磁盘占用都更高；
- 无法在不重新编译的情况下替换引擎；
- 静态库与 Rust 代码共用同一份进程地址空间，一个 C++ 静态初始化错误会直接带崩 Rust 进程，没有隔离。

### 23.4 常见坑与判别方法

| 现象 | 原因 | 判别与处理 |
|---|---|---|
| `file libMNN.a` 显示 `current ar archive`，但 `llvm-nm` 查不到符号 | 归档里是 LLVM **bitcode**（LTO 产物），不是原生机器码 | `llvm-ar t libMNN.a` 看成员后缀；若为 `.bc`，需要匹配的 LTO 插件或改用 `-DCMAKE_INTERPROCEDURAL_OPTIMIZATION=OFF` 重编 |
| `file libMNN.a` 显示 `thin archive` | 用了 `ar rcsT`（thin 模式），只存路径不存内容 | thin archive 不能跨机器移动；重建时去掉 `T` |
| 链接报 `undefined reference to 'MNN::Transformer::Llm::create(...)'`，但 `nm` 明明有 | 这个符号在被链接的 `.o` 里是**未定义引用**，提供方没被拉进来（顺序问题或没写 `-lmnn`） | 见第 24 章：先确认 `-lmnn` 生效，再检查链接顺序 |
| 手机上启动即 `cannot execute: required file not found` | 二进制依赖的 `.so` 找不到（静态库路线通常不会出现，出现说明有动态依赖漏了） | 用 `llvm-readelf -d mnn_smoke` 看 `NEEDED` |
| `.a` 有 212 MB，但链接时提示某个 `MNN::...` 符号不存在 | 构建参数没开对应模块（例如 `MNN_BUILD_LLM=OFF` 时根本没有 LLM 引擎） | 回到 CMake cache 检查 `MNN_BUILD_LLM`；`llvm-nm -C libMNN.a \| Select-String "Transformer::Llm"` 应能命中 |

### 23.5 小结

1. `.o` 是最小编译单元；`.a` 是 `.o` 的归档；`.so` 是可在运行时装载的完整 ELF。
2. 静态库在**链接期**被“按成员挑选”合并；动态库在**加载期**被整体装载。两者的报错时机和排查工具完全不同。
3. 静态库的挑选粒度是 `.o`，不是函数。理解这一点才能真正解释“212 MB → 5 MB”。
4. 本项目的 `static` feature 落到链接器上就是 `-l static=mnn`；它换来的是一份自包含的可执行文件。
5. 判断一个库文件到底是什么，先 `file`，再 `llvm-ar t`，最后 `llvm-nm`，三步足够。

### 23.6 练习题

**第 1 题**：给你一个 60 MB 的 `libfoo.a`，你的程序只调用其中一个函数，产出的可执行文件却也有 60 MB。列出至少两个可能原因，并说明各自怎么验证。

**参考答案要点**：
- 原因一：链接器按 `.o` 取成员，那个函数所在的 `.o` 很大（比如把整个模块编进一个文件）。验证：`llvm-nm -S --defined-only libfoo.a` 看该符号所在成员的体量；`llvm-ar t` 看成员列表。
- 原因二：没有 section 级裁剪（缺少 `-ffunction-sections`/`--gc-sections`）。验证：重新链接时加 `-Wl,--print-gc-sections`，观察是否有大量 section 被丢弃。
- 原因三（加分）：产物没 strip，调试信息占大头。验证：`llvm-size` 看 `debug_*` 段，或对比 `llvm-strip` 前后体积。

**第 2 题**：某一个符号在 `llvm-nm libMNN.a` 里显示为大写 `T`，在你的可执行文件里显示为小写 `t`。这说明什么？

**参考答案要点**：
- `nm` 的类型字母区分“外部可见（大写）”与“本地/内部（小写）”。
- 从 `T` 变 `t` 说明在最终链接时该符号被本地化（localize），常见于 `-Wl,--exclude-libs`、visibility 设置或 `--gc-sections` 后的内部化。
- 对调用方的影响：如果 Rust 侧通过 `extern "C"` 直接引用它，本地化会导致链接失败；如果只是内部调用，无影响。

**第 3 题**：如果把这个项目从静态改成动态链接，列出 Android 侧最少需要额外处理的三件事。

**参考答案要点**：
- 把 `libMNN.so` 及它的依赖放进 `src-tauri/gen/android/app/src/main/jniLibs/arm64-v8a/`（并确保 Gradle 能合并进去）。
- 用 `llvm-readelf -d libMNN.so` 检查 `DT_NEEDED` 与 `SONAME`，确认所有依赖都在包里。
- 检查 16 KB page 对齐（`llvm-readelf -l` 的 LOAD 段 `Align`），否则 Android 15+ 设备可能装不上或跑不起来。
- 需要的话再加 APK 里的 `android:extractNativeLibs` / `useLegacyPackaging` 相关配置。

## 第 24 章 `-l<name>` 的解析规则：为什么 `-lmnn` 找不到 `libMNN.a`

### 24.1 本章要解决什么问题

你确定文件就在那个目录里，链接器却说 `cannot find -lmnn`。这不是链接器“看不到文件”，而是它在按一套固定的命名规则找文件，而你手里的文件名不匹配。

本章要让你能准确预测：

- `-lfoo` 会去找哪几个文件名？
- 目录里同时有 `libfoo.so` 和 `libfoo.a` 时会选哪个？
- 两个库互相依赖时，为什么顺序会决定成败？
- 本项目为什么要在 staging 目录里把 `libMNN.a` **复制**一份叫 `libmnn.a`？

### 24.2 概念：`-L` 是目录，`-l` 是名字模板

**定义**：链接器的两个相关参数：

- `-L<dir>`：把 `<dir>` 加入**搜索目录列表**（Rust 里对应 `cargo:rustc-link-search=native=<dir>`）；
- `-l<name>`：在搜索目录里找名为 `lib<name>.a` 或 `lib<name>.so` 的文件。

**类比**：`-L` 是告诉前台“去这三排货架找”，`-l` 是“找标签上写着 `libmnn` 的那盒”。你手里的盒子标签写的是 `libMNN`，前台当然说没有。

**展开规则（Unix/Android，GNU ld 与 lld 一致）**：

| 你写的 | 链接器实际查找的文件名（按顺序） | 说明 |
|---|---|---|
| `-lmnn` | `libmnn.so` → `libmnn.a` | 默认优先动态库 |
| `-l:libMNN.a` | 精确匹配 `libMNN.a` | 冒号形式，不做 `lib` 前缀和扩展名展开 |
| `-static -lmnn` | `libmnn.a` | 强制静态 |
| `-Bdynamic -lmnn` | `libmnn.so` | 强制动态 |
| `-l static=mnn`（Rust） | `libmnn.a` | Rust 的写法，直接指定类型 |

**MSVC 是另一套规则**：`foo.lib`，没有 `lib` 前缀，也没有 `.a`。所以 `mnn-rs-sys` 在 Windows 上分了两条路：

```rust
// mnn-rs-sys build.rs（节选）
if target_os == "windows" && target_env == "gnu" {
    println!("cargo:rustc-link-lib={}=MNN", link_type);   // MinGW：大写 MNN
} else {
    println!("cargo:rustc-link-lib={}=mnn", link_type);   // 其他：小写 mnn
}
```

（`[依赖源码已核实]`，第 546–552 行）

注意 MinGW 分支用的是 **`MNN`**（大写）。这说明库文件名的大小写在 Windows/MinGW 语境下曾经是个真实问题——Linux 与 Android 的文件系统区分大小写，`libMNN.a` 和 `libmnn.a` 是两个不同文件。

**链接顺序**：静态链接是“从左到右处理命令行上的库，每次只解决当时还缺的符号”。所以：

- 提供方要放在使用方**后面**（`gcc main.o -lmnn -lc++_static`，而不是反过来）；
- 两个库互相引用时，要么重复写一遍，要么用 `-Wl,--start-group ... -Wl,--end-group` 让链接器反复扫描。

**类比**：你在装机器，清单式装配——先拿起主机（`main.o`），发现缺螺丝（未定义符号），才去翻零件箱。如果零件箱先被翻过了，后面才发现缺螺丝，就没人再翻了。

### 24.3 本项目实例：staging 里的那次复制

项目的实际链路是“预编译 MNN + 手工 staging”，而不是让 `mnn-rs-sys` 自己从源码构建。原因很实际：从源码构建一次要 20 分钟量级，而实验需要反复重编 Rust 侧。

`mnn-rs-sys` 的 `build.rs` 支持一条最高优先级的路径：

```rust
let (lib_dir, include_dir) = if mnn_lib_dir.is_some() && mnn_include_dir.is_some() {
    (mnn_lib_dir.as_ref().map(PathBuf::from), mnn_include_dir.as_ref().map(PathBuf::from))
} else if use_prebuilt && !build_from_source {
    ...
```

（`[依赖源码已核实]`，第 264–272 行）

只要同时设置 `MNN_LIB_DIR` 与 `MNN_INCLUDE_DIR`，它就不再下载预编译包、也不再跑 CMake，直接用你给的目录。

于是 staging 目录必须满足两个条件：

1. 库文件名能被 `-l static=mnn` 解析 → 必须是 `libmnn.a`；
2. include 目录里要有 wrapper 编译所需的全部头文件（含 `llm/llm.hpp`）。

**原始记录**是：把 `libMNN.a` 复制为 `libmnn.a`，并手工拼装 include `[历史记录]`。原始 staging 目录名没有留存；书中统一用下面的等价布局，命令里的路径请换成你自己的：

```
%USERPROFILE%\mnn-stage\arm64-v8a\
├─ lib\
│  └─ libmnn.a          ← 由 libMNN.a 复制改名（212.07 MB → 同名副本）
└─ include\
   ├─ MNN\
   │  ├─ Interpreter.hpp
   │  ├─ Tensor.hpp
   │  └─ ...
   └─ llm\
      └─ llm.hpp          ← LLM 引擎头，容易漏
```

**为什么“复制”而不是“重命名”**：

- 构建目录里的 `libMNN.a` 是 CMake 的产物，保留原名便于以后对照 CMake 的 `install` 规则与日志；
- staging 是**派生目录**，可以整个删除重建，不影响构建目录；
- 如果以后要同时保留 `libMNN.so`（动态实验），复制比改名更安全。

**为什么容易漏 `llm/llm.hpp`**：MNN 的 `install` 规则历史上并不总是把 `transformers/llm/engine/include/llm` 下的头文件装进 `include/`。第 28 章会讲，这正是 `POST_BUILD` 那段 `copy_directory` 存在的原因。`mnn-rs-sys` 编译 `mnn_llm_wrapper.cpp` 时必须能 `#include <llm/llm.hpp>`，缺了就在编译期报 `fatal error: 'llm/llm.hpp' file not found`。

**Rust 侧怎么把这两个目录喂进去**：环境变量在 `cargo build` 时传入。PowerShell：

```powershell
$env:MNN_LIB_DIR     = "$env:USERPROFILE\mnn-stage\arm64-v8a\lib"
$env:MNN_INCLUDE_DIR = "$env:USERPROFILE\mnn-stage\arm64-v8a\include"
cargo build --target aarch64-linux-android --release --features local-mnn --example mnn_smoke
```

逐个参数说明：

- `MNN_LIB_DIR`：告诉 `build.rs` 往 `cargo:rustc-link-search=native=` 里加哪个目录；
- `MNN_INCLUDE_DIR`：告诉 `build.rs` 编译 C++ wrapper 时 `-I` 加哪个目录；
- `cargo build`：只编译，不运行；
- `--target aarch64-linux-android`：交叉编译到 Android ARM64（第 10 章讲过三元组）；
- `--release`：优化构建；MNN 是 Release 编译的，混用 Debug 的 Rust 不影响 ABI，但会让性能数据失真；
- `--features local-mnn`：打开那个 optional 依赖；
- `--example mnn_smoke`：只构建这个示例（第 8 章讲过 `required-features`）。

**验证链接确实用了你的 staging**，而不是悄悄下载了预编译包：

```powershell
cargo build -v --target aarch64-linux-android --release --features local-mnn --example mnn_smoke 2>&1 |
  Select-String "rustc-link-search|rustc-link-lib|mnn_wrapper"
```

`-v` 会把 `build.rs` 打印的 `cargo:` 指令显示出来。你应该看到类似：

```
cargo:rustc-link-search=native=C:\Users\...\mnn-stage\arm64-v8a\lib
cargo:rustc-link-lib=static=mnn
```

如果看到的是 `mnn-prebuilt` 之类字样，说明环境变量没生效（常见原因：在新终端里忘了设，或者只设了一个）。

### 24.4 常见坑与判别方法

| 错误信息 | 真实原因 | 排查路径 |
|---|---|---|
| `error: linking with 'cc' failed ... cannot find -lmnn` | 搜索目录里没有 `libmnn.a` / `libmnn.so` | ① `dir` 确认文件名；② `cargo build -v` 确认 `rustc-link-search` 指向它；③ 检查是否只在 PowerShell 里设了变量而子进程没继承 |
| `undefined reference to 'MNN::Transformer::Llm::create(...)'` | `-lmnn` 生效了，但那个符号所在的 `.o` 没被拉入（顺序/未引用） | ① `llvm-nm -C libmnn.a \| Select-String "Llm::create"` 看符号存在且为 `T`；② 检查链接顺序（Rust 场景下多为库顺序或 `-Wl,--as-needed`） |
| `file format not recognized` | 拿 x86_64 的库给 ARM64 链接器，或给了文本文件 | `file libmnn.a`、`llvm-readelf -h` 看 `Machine: AArch64` |
| 链接成功但手机上 `undefined symbol: _ZN3MNN...` | 动态链接时库版本不匹配（符号在新库里被去掉/改名） | `llvm-readelf --dyn-syms libMNN.so` 对比；这在静态路线不会出现 |
| `cannot find -lMNN`（大写） | 沿用了 CMake 或某些示例里的写法 | Rust 侧不要写大写；`-l` 的名字由 `build.rs` 决定，不要在 `build.rs` 之外手写链接参数 |
| 改了 staging 里的库，重编没生效 | Cargo 有缓存，`build.rs` 没声明 `rerun-if-changed` 对库文件的依赖 | `cargo clean -p mnn-rs-sys` 后重编；库的变更不参与指纹时，这是唯一可靠办法 |

### 24.5 小结

1. `-L` 给目录，`-l` 给名字模板：`-lfoo` → `libfoo.so` / `libfoo.a`；精确文件名要用 `-l:libfoo.a`。
2. 默认优先动态库；Rust 用 `-l static=foo` 或 `-l dylib=foo` 明确类型。
3. Linux/Android 区分大小写，`libMNN.a` 不会被 `-lmnn` 找到——本次复制改名是构建流程的必要一环，不是多余动作。
4. 静态链接对顺序敏感：使用方在前，提供方在后。
5. 环境变量 `MNN_LIB_DIR` / `MNN_INCLUDE_DIR` 是这条链路的入口；验证方式是 `cargo build -v` 看 `cargo:` 指令，而不是猜。

### 24.6 练习题

**第 1 题**：目录里同时有 `libmnn.a` 和 `libmnn.so`，链接命令是 `clang++ main.o -L. -lmnn`。最终链接的是哪一个？如果想让静态库一定被选中，写出两种写法。

**参考答案要点**：
- 默认选 `libmnn.so`（动态优先）。
- 写法一：`-static -lmnn`；写法二：`-l:libmnn.a`（精确文件名）。Rust 侧对应 `-l static=mnn`。

**第 2 题**：为什么 `mnn-rs-sys` 在 Windows + MinGW 分支要用大写 `MNN`？

**参考答案要点**：
- MinGW 生态里 MNN 的静态库历史上被命名为 `libMNN.a`（大写），与 Unix 的 `libmnn.a` 不一致；
- 该分支是对历史命名的兼容，不是“Windows 特有大写规则”；
- 若你手工 staging 到 Windows，同名文件要按分支要求命名，否则 `cannot find -lMNN`。

**第 3 题**：你设置了 `MNN_LIB_DIR` 和 `MNN_INCLUDE_DIR`，构建却仍去下载预编译包。按可能性从高到低列出三种原因。

**参考答案要点**：
- 只设了其中一个（代码要求两个都 `Some` 才走环境变量分支）。
- 环境变量设在父 shell，但构建发生在 IDE/其他进程里，没有继承。
- `build.rs` 没有因环境变量变化而重跑（Cargo 指纹缓存），需要 `cargo clean -p mnn-rs-sys` 或 touch。

## 第 25 章 符号表与裁剪：212 MB 的库，5 MB 的程序

### 25.1 本章要解决什么问题

`libMNN.a` 有 212.07 MB `[历史记录]`，而链接出来的 `mnn_smoke` 只有 5.0 MB `[历史记录]`。这个比例容易让人产生两种相反的错误判断：

- “是不是库根本没链进去？”（如果没链进去，运行时就会立刻报错或链接期就失败）
- “是不是链接器只抄了 2% 的代码，所以功能不全？”（功能是否齐全要看符号，不看体积）

本章要让你能用工具证明三件事：

1. 可执行文件里确实有 MNN 的 LLM 代码；
2. 那 207 MB 去了哪里；
3. 如果体积异常（该小的不小、该有的没有），从哪一层开始查。

### 25.2 概念：符号表、符号类型与裁剪粒度

#### 25.2.1 符号表

**定义**：符号表是“名字 → 地址/大小/类型”的映射。ELF 里常见的两张：

- `.symtab`：链接期用的完整符号表，可以 `strip` 掉；
- `.dynsym`：动态链接用的符号表，运行时必需，不能随便删。

**类比**：`.symtab` 是施工图纸上标注的所有管线位置，完工后可以收起来；`.dynsym` 是大楼门口的导览牌，访客（动态加载器）必须看得见。

#### 25.2.2 `nm` 的类型字母

`llvm-nm` 输出的每一行形如：

```
0000000000012a40 T _ZN3MNN11Transformer3Llm6createERKNSt6__ndk112basic_string...
```

三列：地址、类型、名字。类型字母的关键区别：

| 字母 | 含义 | 大小写差异 |
|---|---|---|
| `T` / `t` | 代码段（text）里的符号 | 大写=外部可见，小写=本地 |
| `D` / `d` | 已初始化数据段 | 同上 |
| `B` / `b` | 未初始化数据段（bss） | 同上 |
| `U` | **未定义**，需要别人提供 | 只有大写 |
| `W` / `w` | 弱符号 | 可被覆盖 |

**这一条极其重要**：`U` 不代表“库里有这个函数”，恰恰相反，它表示“这个 `.o` 需要别人提供这个函数”。排查 `undefined reference` 时，先分清你要找的符号在库里是 `T` 还是 `U`。

#### 25.2.3 C++ 名字修饰（mangling）

C++ 编译器要把 `MNN::Transformer::Llm::create` 这种带命名空间、参数类型的名字编码成一个合法标识符，才能放进符号表。Itanium ABI（Linux/Android/macOS 通用）的规则大致是：

```
MNN::Transformer::Llm::create(std::string const&)  →  _ZN3MNN11Transformer3Llm6createERKNSt6__ndk112basic_string...
```

拆开看：

- `_Z`：修饰前缀；
- `N`：嵌套名字开始；
- `3MNN`：长度 3 的 `MNN`；
- `11Transformer`：长度 11 的 `Transformer`；
- `3Llm`：长度 3 的 `Llm`；
- `6create`：长度 6 的 `create`；
- `E`：嵌套名字结束；
- 后面是参数类型编码。

**为什么它重要**：

1. 你在 `extern "C"` 里写的名字**不会**被这样修饰，所以 C 和 C++ 才能对上（第 11、12 章）；
2. 搜索符号时必须加 `-C`（demangle），否则你搜 `MNN::Transformer::Llm` 永远搜不到；
3. 不同编译器/标准库版本可能产生不同编码（比如 `std::__ndk1` 与 `std::__1`），这属于 ABI 问题（第 26 章）。

#### 25.2.4 裁剪的三个层次

体积从 212 MB 降到 5 MB，不是一次操作，而是三层过滤叠加：

```
第 1 层：归档成员级（链接器默认行为）
  libMNN.a 里有 N 个 .o，只把“能解决当前未定义符号”的成员搬进来
  → 一个 .o 里只要有 1 个函数被用到，整个 .o 都会进来

第 2 层：section 级（需要编译期配合）
  .o 内按函数/数据分 section（-ffunction-sections -fdata-sections），
  链接器再用 --gc-sections 丢掉没人引用的 section
  → 这是“一个 .o 里只用 1 个函数也能只保留 1 个函数”的前提

第 3 层：符号与调试信息级（strip）
  删除 .symtab、调试段，只留运行必需内容
  → 不影响功能，但会影响后续能否 nm/addr2line 定位
```

**注意一个事实**：本次 `mnn_smoke` 能 `nm` 出 147 行 LLM 符号 `[历史记录]`，说明它**没有**做第 3 层（否则 `.symtab` 被删，`nm` 会报 `no symbols`）。所以 5.0 MB 是“成员级 + section 级”裁剪后的结果，不含 strip 收益。

### 25.3 本项目实例：用三组命令证明“MNN 真的在里面”

#### 25.3.1 证明一：可执行文件里有 LLM 符号

```powershell
& "$TOOLS\llvm-nm.exe" -C .\mnn_smoke |
  Select-String "MNN::Transformer::Llm" |
  Measure-Object -Line
```

参数逐个说明：

- `llvm-nm.exe`：列符号表的工具（NDK 自带，避免用 MSVC 的 `dumpbin`，两者格式不同）；
- `-C`：把修饰名还原成 `MNN::Transformer::Llm::...` 这种可读形式；
- `.\mnn_smoke`：被检查的 ELF 文件（**必须在宿主机上检查**，手机上通常没有 `nm`）；
- `Select-String`：PowerShell 的文本过滤，等价于 `grep`；
- `Measure-Object -Line`：数行数。

历史记录的结果是 **147 行** `[历史记录]`。这个数字的意义不是“MNN 有 147 个函数”，而是“最终二进制里能 nm 到的、名字包含 `MNN::Transformer::Llm` 的符号行数”。它能证明 LLM 引擎被链接进来了。

#### 25.3.2 证明二：它只依赖 5 个系统库

```powershell
& "$TOOLS\llvm-readelf.exe" -d .\mnn_smoke |
  Select-String "NEEDED"
```

`-d` 表示 dump `.dynamic` 段。历史记录的输出包含且仅包含：

```
libc++_shared.so
liblog.so
libc.so
libdl.so
libm.so
```

`[历史记录]`。这五个都是 Android 平台自带或随包提供的运行库，没有 `libMNN.so`、没有 `libllm.so`——这正是静态链接的直接证据。

**注意**：这里出现 `libc++_shared.so` 与第 26 章要讲的 `c++_static` 声明存在张力，第 26 章会专门处理，并标注“未复核”。

#### 25.3.3 证明三：体积分布在哪里

```powershell
& "$TOOLS\llvm-size.exe" .\mnn_smoke
& "$TOOLS\llvm-readelf.exe" -S .\mnn_smoke | Select-Object -First 40
```

- `llvm-size`：按 `text`（代码）、`data`（已初始化数据）、`bss`（未初始化数据）三列汇总；
- `-S`：列 section 头表，能看到每段的名字、类型、大小。

本次构建的 `llvm-size` 具体输出没有留存，`[未复核]`。要复核，重跑上面两条命令即可；判断标准：`text` 应在数 MB 量级，`bss` 可能很大（MNN 的静态缓冲、线程池、KV cache 相关结构可能落在 bss，但 bss 不占文件体积）。

#### 25.3.4 207 MB 去哪了：逐项拆解

| 去向 | 机制 | 能否避免 |
|---|---|---|
| 未被引用的归档成员 | 链接器按需取 `.o`；转换工具、训练模块、其他后端（OpenCL/Vulkan/Metal/CUDA）没有被 LLM 推理路径引用 | 默认就会省略；`MNN_BUILD_SHARED_LIBS=OFF` 且不打开那些后端时本来就没编进来 |
| 被引用成员里的无关函数 | 成员粒度取用；同一个 `.o` 里其他函数一并进入 | 需要 `-ffunction-sections` + `--gc-sections` |
| 调试信息 | Release 下 MNN 可能仍保留部分调试/符号信息 | `strip` / `-g0` |
| 重复的模板实例化与内联代码 | C++ 模板在每个使用点生成代码 | 部分可用 `-Os` / LTO 缓解，但会影响性能 |
| 静态数据（大表） | 量化反量化查表、算子注册表 | 通常无法避免，属必要数据 |

**关键提醒**：5.0 MB 这个数字**不能**当作“MNN 只占 5 MB”的结论。它只说明“这一个示例程序用到的那部分 MNN，裁剪后是 5 MB”。换一个后端（例如打开 OpenCL）、换一个模型结构，体积会变。

### 25.4 常见坑与判别方法

| 现象 | 原因 | 排查路径 |
|---|---|---|
| `llvm-nm: error: ... no symbols` | 二进制被 strip 了 | `llvm-readelf -S` 看有没有 `.symtab`；需要符号就重编，不要对调试产物 strip |
| `nm` 能看到符号，但链接时报 undefined | 你看到的可能是同名的弱符号或另一个 ABI 版本 | `llvm-nm -C -S` 看符号大小与所属成员；`llvm-readelf -s` 看 `Bind`（GLOBAL/WEAK） |
| 程序体积没有下降，反而接近库大小 | 某个“锚点”把大量 `.o` 拉进来了（全局对象、静态注册表、`__attribute__((constructor))`） | 用 `-Wl,-Map=map.txt` 生成链接映射，搜大段来源；或 `-Wl,--print-gc-sections` |
| `--gc-sections` 加了却没效果 | 编译时没开 `-ffunction-sections -fdata-sections`，section 粒度仍是整个 `.o` | 检查 MNN 的 `CMAKE_CXX_FLAGS`；或接受成员级裁剪 |
| `llvm-nm` 读 Windows 的 `.lib` 报格式错 | `.lib`（COFF）与 `.a`（ELF ar）不同 | Windows 上用 `dumpbin /symbols`；跨平台检查统一在 Linux/Android 产物上做 |
| 147 个符号“看起来太少” | 很多函数被内联，或被编译器优化成局部符号 | 用 `llvm-nm -a` 连本地符号一起看；或用 `llvm-objdump -d` 反汇编确认代码存在 |

### 25.5 小结

1. 静态库裁剪的第一层是“按 `.o` 取成员”，第二层才是“按 section 丢函数”，第三层是 strip。
2. `nm` 的 `T` 与 `U` 是排查链接问题最重要的两个字：`U` 是“我需要”，不是“我有”。
3. C++ 符号必须 demangle（`-C`）后再搜索；`std::__ndk1` 这类前缀是 ABI 线索。
4. 本次产物 5.0 MB、147 行 LLM 符号、5 个 `NEEDED` 系统库，三者互相印证“LLM 被静态链接进来了” `[历史记录]`。
5. 体积不是功能指标。判断功能看符号与运行结果，判断体积看 section 与映射文件。

### 25.6 练习题

**第 1 题**：`llvm-nm -C mnn_smoke | Select-String "U "` 里出现 `MNN::Transformer::Llm::create`。这意味着什么？为什么它还能正常运行？

**参考答案要点**：
- `U` 表示该符号在这个 ELF 里是未定义引用；但完整输出里应同时存在 `T` 的定义，`nm` 会把定义与引用分别列出（同一个名字可能既有一行 `T` 又有一行 `U`，来自不同调用点）。
- 若只有 `U` 没有 `T`，静态链接不可能成功；能运行说明 `T` 存在，只是 `Select-String` 的过滤把它筛掉了。

**第 2 题**：你想把 5 MB 再压到 3 MB，列出三种手段，并说明各自的风险。

**参考答案要点**：
- `strip`（删 `.symtab`/调试段）：风险是崩溃后无法 `addr2line`，也无法 `nm` 排查。
- `-Os` 重编 MNN：风险是推理性能下降，且与 llama.cpp 的对照数据失去可比性。
- 关闭未用后端/模块（例如 OpenCL、图像处理）：风险是功能缺失；必须确认 LLM 路径不依赖。
- 加分：`--gc-sections` 前提确认；LTO（跨静态库较麻烦，可能需 bitcode 归档）。

**第 3 题**：给出一个命令序列，用来判断“某个符号到底是库里有定义，还是只是被引用”。

**参考答案要点**：
```powershell
& "$TOOLS\llvm-nm.exe" -C <lib或可执行文件> | Select-String "符号名"
& "$TOOLS\llvm-readelf.exe" -s <文件> | Select-String "符号名"   # 看 Bind/Type/Ndx
```
- `nm` 看类型字母：`T/t/D/B` 为定义，`U` 为引用；
- `readelf -s` 看 `Type`（FUNC/OBJECT）、`Bind`（GLOBAL/WEAK）、`Shndx`（`UND` 表示未定义）。

## 第 26 章 头文件、ABI 与 STL 运行时

### 26.1 本章要解决什么问题

“编译通过、链接通过、手机上闪退”是跨语言工程里最常见的三段式故障。三段分别检查不同的东西：

- 编译期检查**声明**是否一致（头文件）；
- 链接期检查**名字与地址**是否能对上（符号）；
- 运行期检查**二进制布局与运行时库**是否兼容（ABI + STL）。

本章把这三层讲清，并解释本项目里一个必须标注“未复核”的细节：产物 `NEEDED` 里出现了 `libc++_shared.so`，而依赖的构建脚本明明要求 `c++_static`。

### 26.2 概念

#### 26.2.1 头文件：只是一份“菜单”

**定义**：头文件（`.h` / `.hpp`）里放的是**声明**：函数签名、类的成员布局、枚举值、宏。它不含地址，也不含实现。

**类比**：头文件是餐厅菜单。菜单告诉你“有这道菜、叫什么、多少钱”，但不告诉你厨房怎么做的。你照着菜单点菜（编译），厨房（库）得真的会做（链接）。

**为什么头文件必须与库严格配套**：

1. **结构体大小与字段偏移**：如果库是用旧头文件编译的（结构体 5 个字段），你的代码用新头文件（6 个字段），运行时读写就会错位。这类错误不会在编译或链接期暴露，只会表现为“数据莫名其妙不对”或段错误。
2. **枚举与常量**：`enum` 的值被直接编进机器码；头文件与库版本不一致时，传进去的枚举值含义就变了。
3. **内联函数**：头文件里 `inline` 的函数会被编进你的 `.o`；如果它内部依赖库的私有布局，版本不一致会直接崩。
4. **类模板**：模板定义全在头文件里，实例化发生在你的编译单元；这也是 bindgen 无法处理 C++ 模板的根本原因（第 15 章）。

#### 26.2.2 ABI：二进制接口

**定义**：ABI（Application Binary Interface，应用二进制接口）是“两个已编译的二进制模块之间如何互相调用”的约定，至少包括：

- **调用约定**：参数放寄存器还是栈、谁清理栈、返回值怎么传；
- **名字修饰**：C++ 的 mangling 规则；
- **类型布局**：`struct` 对齐、`bool`/`long` 宽度、位域顺序；
- **异常与 RTTI 模型**：抛出异常时栈怎么展开、类型信息怎么表示；
- **标准库 ABI**：`std::string`、`std::vector` 的内部布局，以及实现它们的运行时库版本。

**类比**：ABI 是两个人握手的规则——用哪只手、握几下、力道多大。规则不一致，两只手就是握不上，哪怕两边都很热情。

**关键结论**：

> `extern "C"` 只统一了“名字修饰”和部分调用约定，**不统一类型布局，也不统一 STL**。

所以跨语言边界的安全做法是：边界上只用 C 兼容类型（`int32_t`、`void*`、`const char*`），把 C++ 对象藏在 wrapper 内部（第 12、14 章）。

#### 26.2.3 Android 上的 STL 运行时

Android NDK 提供 libc++，三种形态：

| 形态 | 产物 | 部署方式 | 特点 |
|---|---|---|---|
| 静态 | `libc++_static.a` | 链接进你的二进制 | 无需额外 `.so`；每个二进制各带一份，多库时体积重复 |
| 共享 | `libc++_shared.so` | 随 APK 打包，进程内唯一一份 | 体积省；但必须保证整个 APK 只有一个版本 |
| 系统（旧） | `libstdc++.so`（历史） | 系统自带 | NDK 早已不再默认使用，不要指望 |

**NDK 的选择项**：CMake 里 `-DANDROID_STL=c++_static` 或 `c++_shared`；直接调 clang++ 时用 `-stdlib=libc++` 配合链接具体库文件。

**一条硬规则**：一个进程里不能同时存在两份 libc++（静态 + 共享，或两个不同版本的共享）。这会导致 ODR（One Definition Rule，单一定义规则）冲突，表现为随机的诡异崩溃——同一个 `std::string` 在两份实现眼里布局不同。

`mnn-rs-sys` 的构建脚本在 Android 分支写的是：

```rust
if cfg!(feature = "android") || target_os == "android" {
    println!("cargo:rustc-link-lib=c++_static");
    println!("cargo:rustc-link-lib=log");
    println!("cargo:rustc-link-lib=c");
    ...
}
```

（`[依赖源码已核实]`，第 1522–1528 行）

同时它给 MNN 的 CMake 传 `-DANDROID_STL=c++_static`（第 1183 行）。从这两处看，作者的设计意图是**全静态 STL**。

#### 26.2.4 三层检查各自会漏掉什么

| 阶段 | 检查内容 | 漏掉的东西 |
|---|---|---|
| 编译 | 头文件里的声明是否匹配调用 | 库的实际实现、结构体真实布局（头文件可能过期） |
| 链接 | 符号能否解析、地址能否重定位 | 运行时库是否存在、ABI 细节是否一致、初始化顺序 |
| 运行 | 依赖能否加载、构造/析构是否正常 | 只有在特定输入/特定设备上才暴露的问题 |

### 26.3 本项目实例

#### 26.3.1 头文件：staging 必须自带 `llm/llm.hpp`

`mnn-rs-sys` 编译 wrapper 的关键片段：

```rust

if cfg!(feature = "llm") && llm_wrapper_cpp.exists() {
    build.file(&llm_wrapper_cpp);

    panic!("mnn-sys: 'llm' feature enabled but mnn_llm_wrapper.cpp is missing (corrupted checkout)");
}
```

（`[依赖源码已核实]`，第 405–424 行）

wrapper 要能编译，`include_dir` 里必须有 `llm/llm.hpp`。本次 staging 是手工拼装的（`[历史记录]`），这也是第 24 章强调“容易漏”的原因。

**缺头文件的典型报错**：

```
error: 'llm/llm.hpp' file not found
```

排查路径：

1. `dir "$env:MNN_INCLUDE_DIR\llm"` 确认文件在；
2 `cargo build -v` 看 `build.rs` 打印的 `cargo:include=` 路径是否是同一个；
3. 如果 CMake 的 `install` 只装了 `MNN/` 没装 `llm/`，回 MNN 源码树里补 `transformers/llm/engine/include/llm`（第 28 章的补丁与此直接相关）。

#### 26.3.2 ABI：三处必须对齐

| 对齐项 | 本项目取值 | 不一致时的后果 |
|---|---|---|
| 目标架构 | `arm64-v8a` / `aarch64-linux-android` | 链接器报 `file format not recognized` 或 `incompatible` |
| API level | MNN 用 `android-24`；`mnn-rs-sys` 硬编码 `api_level = 24`（`[依赖源码已核实]`，第 435 行）；项目侧 `src-tauri/tauri.conf.json` 未设置 `bundle.android.minSdkVersion`，Tauri Android 使用默认值 24（`[仓库已核实]`） | MNN 用 26 而设备/应用最低 24 → 调用 26 才有的符号时 `dlopen`/加载失败 |
| STL | `c++_static`（构建脚本声明） | 混用共享 STL → ODR 冲突、随机崩溃 |

**API level 的机制**：`android-24` 不是“编译时用的 SDK 版本号”这么简单，它决定了链接时能看到哪些 libc/libm 符号（新版 API 才有的函数不会给你）。如果库按 26 编译、运行在 24 的设备上，链接期不会报错，运行期会因找不到符号而失败。

#### 26.3.3 未复核的细节：`libc++_shared.so` 与 `c++_static` 的矛盾

历史记录里 `mnn_smoke` 的 `NEEDED` 列表包含 `libc++_shared.so` `[历史记录]`，而依赖源码明确要求 `c++_static`（`[依赖源码已核实]`）。这两种记录互相矛盾，可能的解释：

1. **该产物不是由 `cargo build` 直接产生的**，而是走了 Gradle/tauri-cli 的 Android 构建（其模板或 AGP 配置可能引入 `c++_shared`）；
2. **构建时环境里另有链接参数**（例如 `RUSTFLAGS`、`.cargo/config.toml` 的 `rustflags`、或 wrapper 编译时的其他 `-stdlib` 选项）覆盖了脚本意图；
3. **历史记录本身标注有误**（例如把 `libc++_shared.so` 与别的产物混淆）。

**结论状态**：`[未复核]`。不改写历史记录，也不把它当成结论。

**复核方法**（三步，全部可执行）：

```powershell
# 1. 看实际依赖
& "$TOOLS\llvm-readelf.exe" -d .\mnn_smoke | Select-String "NEEDED|SONAME"

# 2. 看 libc++ 符号从哪来：静态链接时 std 符号应在 .symtab 里有本地定义
& "$TOOLS\llvm-nm.exe" -C .\mnn_smoke | Select-String "std::__ndk1::basic_string" | Select-Object -First 5

# 3. 重新构建并保留详细输出，确认 build.rs 的链接指令
$env:MNN_DEBUG_BUILD = "1"
cargo build -v --target aarch64-linux-android --release --features local-mnn --example mnn_smoke 2>&1 |
  Tee-Object -FilePath .\mnn-build.log
Select-String "cargo:rustc-link-lib" .\mnn-build.log
```

判读标准：

- 若第 3 步显示 `cargo:rustc-link-lib=static=c++_static` 且第 1 步仍出现 `libc++_shared.so`，说明有第二方（Gradle 或其它依赖）引入了共享 STL；
- 若第 2 步能 nm 到 `std::__ndk1` 的本地定义（`t`），说明静态 STL 确实被链入，`NEEDED` 里的 `libc++_shared.so` 可能来自另一个共享依赖（需逐个查 `DT_NEEDED` 的提供者）。

### 26.4 常见坑与判别方法

| 错误/现象 | 原因 | 排查路径 |
|---|---|---|
| `undefined reference to 'std::__ndk1::...'` | STL 未链接，或链接的是另一套 ABI 命名空间（如 `std::__1`） | `cargo build -v` 看是否有 `c++_static`；`llvm-nm -C libmnn.a \| Select-String "__ndk1"` 确认库侧命名空间 |
| 启动即 `java.lang.UnsatisfiedLinkError` / `dlopen failed: library "libc++_shared.so" not found` | APK 里没带 `libc++_shared.so`，或 ABI 目录不匹配 | 解包 APK（`unzip -l`）看 `lib/arm64-v8a/`；`llvm-readelf -d` 看 `NEEDED` |
| 构造阶段崩溃（`signal 11`，栈在 `__cxa_...`） | 两份 libc++ 混用，或全局对象初始化顺序问题 | `llvm-readelf --dyn-syms` 查 STL 符号来源；试 `c++_shared` 与 `c++_static` 二选一 |
| 同一函数在 A 设备正常、B 设备崩 | API level 差异导致符号缺失 | `llvm-readelf --version-info` 查符号版本；对比设备 API |
| 结构体字段值错乱 | 头文件与库不配套 | 重新 staging，确保 include 与 `.a` 来自同一次构建；用 `static_assert(sizeof(X)==...)` 自查 |
| 链接报 `incompatible target` | 架构/ABI 不匹配 | `llvm-readelf -h` 看 `Machine` 与 `Flags`（ARM64 的 `Tag_ABI_VFP_args` 等） |

### 26.5 小结

1. 头文件只保证声明；结构体布局、枚举值、内联函数仍可能因版本不一致而出错。
2. `extern "C"` 统一名字与调用约定，不统一 STL 与类型布局——边界上只用 C 兼容类型。
3. Android 上 STL 必须二选一：`c++_static` 或 `c++_shared`；混用是 ODR 冲突。
4. 本项目的架构/API/STL 三处对齐值分别是 `arm64-v8a`、`android-24`、`c++_static`；前两项有代码依据，第三项与历史 `NEEDED` 记录存在矛盾，标注 `[未复核]` 并给出复核步骤。
5. 排查顺序永远是“编译错误 → 链接错误 → 加载错误 → 运行错误”，不要跳步。

### 26.6 练习题

**第 1 题**：为什么“编译通过”完全不能证明“头文件与库配套”？

**参考答案要点**：
- 编译器只校验你代码与头文件之间的一致性，不知道库的真实实现；
- 头文件可能来自旧版本，结构体大小与库不一致；
- 只有链接（符号）和运行（布局/STL）才会暴露不匹配。

**第 2 题**：你的 APK 在 Android 14 上正常，在 Android 15 上装不上。列出两个最可能的原因和验证命令。

**参考答案要点**：
- 16 KB page 对齐问题（第 30 章）：`llvm-readelf -l` 看 LOAD 段 `Align` 是否为 `0x4000`；
- ABI 不匹配/仅 32 位库：`unzip -l app.apk | Select-String "lib/"` 看目录；
- 加分：targetSdk/权限变化导致的安装拒绝，用 `adb install` 的原始错误码判断。

**第 3 题**：如果必须改成 `c++_shared`，写出需要同步修改的三个位置。

**参考答案要点**：
- MNN 的 CMake 参数 `-DANDROID_STL=c++_shared`（否则静态库内部仍按 static 编译）；
- `mnn-rs-sys` 的 Android 链接声明（`c++_static` → `c++_shared`），或提供等价的链接参数；
- APK 打包：确保 `libc++_shared.so` 进入 `jniLibs/arm64-v8a/`，且整个 APK 只有一份。

## 第 27 章 静态与动态的取舍

### 27.1 本章要解决什么问题

第 23 章讲了两种形态的区别，本章回答“什么时候该选哪个”。这不是风格问题，而是由部署方式、团队协作、许可证和故障容忍度共同决定的工程决策。

本章给出一张决策表、一个决策树，以及本项目“现在静态、以后可能动态”的具体切换清单。

### 27.2 概念：五个维度上的差异

#### 27.2.1 体积

- 静态：可执行文件包含用到的代码。单个文件变大，但**总部署体积**可能更小（无需额外 `.so`）。
- 动态：可执行文件小，但 `.so` 单独存在；多个程序共用同一 `.so` 时总积更省。

**容易忽略的点**：动态方案里，`.so` 的符号表和重定位信息必须保留，通常比静态裁剪后的代码更大。所以“动态一定更小”是错的。

#### 27.2.2 启动与加载

- 静态：启动即执行，没有“找库”阶段。
- 动态：启动多了一步 `linker64` 解析 `DT_NEEDED`。库多时这一步可能几十毫秒；库缺失时直接失败。

#### 27.2.3 升级与替换

- 静态：换引擎必须重编整个程序。
- 动态：理论上可以只替换 `.so`；但 ABI 必须兼容，否则崩溃比不升级更糟。

#### 27.2.4 多进程与内存

- 动态库的代码段在多个进程间共享物理内存（只读映射）；静态则是每进程一份。
- 对手机应用，通常只有一个进程，这一项收益有限。

#### 27.2.5 许可证

这是容易被忽略但会带来法律风险的一项：

- **Apache-2.0**（MNN 本体）：允许静态或动态链接，义务主要是保留许可证与 NOTICE。
- **LGPL**（某些库）：动态链接通常被视为“独立作品”，静态链接则可能触发“必须提供可重新链接的目标文件”等义务。

**结论**：许可证决定的是“能不能静态”，不是“哪个更好”。本项目 MNN 是 Apache-2.0，静态是允许的（细节见附录 D）。

### 27.3 本项目实例：当前静态，切换动态要动哪里

#### 27.3.1 现状

- MNN 以 `MNN_BUILD_SHARED_LIBS=OFF` 构建成 `libMNN.a`；
- Rust 侧 `features = ["cpu", "static", "llm"]`；
- 产物 `mnn_smoke` 是单个可执行文件，`NEEDED` 只有 5 个系统库 `[历史记录]`；
- Tauri 应用侧，Android 打包只处理 `libapp_lib.so`（Rust 的 `cdylib`），MNN 已经静态合并进它。

#### 27.3.2 切换清单（如果你要试动态）

```
① 重编 MNN：MNN_BUILD_SHARED_LIBS=ON，MNN_SEP_BUILD 视需要
        ↓ 产物 libMNN.so（可能还有 libllm.so，取决于 SEP_BUILD）
② Rust：features 改成 ["cpu", "dynamic", "llm"]（mnn-rs 的两个 feature 互斥）
        ↓ 链接期只记录 NEEDED
③ 打包：libMNN.so（及其依赖）→ src-tauri/gen/android/app/src/main/jniLibs/arm64-v8a/
        ↓ Gradle mergeJniFolders 收进 APK
④ 校验：llvm-readelf -d 看 SONAME/NEEDED；llvm-readelf -l 看 16 KB 对齐
        ↓
⑤ 运行：设备上跑，确认无 dlopen 失败
```

每一步的失败信号：

| 步骤 | 失败信号 | 处理 |
|---|---|---|
| ① | `MNN_BUILD_SHARED_LIBS=ON` 后 CMake 报 target 冲突 | 检查 `MNN_SEP_BUILD` 的取值组合，第 28 章有说明 |
| ② | 同时启用 `static` 与 `dynamic` → 构建期 panic | 只保留一个（`build.rs` 第 250–257 行有明确报错文案） |
| ③ | 安装后 `dlopen failed: library "libMNN.so" not found` | 解包 APK 看目录；检查 `abiFilters` 是否只剩 `arm64-v8a` |
| ④ | `NEEDED` 里出现构建机的绝对路径 | 说明 soname 没设好；需要 `-Wl,-soname,libMNN.so` |
| ⑤ | 启动即崩，`logcat` 里有 `avc: denied` | SELinux 问题（第 36 章） |

**未验证项**：`MNN_SEP_BUILD=OFF` 时 `libMNN.so` 是否把 LLM 引擎一起打进同一个 `.so`，本项目没有做过这个实验。验证方法：打开 `MNN_BUILD_SHARED_LIBS=ON` 构建一次，`llvm-readelf -d libMNN.so` 看它是否依赖 `libllm.so`；再 `llvm-nm -D -C libMNN.so | Select-String "Transformer::Llm"` 看符号在不在主库。

#### 27.3.3 为什么本项目“现在不改”

- 实验目标是**同口径性能对照**，静态产物少一个变量；
- 真机推送流程是 `adb push` 单个可执行文件 + 模型目录，静态最省事；
- 动态方案会引入 APK 打包环节，而 Windows 上这个环节更容易被误判（第 32 章的对照实验说明：真实原因多为 NDK 指向错误或命令沙箱写限制，而不是“符号链接权限不足”）。

### 27.4 概念对比表（可直接用于评审）

| 维度 | 静态 `.a` | 动态 `.so` | 本项目取舍 |
|---|---|---|---|
| 缺库报错时机 | 链接期 | 运行期 | 选静态，把风险前移 |
| 单文件体积 | 大 | 小 | 可接受（5.0 MB `[历史记录]`） |
| 部署文件数 | 1 | ≥2 | 静态更适合实验 |
| 升级方式 | 重编 | 换文件 | 实验期不需要热替换 |
| 多进程共享 | 无 | 有 | 单进程，无收益 |
| 符号冲突风险 | 高（全局符号合并） | 中（可隔离） | 当前无冲突 |
| 许可证限制 | 取决于库 | 更宽松 | Apache-2.0 两者皆可 |
| 调试难度 | 符号在本体内，好查 | 需确认加载的是哪个版本 | 静态更易排查 |

### 27.5 常见坑与判别方法

| 现象 | 原因 | 处理 |
|---|---|---|
| 同时开 `static` 与 `dynamic` feature，构建直接 panic | 两个 feature 互斥（`build.rs` 显式检查） | 只选一个；别在 workspace 级 feature 里同时打开 |
| 静态链接后两个库的同名全局符号打架 | 静态合并时全局符号进了同一命名空间 | `-Wl,--allow-multiple-definition`（危险）、或给符号加 visibility 隐藏、或改动态 |
| 动态库版本替换后崩溃 | ABI 不兼容（结构体/STL 变了） | 用 `llvm-readelf --version-info` 对比；保留旧库回滚 |
| `ldd` 在手机上不可用 | Android bionic 没有 `ldd` | 在宿主机用 `llvm-readelf -d` / `llvm-objdump -p` 分析 |
| `.so` 被 strip 后无法定位崩溃 | 符号被删 | 保留一份未 strip 的符号文件（`llvm-objcopy --only-keep-debug`） |

### 27.6 小结

1. 静态把风险前移到链接期，动态把风险后移到运行期；实验阶段优先选前者。
2. “动态一定更小”是误解：动态库必须保留符号与重定位信息。
3. 许可证是硬约束：LGPL 倾向动态，Apache-2.0 两者皆可，但仍需保留 NOTICE。
4. 本项目选择静态的三条理由：单文件部署、少一个打包环节、少一类失败点。
5. 切换动态的五个步骤与各自失败信号，可以直接当作 checklist 用。

### 27.7 练习题

**第 1 题**：一个团队要发布两个安卓应用，都用到同一个 30 MB 的推理引擎。静态还是动态更省用户总下载量？说明前提。

**参考答案要点**：
- 若两个应用各自独立发布、用户可能只装一个：静态通常更省（动态仍要各带一份 `.so`）。
- 若用户几乎都装两个，且两个应用可共享同一 `.so`（同一签名/同一安装来源才可能共享，实际 Android 上不同 APK 不共享）：静态不省。
- 关键点：Android 不同应用之间**不会**共享 `.so` 的映射，所谓“共享”只在同一进程内。因此对多 APK 场景，静态与动态的总下载量差别不大，动态反而多一层失败点。

**第 2 题**：为什么 `mnn-rs-sys` 要在构建期 `panic!` 阻止同时启用 `static` 和 `dynamic`，而不是默默选一个？

**参考答案要点**：
- 两种链接方式的符号解析、依赖记录、部署方式完全不同，混用会产生难以解释的行为；
- 静默选择会让“我明明开了 dynamic 却没生成 `.so`”这种问题极难排查；
- 构建期报错是最便宜的失败。

**第 3 题**：写出检查一个 `.so` 是否满足 Android 16 KB page 要求的命令，并说明看哪个字段。

**参考答案要点**：
```powershell
& "$TOOLS\llvm-readelf.exe" -l libMNN.so
```
- 看 `LOAD` 段的 `Align` 列；16 KB 要求对齐到 `0x4000`（16384）。若为 `0x1000`，在 16 KB page 设备上可能无法加载（第 30、33 章）。
